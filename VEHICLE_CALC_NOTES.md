# Калькулятор транспорта (`service.VehicleCalc`) — статус и источники

Реализовано 2026-08-18 по запросу от менеджеров: на основании состава
проекта (кабинеты, железо, кофры коммутации) и с учётом того, что кофры
можно штабелировать, выдавать сообщение о том, какую машину минимально
рекомендуется заказать. Согласовано с пользователем через план — см. этот
файл как «выгрузку для других агентов»: что сделано, какие решения приняты
и почему, какие допущения нужно перепроверить, что отложено.

## Что реализовано

- `ledscheme-model`: `CaseType.java` (тип кофра — габариты, вес, лимит
  штабелирования, флаг `carriesCabinets` + вместимость `cabinetsPerCase`),
  `VehicleType.java` (тип машины — габариты кузова, грузоподъёмность). Оба —
  стандартный флат-POJO с `copy()`/`applyEditedValues()`, как у HoistType.
- `ledscheme-server`: `LibraryItemKind.CASE`, `LibraryItemKind.VEHICLE` —
  обычные (не-синглтон) виды, больше ничего на сервере менять не
  понадобилось (подтверждён рецепт «обычно больше ничего менять не нужно»
  из секции 3 CLAUDE.md — CRUD/синк уже kind-agnostic).
- `ledscheme-admin`: `CaseTypeFormPanel`/`VehicleTypeFormPanel`
  (`ui/library/`), зарегистрированы в `LibraryBrowserPanel` (KINDS,
  typedForms, LOCAL_LIBRARY_FIELDS для локального импорта library.json).
- Клиент (`VJsTB_reborn`):
  - `model/Library.java`/`model/Workspace.java` — поля `caseTypes`/
    `sharedCaseTypes`, `vehicleTypes`/`sharedVehicleTypes` + `caseTypeById`/
    `vehicleTypeById`, по образцу hoistTypes/structureFrameTypes.
  - `service/AppModel.java` — CRUD (`getCaseTypes`/`addCaseType`/...,
    аналогично для VehicleType), синк (`applyLibrarySyncItems`, кейсы
    `"CASE"`/`"VEHICLE"`) и удаление (`applyDeletion`).
  - `service/VehicleCalc.java` — сам алгоритм подбора (см. ниже).
  - `ui/VehicleCalculatorDialog.java` — диалог (таблица строк «тип кофра +
    количество», переключатель учёта веса, результат), вызывается из меню
    «Инструменты → Калькулятор транспорта…» (`ui/MainMenuBar.java`).
  - `service/VehicleCalcTest.java` — 9 тестов.

**Исправлено 2026-08-18 по прямому запросу пользователя**: изначально
авто-подстановка количества кофров-с-кабинетами считала кабинеты ВСЕГО
проекта (`service/ProjectStats.java` + `ScreenLogic.projectStats` — были
добавлены и затем удалены как ненужные, больше нигде не использовались).
Машина обычно возит содержимое ОДНОЙ сцены, не весь проект сразу — теперь
`VehicleCalculatorDialog.sceneCabinetTotal()` берёт `model.getCurrentScene()`
+ уже существующий (и уже протестированный в других местах, см.
`AppModelTest`) `ScreenLogic.sceneStats`. Никакого запаса/наценки авто-
подстановка не добавляет — это голое число кабинетов сцены; запас на
неполные/повреждённые/запасные кофры менеджер вписывает вручную поверх
подставленного значения (оно остаётся редактируемым, как и раньше).

## Неочевидные решения

**У CaseType нет дискриминатора вида (`Kind`-enum), в отличие от
StructureFrameType.** Там enum нужен потому что разные подвиды (рама/
стакан/контейнер балласта) требуют РАЗНЫХ полей (у стакана нет
height/width/depth). Здесь у любого кофра — под кабинеты, под коммутацию,
под прочее оборудование — один и тот же всегда осмысленный набор полей;
единственное содержательное различие, которое реально влияет на расчёт —
флаг `carriesCabinets`. «Кофр коммутации» из исходного запроса — просто
запись с этим флагом снятым, отдельная сущность не понадобилась.

**Удаление CaseType/VehicleType при синке — БЕЗ охраны от FK
(`removeSharedIfUnreferenced`), в отличие от HOIST/STRUCTURE_FRAME.** У тех
двух видов есть настоящие персистентные FK (`Screen.riggingHoistTypeId` и
три `Screen.structureXxxTypeId`) — удаление использованной записи молча
портит открытый проект, поэтому там нужна проверка ссылок. Калькулятор
транспорта — одноразовый stateless-диалог: строки «тип+количество» не
сохраняются в проекте, ничего не ссылается на CaseType/VehicleType по id
нигде в `Project`/`Scene`/`Screen`. Поэтому удаление безусловное — как у
CABLE/INTERFACE/CABLE_LENGTH_PROFILE. **Если в будущем появится
персистентная ссылка на CaseType/VehicleType — это место нужно будет
пересмотреть.**

**Авто-расчёт количества — только для кофров с `carriesCabinets`.** Остальные
виды кофров (коммутация, прочее оборудование) вводятся вручную — сознательно
не стали привязывать конкретные записи EQUIPMENT/CABLE/CABLE_LENGTH_PROFILE
к типам кофров (какая связка «столько-то метров кабеля = один кофр» — само
по себе неочевидный дополнительный расчёт, не входивший в исходный запрос).

**Штабелирование пересчитывается заново для КАЖДОЙ машины-кандидата**, а не
фиксируется один раз глобально (`VehicleCalc.checkFit` берёт
`vehicle.getCargoHeightMm()` внутри проверки). Единственная трактовка,
согласующаяся с требованием «высота кузова учитывается»: машина с меньшей
площадью пола, но более высоким кузовом может позволить более плотный
штабель и оказаться меньше по площади — фиксированная заранее высота
штабеля не даст правильно её выбрать. Диалогу из-за этого не нужен
отдельный контрол «уровень штабелирования» — он полностью определяется
`CaseType.maxStackCount` и высотой конкретного кандидата.

**`CaseType.weightKg` — номинальная спецификационная величина одного
гружёного кофра**, вводится в библиотеке вручную, НЕ выводится из
фактического содержимого проекта (веса реальных кабинетов/оборудования в
этом кофре). Учёт веса в калькуляторе — опциональный переключатель
(по требованию пользователя), по умолчанию включён.

## Явные допущения (v1, требуют проверки на реальных данных)

- **Площадь — простая сумма**, без 2D-раскладки (bin packing) и без запаса %
  на неидеальную укладку (в отличие от `CableSpecCalc`, где запас % есть).
  Оптимистичная оценка: угловатые/неправильно сочетающиеся по размеру кофры
  реально в кузове могут не улечься так плотно, как показывает сумма
  площадей. Диалог явно предупреждает об этом в тексте результата.
- Ранжирование «от меньшей к большей» машины — площадь пола по возрастанию,
  тай-брейки высота кузова → грузоподъёмность. Не привязано к реальной
  стоимости/классу машины (площадь как прокси для размера — разумное, но не
  проверенное реальными тарифами допущение).
- Внешняя методология НЕ привлекалась — алгоритм полностью задан
  требованиями пользователя (простое сравнение площадей + учёт высоты +
  опциональный вес), в отличие от RIGGING_CALC_NOTES.md/
  STRUCTURE_CALC_NOTES.md, где есть источники по грузоподъёмности/
  конструктиву для сверки.

## Визуализатор загрузки — MVP, реализован 2026-08-18

По запросу пользователя добавлен первый заход визуализатора (ранее был в
«явно отложено» ниже — теперь частично сделан, доработка по референсным
фото пользователя ожидается позже):

- `ui/VehicleLoadCanvasPanel.java` — вид сверху на грузовой отсек выбранной
  машины (масштабируемый прямоугольник по образцу `CanvasEditorPanel`/
  `ContentCanvas`), кофры — перетаскиваемые мышью прямоугольники L×W.
- `ui/VehicleLoadVisualizerDialog.java` — обвязка: комбобокс машины, меню
  выбора кофра (список слева + кнопка «Добавить»), легенда цветов.
  Открывается кнопкой «Визуализация загрузки…» в `VehicleCalculatorDialog`.
  **Исправлено по прямому запросу пользователя**: изначально меню выбора
  показывало ВСЮ библиотеку кофров (`model.getCaseTypes()`), а строки из
  калькулятора были только подсказкой «нужно: N». Теперь меню строится
  ИСКЛЮЧИТЕЛЬНО из строк, которые менеджер ввёл в калькуляторе
  (`neededCounts`, из `VehicleCalc.CaseRow`) — полная библиотека сюда не
  подмешивается вообще. Кнопка «Добавить» дополнительно блокируется
  (`remainingFor(type) <= 0`), как только для типа размещено ровно столько,
  сколько было указано — нельзя разместить больше реального расчёта.
- **Цвет — временное правило по прямому указанию пользователя**: кофры с
  `carriesCabinets == true` чёрные, все остальные (коммутация и прочее)
  синие. Модель не различает «коммутацию» отдельным полем от прочих не-
  кабинетных кофров — правило различает только по единственному булеву
  флагу, который уже есть. Пользователь обещал прислать референсные
  фото позже — тогда, вероятно, потребуется полноценное поле категории/
  цвета на CaseType вместо этого бинарного правила.
- **Пересечение кофров запрещено** (в отличие от `CanvasEditorPanel`, где
  экраны на канвасе маски МОГУТ пересекаться) — перетаскивание на позицию,
  которая пересекает другой кофр или выходит за пределы кузова, откатывается
  на позицию до начала перетаскивания. Кофр, брошенный почти точно (≥50%
  площади меньшего прямоугольника) на другой кофр ТОГО ЖЕ типа — уходит в
  штабель (счётчик уровней на месте вместо второго прямоугольника,
  ограничен `CaseType.maxStackCount`), а не трактуется как пересечение.
- **Без персистентности** — раскладка живёт только в памяти диалога,
  закрытие диалога её теряет. Осознанно для MVP (см. «явно отложено» про
  привязку к штабелированию/раскладке проекта, если решим сохранять).
- **Смена машины сбрасывает раскладку целиком** — пространство определяется
  габаритами конкретной машины, показывать прежние позиции под другой кузов
  было бы вводящим в заблуждение.
- Тестов нет — чисто интерактивная Swing-панель (drag/drop, paintComponent),
  как и `Structure3DPanel`/`CanvasEditorPanel`, которые тоже без тестов в
  этом кодовой базе.

## Область расчёта (сцена/проект/несколько сцен) + разбивка на несколько машин + прилипание + примечания — 2026-08-18

Четыре доработки в один заход, все по прямым запросам пользователя:

**Область расчёта авто-количества** (`VehicleCalculatorDialog.CalcScope`,
комбобокс «Область расчёта:» вверху диалога) — три режима вместо жёстко
зашитой «текущая сцена»:
- `SCENE` (по умолчанию) — как раньше, `ScreenLogic.sceneStats(model.getCurrentScene(), ...)`.
- `PROJECT` — весь проект разом, `ScreenLogic.cabinetCountAcross(project.getScenes(), ...)`.
- `CUSTOM` — вручную выбранный набор сцен (диалог-чекбокс-лист, `pickScenes(...)`),
  тот же `cabinetCountAcross` на произвольном подмножестве.

`ScreenLogic.cabinetCountAcross(List<Scene>, Workspace)` — новый переиспользуемый
метод (сумма `sceneStats(...).totalCabinetCount()` по списку сцен). Это
концептуально то же самое, что раньше делал удалённый `ScreenLogic.projectStats`
(см. секцию выше про его удаление) — но теперь у суммирования по списку сцен
ДЕЙСТВИТЕЛЬНО два независимых вызывающих (весь проект и произвольное
подмножество), так что реюз оправдан, в отличие от прошлого раза, когда
был только один вызывающий с неверным по умолчанию охватом.

**Несколько машин сразу в визуализаторе** (`VehicleLoadVisualizerDialog.VehicleSection`) —
по запросу «одну сцену можно укладывать в несколько машин»: диалог теперь
держит список секций-машин (каждая — свой холст `VehicleLoadCanvasPanel` +
свой комбобокс типа машины + кнопки «Добавить сюда»/«Убрать машину»), кнопка
«+ Добавить машину» наверху добавляет ещё одну карточку снизу и раздвигает
окно (`repackWindow()`, до `MAX_SECTIONS_VIEWPORT_HEIGHT`=640px, дальше —
прокрутка вместо бесконечного роста окна). Меню выбора кофра ОБЩЕЕ на все
машины сразу — `remainingFor(type)` считает уже размещённое across ВСЕХ
секций, а не одной; у каждой карточки СВОЯ кнопка «Добавить сюда» (кладёт
выбранный в общем меню тип именно в эту машину) — так менеджер вручную
распределяет кофры между несколькими машинами, если одна не устраивает.
Убрать машину с уже размещёнными в ней кофрами — запрашивает подтверждение
(`JOptionPane.YES_NO_OPTION`), нельзя остаться вообще без машин (минимум одна).

**Прилипание к соседним кофрам** (`VehicleLoadCanvasPanel.snapEnabled`) —
переключатель ЖИВЁТ в окне калькулятора (`VehicleCalculatorDialog.snapCheck`,
чекбокс «Прилипание кофров в визуализаторе», применяется через
`VehicleLoadVisualizerDialog.setSnapEnabled(...)` перед показом диалога и
распространяется на все секции-машины), не в самом визуализаторе — по
прямому указанию пользователя. В отличие от `CanvasEditorPanel` (там Shift
включает прилипание НА ВРЕМЯ перетаскивания) — здесь это постоянный
переключатель, без модификатора клавиши. Прилипает к краям ДРУГИХ кофров
и краёв кузова в пределах 10 экранных px (переведено в мм через текущий
scale), без плавного "blend" — при попадании в порог сразу прилипает вплотную.

**Примечание менеджера по ПКМ** (`VehicleLoadCanvasPanel.Placement.note`,
`editNote(...)`) — правый клик по размещённому кофру открывает
`JOptionPane.showInputDialog` с текущим примечанием (пусто — не задано),
результат сохраняется и рисуется отдельной строкой под именем кофра
(другим цветом, чтобы отличаться от имени типа). Пустое примечание/Отмена —
без изменений.

**Баг-репорт, исправлен тем же заходом**: счётчик штабеля («×N») пропадал
целиком на маленьких отпечатках, потому что раньше рисовался ОДНОЙ строкой
с именем кофра («Имя ×N») — если вся строка не влезала по ширине, весь
label (вместе с ×N) просто не рисовался. Теперь счётчик — отдельный бейдж
в углу (`drawStackBadge`), рисуется НЕЗАВИСИМО от имени и всегда, пока
`stackCount > 1`, размер шрифта подстраивается под отпечаток (не мельче 9pt).

## Drag-n-drop, запас по периметру, свой тип кофра — 2026-08-18

Три доработки следом, снова по прямым запросам пользователя:

**Drag-n-drop из палитры в машину** (`VehicleLoadCanvasPanel.CASE_TYPE_FLAVOR`,
`addPlacementAt`, `pxToMm`; `VehicleLoadVisualizerDialog` — `TransferHandler`
на палитре как источник, на каждой секции-машине как приёмник) — тащим тип
кофра из общего меню слева прямо на нужную машину, кофр появляется под
курсором (с центрированием), не всегда в углу. Кнопка «Добавить сюда»
осталась как альтернатива (мышь/доступность). Локальный
{@code DataFlavor(javaJVMLocalObjectMimeType + ";class=CaseType")} — обмен
только внутри одной JVM, без сериализации. Слева также появился всегда
видимый жирный «Осталось разместить: X из Y» — суммарно по всем типам сразу
(построчные «нужно/осталось» в самом списке остались как были).

**Запас по периметру кофра** (`CaseType.clearanceMm`, по умолчанию 50мм/5см,
запрос пользователя: «кофры всегда в машине будут располагаться не совсем
впритирку») — новое поле модели (ledscheme-model, + форма в ledscheme-admin),
используется в двух местах:
- `VehicleCalc.checkFit` — площадь каждой занятой позиции пола теперь
  {@code (L+clearance)×(W+clearance)}, не голое L×W.
- `VehicleLoadCanvasPanel` — коллизии между РАЗНЫМИ кофрами проверяются с
  раздвижкой на суммарный зазор {@code (a.clearanceMm + b.clearanceMm)/2}
  (см. `overlaps`) — по половине запаса с каждого кофра, чтобы пара кофров
  с одинаковым дефолтом получала между собой ровно 50мм, а не 100мм. Цели
  прилипания (`snap`) для касания соседа тоже сдвинуты на этот зазор — снап
  ставит кофр не впритирку, а на минимально допустимом расстоянии. Запас
  применяется ТОЛЬКО между кофрами, не у стенок кузова (штабелирование —
  `overlapArea`/`resolveDrop` — НЕ инфлейтится, это намеренное почти-полное
  перекрытие, не соседство).
  Существующие тесты `VehicleCalcTest` явно зануляют `clearanceMm=0` в своём
  тестовом хелпере (чтобы не завязываться на дефолт) — отдельный
  `checkFit_addsClearanceAroundEachFootprint` проверяет сам запас.

**Свой тип кофра прямо в калькуляторе** (`ui/CaseTypeDialog.java`, кнопка
«+ Новый тип кофра…» рядом с «Добавить строку» в `VehicleCalculatorDialog`) —
по образцу `CableLengthProfileDialog`/`WireLabelDialog.registerAsAdapter`:
модальная форма со всеми полями CaseType (те же, что в админ-форме, включая
clearanceMm), `showDialog()` возвращает объект или null. При сохранении:
`model.addCaseType(...)` в личную библиотеку → сразу новая строка в таблице
кофров (не нужно ещё раз искать в комбобоксе) → `ProposeDialog.show(...)`
предлагает отправить тот же объект на модерацию в общую библиотеку (тот же
приём, что и у переходников/каталогов длин кабеля в WireLabelDialog).
`VehicleCalculatorDialog` теперь принимает `SettingsManager settings`
третьим параметром конструктора (нужен для ProposeDialog — проверяет, что
пользователь вошёл в аккаунт) — `MainMenuBar.buildToolsMenu` прокидывает его
из своего конструктора.

## Два UI-фикса по скриншотам пользователя — 2026-08-18

**Панель кофров стала растягиваемой** — раньше сидела в `BorderLayout.WEST`
с фиксированным `setPreferredSize(220, 10)`, из-за чего текст «нужно: N,
осталось: M» обрезался до горизонтальной прокрутки списка (баг-репорт со
скриншотом). Заменено на `JSplitPane` (палитра слева, машины справа,
`resizeWeight=0.25`) — тот же приём, что уже использует `ScenarioEditorPanel`
в этом кодовой базе для похожей раскладки «список слева / контент справа».
Пользователь теперь сам двигает разделитель.

**Подпись типа/примечания у повёрнутого кофра не рисовалась** — тот же класс
бага, что уже чинили для счётчика штабеля (см. выше): имя/примечание
рисовались ОДНОЙ горизонтальной строкой и просто не рисовались вообще, если
не влезали по ширине — а у повёрнутого (или изначально узкого) кофра ширина
отпечатка маленькая. Первая версия фикса добавила вертикальный вариант
(`drawVerticalString`, `Graphics2D.rotate`) — но выбирала ориентацию для
каждой строки НЕЗАВИСИМО (свой best-fit у имени, свой у примечания), из-за
чего у одного и того же повёрнутого кофра имя оказывалось вертикальным, а
примечание — горизонтальным (баг-репорт со скриншотом: «лейбл примечания в
повёрнутом кофре не поворачивается»). Исправлено во втором заходе (см. ниже,
секция про зум) — ориентация теперь следует {@code p.rotated}, а не
независимому фиту каждой строки.

## Приближение (зум), масштабируемые подписи, растровый рендер — 2026-08-18

Три доработки в один заход, по прямым запросам пользователя.

**Приближение** (`VehicleLoadCanvasPanel.zoom`/`setZoom`/`zoomBy`) — Ctrl+колесо
мыши над холстом, либо кнопки «−»/«100%»/«+» в шапке каждой карточки-машины
(добавлены для discoverability — не все догадаются про Ctrl+колесо). Диапазон
0.3×–5×. Реализовано как множитель поверх базового "вписать в вид" масштаба
(`baseFitScale`, пересчитывается ТОЛЬКО при смене машины — от опорного
размера вьюпорта 600×190, не от живых `getWidth()/getHeight()` холста, иначе
получилась бы обратная связь: выросший preferred size менял бы getWidth(),
которая меняла бы scale(), которая опять меняла бы preferred size).

Каждый холст теперь обёрнут в СВОЙ `JScrollPane` (`VehicleSection` в
`VehicleLoadVisualizerDialog`) — `VehicleLoadCanvasPanel.getPreferredSize()`
растёт вместе с зумом, и когда содержимое перестаёт помещаться в исходный
600×190 — появляется прокрутка вместо вылезания за карточку. Обычное (без
Ctrl) колесо мыши над холстом руками прокидывается в вертикальный скроллбар
этого JScrollPane (`SwingUtilities.getAncestorOfClass(JScrollPane.class,
this)`) — Swing не форвардит колесо в scroll pane автоматически, если у
дочернего компонента уже есть свой `MouseWheelListener` (нужен для Ctrl+зума).

**Подписи масштабируются вместе с блоком** (запрос пользователя) — шрифты
имени/примечания/подписи машины внизу и толщина линий (граница кузова,
граница кофра) больше не фиксированы в pt/px, а умножаются на `zoom`
(clamped, чтобы не улетали в абсурд на краях диапазона). Бейдж штабеля
(`drawStackBadge`) и раньше подстраивался под размер САМОГО отпечатка —
теперь его верхний потолок тоже растёт с zoom, а не упирается в старый
фиксированный максимум.

**Растровый DPI 300 в ЖИВОМ холсте не применён — осознанно, ПОДТВЕРЖДЕНО
пользователем, что это верно.** Изначальная формулировка запроса ("система
рендера аналогично выводу документации с dpi 300") звучала как про сам
интерактивный холст — живая Swing-панель уже векторная (Java2D `Graphics2D`
с антиалиасингом), приближение остаётся чётким на любом zoom без
DPI-параметра, растровый рендер ВНУТРИ холста был бы шагом назад (потерял
бы чёткость при дальнейшем приближении). Пользователь затем уточнил, что
имел в виду другое: DPI 300 для ЭКСПОРТА схемы размещения в пакет
документации — тот же смысл, что у существующих JPEG-схем расключения
(`SchemeRenderer`). Реализовано отдельным заходом, см. секцию «Экспорт
схемы размещения в документацию» ниже — вывод про сам холст остаётся в
силе, он просто отвечал не на тот вопрос.

**Исправление ориентации имя+примечание у повёрнутого кофра** — та же
причина, что описана выше, но теперь у обеих подписей (имя и примечание)
единая логика: `p.rotated ? (fitsVertical || !fitsHorizontal) :
(!fitsHorizontal && fitsVertical)`. При повороте кофра (R) обе подписи
пытаются встать вертикально В ПЕРВУЮ ОЧЕРЕДЬ (с фит-проверкой как страховкой,
на случай если даже предпочитаемая ориентация не влезает вовсе) — больше не
может получиться так, что имя вертикальное, а примечание горизонтальное на
одном и том же повёрнутом кофре.

## Персистентность раскладки (в т.ч. облако) — 2026-08-18

Запрос пользователя: «сохранение списков и раскладок в машинах как это
работает для всех наших схем, включая выгрузку в облако» — реализовано БЕЗ
единой строчки нового кода синхронизации, чисто подключением к уже
существующей генерической персистентности проекта (см. исследование перед
реализацией — `Project`/`Scene` сериализуются Jackson'ом целиком и локально
(`WorkspaceStore`), и при выгрузке в облако (`CloudProjectsDialog.upload()`
делает `MAPPER.writeValueAsString(project)` без отдельного DTO), сервер
хранит присланный `project_json` как opaque TEXT-блоб (см. миграции
`V2__project_archives.sql`/`V3__project_versions.sql` в ledscheme-server) —
любое новое поле на `Scene`/`Project` с геттером/сеттером едет бесплатно
везде, тот же принцип, что уже подтверждён на `ContentCanvas`/`SchemaNode`).

**Новые модельные классы** (`model/VehicleLoadPlan.java`,
`VehicleLoadSection.java`, `VehicleLoadPlacement.java`) — персистентная
форма `VehicleLoadCanvasPanel.Placement`/секций диалога. Ссылаются на
`CaseType`/`VehicleType` ПО ID (`caseTypeId`/`vehicleTypeId`), не embed'ят
объект — тот же приём, что у `Screen.cabinetTypeId`/`riggingHoistTypeId`
(резолвится через `Workspace.caseTypeById`/`vehicleTypeById`). **Ровно один
план на сцену** (не список именованных вариантов) — осознанное упрощение
v1, поле `Scene.vehicleLoadPlan` (nullable, рядом с `canvases`/`schemaNodes`
— тот же паттерн «плоское поле на Scene»).

**Область (сцена/проект/несколько сцен, см. выше) сознательно НЕ определяет,
куда сохраняется план** — план ВСЕГДА привязывается к `model.getCurrentScene()`
на момент открытия визуализатора, независимо от того, что было выбрано в
`scopeCombo` калькулятора. Так проще и предсказуемее, чем пытаться
персистить план, охватывающий несколько сцен, куда-то ещё («план для
нескольких сцен» — самостоятельная задача, не запрашивалась).

**`AppModel.saveVehicleLoadPlan(Scene, VehicleLoadPlan)`** — новый публичный
метод, по образцу `movePlacement`/`removePlacement` (тот же класс): просто
`scene.setVehicleLoadPlan(plan); changed();`. Специально БЕЗ `pushUndo` —
раскладка меняется слишком часто (каждое перетаскивание/поворот/примечание)
для содержательных записей в отменяемой истории проекта; интеграция с undo
не запрашивалась.

**Загрузка/сохранение в `VehicleLoadVisualizerDialog`**: `loadOrInitSections`
при открытии восстанавливает сохранённый план (кофры/машины, которых больше
нет в библиотеке — id не резолвится — молча пропускаются, тот же приём, что
у комбобоксов SetupStagePanel), `persistPlan` сериализует текущее состояние
и сохраняет — вызывается из `refreshAll()` (единая точка "что-то
изменилось" уже существовала, персистентность просто ещё одна её
обязанность). Восстановление идёт БЕЗ проверки коллизий (`
VehicleLoadCanvasPanel.restorePlacement`, отдельно от `addPlacementAt`) —
позиция уже была валидна при сохранении, повторная проверка рискует
разойтись с оригиналом при, например, более позднем изменении `clearanceMm`
типа кофра в библиотеке.

Запрос пользователя (уточнение после первой, неверно понятой версии запроса
про DPI — см. выше): рендер схемы размещения в пакет документации проекта,

## «Разместить всё» — автоматическая раскладка в визуализаторе — 2026-08-20

Запрос пользователя: "кофры все должны максимально добавиться в машину с
учётом этажирования и распределяться по машине" — кнопка в карточке КАЖДОЙ
машины визуализатора (рядом с «Добавить сюда»), автоматически расставляющая
СРАЗУ ВСЕ ещё не размещённые типы кофров (не один выбранный в меню).

**`VehicleLoadCanvasPanel.autoPlaceAll(Map<CaseType,Integer> needed)`** —
простой shelf-алгоритм (не настоящий 2D bin-packing оптимизатор, см. п. ниже
про то, что по-прежнему отложено):
1. Штабелирование учитывается ЗАРАНЕЕ, не отдельным проходом: для каждого
   типа `effectiveStack = min(maxStackCount, floor(cargoHeightMm/heightMm))`,
   и нужное количество режется на "стопки" — в одну клетку пола сразу
   становится stackCount=effectiveStack (кроме последней неполной стопки).
2. Стопки сортируются по площади отпечатка по убыванию (first-fit-decreasing
   — простая эвристика против пустых зазоров, не полноценная оптимизация).
3. Ряды слева направо вдоль `cargoLengthMm`, перенос на новый ряд (по
   `cargoWidthMm`) когда очередной отпечаток не влезает в оставшуюся ширину
   текущего ряда. Запас по периметру типа (`clearanceMm`) добавляется К
   КАЖДОМУ отпечатку целиком (упрощение относительно ручного
   перетаскивания, где `overlaps`/`snap` делят зазор пополам между
   соседями) — гарантирует НЕ МЕНЬШЕ нужного зазора, первый элемент
   ряда/столбца прилегает к стенке кузова без зазора, как и при ручной
   раскладке.
4. Если отпечаток не влезает по длине кузова без поворота — пробует
   развёрнутый на 90°; если не влезает ни так, ни так, либо не хватило
   места по высоте ряда/ширине кузова — тип уходит в возвращаемый `leftover`
   (штук, которые не поместились), кузов при этом не "переполняется"
   молча.

**Метод ЗАМЕНЯЕТ, а не дополняет** текущие размещения этой машины
(`placements.clear()` в начале) — раскладка с нуля проще и предсказуемее,
чем 2D bin-packing вокруг уже существующих произвольно расположенных
вручную кофров (частный случай общей 2D-раскладки с препятствиями, которую
проект сознательно не делает, см. допущения выше). `VehicleLoadVisualizerDialog
.autoPlaceAllInSection` спрашивает подтверждение («Автоматическая раскладка
заменит текущее размещение...») ТОЛЬКО если в карточке уже что-то есть —
на пустой машине подтверждение не нужно.

**Несколько машин** — бюджет для конкретной карточки считается как `нужно
всего (neededCounts) − уже размещено в ДРУГИХ секциях`
(`placedInOtherSections`) — то есть при добавлении второй машины и повторном
клике «Разместить всё» на ней распределяется именно остаток, а не
дублируется уже пристроенное в первой. Если что-то не поместилось даже
после этого — статус-строка внизу диалога явно называет тип и количество и
подсказывает добавить ещё одну машину (та же ручная работа, что и раньше,
просто заготовка теперь автоматическая, а не построчная).

**`VehicleLoadCanvasPanelTest`** (новый файл, `ui` пакет — Placement
package-private, тест в том же пакете, как и остальной класс) — 8 тестов:
заполнение без остатка, штабелирование до раскладки (9 шт/maxStack=3 → ровно
3 позиции), остаток при нехватке площади, полный остаток при кофре выше
кузова, поворот на 90° когда влезает только боком, замена (не дополнение)
существующей раскладки, все позиции в границах кузова, пустой холст (машина
не выбрана) возвращает всё как остаток.

## Персистентность строк калькулятора (тип кофра → количество) — 2026-08-20

Баг-репорт: "если для проекта или сцены уже задавось количество кофров и их
раскладки в машинах, то при повторном вызове они должны подтягиваться,
сейчас табличка каждый раз пустая при открытии". Раскладка в кузове

`CaseType#getId()`) — та же генерическая Jackson-сериализация, что и у

РАСКЛАДКУ в кузове, это — исходные количества, из которых раскладка

PROJECT/CUSTOM областей восстановления НЕТ — единой сцены-владельца не
существует, таблица в этом случае по-прежнему стартует пустой (как и было
раньше для всех областей). Отдельного персистентного места для
"project-level" набора строк не заводили — не запрошено явно, и первый
(дефолтный, самый частый) сценарий "Текущая сцена" уже закрывает
зарепорченный баг.

Типы кофров, удалённые из библиотеки после сохранения строк, при
восстановлении молча пропускаются (id не резолвится) — тот же приём, что у
`VehicleLoadVisualizerDialog.loadOrInitSections` для устаревших ссылок.

полный цикл через РЕАЛЬНЫЙ файл (`AppModel` пересоздаётся с нуля на том же

что `AppModelTest.legacyPerPlacementMaskColorIsSeededOntoScreenOnLoad`.
`vehicleCaseCounts_defaultsToEmptyForNewScene` — новая сцена без сохранённых
строк не падает, возвращает пустую карту (не null).

## Персистентность распространена на PROJECT/CUSTOM — 2026-08-20 (тот же день)

Прямой вопрос пользователя после предыдущего раунда: "как будет работать
этот сценарий, если табличка собиралась для нескольких сцен сразу?" — честный
разбор кода показал реальную дыру, не просто отсутствие фичи: строки ВСЕГДА
сохранялись под `model.getCurrentScene()`, независимо от того, что было
выбрано в `scopeCombo` — то есть числа, посчитанные для "Весь проект" или
"Несколько сцен…", тихо утекали под какую-то одну сцену (ту, что была
активна в приложении в момент правки таблицы), и при следующем открытии либо
подтягивались под чужим ярлыком ("Текущая сцена", хотя считались иначе), либо
пропадали вовсе, если активная сцена успела смениться. Плюс сам выбор
области расчёта нигде не сохранялся — комбобокс всегда стартовал с "Текущая
сцена", даже если в прошлый раз работали с проектом целиком.

**`Project` получил 4 новых поля** (та же генерическая Jackson-сериализация,
без отдельного кода (де)сериализации):
- `vehicleCaseCountsProject` (`Map<String,Integer>`) — строки для области
  "Весь проект".
- `vehicleCaseCountsCustom` (`Map<String,Integer>`) + `vehicleCaseCustomSceneIds`
  (`List<String>`, id сцен) — строки для "Несколько сцен…" ВМЕСТЕ с тем,
  какие именно сцены были выбраны (без списка id восстановленные числа
  не с чем сверить — набор сцен мог быть любым подмножеством проекта).
- `vehicleCaseLastScope` (`String`, имя константы `CalcScope`) — какая
  область использовалась последней, восстанавливает выбор в `scopeCombo`.

**`AppModel`**: `saveVehicleCaseCountsProject`/`saveVehicleCaseCountsCustom`/
`saveVehicleCaseLastScope` — тот же приём (`set... ; changed();`), что уже
был у `saveVehicleCaseCounts` для сцены.

**`VehicleCalculatorDialog`**:
- `savedCountsForCurrentScope()` — единая точка выбора источника чтения по
  текущему `scope` (SCENE→сцена, PROJECT/CUSTOM→проект), используется
  `loadSavedRows()`.
- `persistRows()` переписан на `switch (scope)` — пишет в то же место,
  откуда читает `savedCountsForCurrentScope()`; для CUSTOM пишет
  `customScenes` вместе со счётчиками ЗА ОДИН вызов
  (`saveVehicleCaseCountsCustom(project, ids, counts)`), не двумя разными,
  чтобы не оставалось окна с рассинхроном id/counts.
- `restoreLastScope()` (новый метод, вызывается ПЕРВЫМ в конструкторе, до
  `loadSavedRows()`) — читает `Project#getVehicleCaseLastScope()`, для
  CUSTOM резолвит `vehicleCaseCustomSceneIds` в реальные `Scene` (сцены,
  удалённые из проекта с тех пор, молча пропускаются; если НИ ОДНА не
  резолвилась — остаёмся на дефолтном SCENE, не открываем диалог выбора
  сцен сами). **Критичная деталь реализации**: меняет `scopeCombo` НАПРЯМУЮ,
  временно сняв листенер (`scopeListener`, вынесен в именованное поле
  специально ради этого) — если бы восстановление шло через обычный путь
  (`scopeCombo.setSelectedIndex(...)` с висящим листенером), это запустило
  бы `applyScopeSelection()`, а та для CUSTOM открыла бы диалог выбора сцен
  ПОВЕРХ восстановления (ничего не выбрал пользователь — сам процесс
  открытия), и, что хуже, вызвала бы `recalculate()`/`persistRows()` ДО
  того, как строки вообще загружены — затерев только что прочитанные
  сохранённые количества пустой таблицей.
- `applyScopeSelection()` (интерактивная смена пользователем) теперь также
  вызывает `persistLastScope()` — запоминает новый выбор области расчёта.

**Тесты**: `vehicleCaseCountsProject_persistAndReloadWithProject`,
`vehicleCaseCountsCustom_persistsSceneIdsAndCountsTogether` (проверяет, что
третья, НЕ выбранная в набор сцена, не попадает в сохранённый список id),
`vehicleCaseLastScope_persistsAcrossReload` — все три через реальный файл
(пересоздание `AppModel` на диске), тем же приёмом, что и сценовый тест
выше.

## Явно отложено

- Настоящий 2D bin-packing вместо суммы площадей (в самом `VehicleCalc`) —
  визуализатор даёт РУЧНУЮ проверку раскладки (и, с 2026-08-20, кнопку
  «Разместить всё» — простой shelf-алгоритм, см. выше, НЕ настоящая
  оптимизация: не пытается минимизировать площадь/число машин, не учитывает
  уже существующие произвольные размещения при добавлении новых), но
  `VehicleCalc.checkFit` сам по себе по-прежнему считает только сумму
  площадей (и не знает о распределении по нескольким машинам — расчёт
  общего числа машин остаётся ручной работой в визуализаторе, `VehicleCalc`
  продолжает считать «одна минимально достаточная машина»).
