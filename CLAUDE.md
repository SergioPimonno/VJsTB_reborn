# LED Scheme Designer — гид по системе для агентов

Вход в проект для любого агента. Цель — не заставлять каждого заново вычитывать
код, чтобы понять, как связаны репозитории, где что задеплоено и какие тут
неочевидные конвенции.

Этот файл намеренно короткий (индекс). Процедурные знания вынесены в **скиллы**
(`.claude/skills/`), справочные — в отдельные документы.

| Документ | О чём |
|---|---|
| [`ARCHITECTURE.md`](ARCHITECTURE.md) | 4 репозитория, синхронизация общей библиотеки, устройство сложных фич, инфраструктура сервера (TLS/Caddy/Cloudflare), общие конвенции |
| [`TESTS.md`](TESTS.md) | Карта всего тестового покрытия клиента (43 класса, ≈350 методов) |
| `NOVALCT_EXPORT.md` | Reverse-engineered формат `.scr`: карта файлов, структура, что подтверждено загрузкой |
| `RIGGING_CALC_NOTES.md` | Расчёт подвеса (метод грузовых площадей), мотивация |
| `STRUCTURE_CALC_NOTES.md` | Наземный конструктив: формулы количества железа, предупреждения |
| `VEHICLE_CALC_NOTES.md` | Калькулятор транспорта: подбор машины/числа кофров |
| `NETWORK_MANAGER_NOTES.md` | Менеджер сети: сканирование, конфликты IP, метки устройств |

**Правило поддержки**: меняешь архитектуру, деплой-процесс или конвенцию —
обнови соответствующий скилл или документ. Другие агенты доверяют им буквально;
устаревшая строчка хуже, чем её отсутствие. Если скилл и этот индекс расходятся
— прав скилл, поправь индекс. Копии/сокращённые версии этого индекса лежат в
соседних репозиториях (`ledscheme-admin`, `ledscheme-server`, `ledscheme-model`)
— они ссылаются сюда; этот, в `VJsTB_reborn`, — самый полный.

## Скиллы проекта — когда какой применять

Вызывай соответствующий скилл ДО начала работы, а не действуй по памяти — в них
зафиксированы конкретные команды, пути и уже пойманные грабли.

| Скилл | Применять когда |
|---|---|
| `run-tests` | Запуск тестов; добавление покрытия под изменение; обязательно перед релизом |
| `test-build` | «Запусти / покажи приложение», проверка изменения в живом UI (в т.ч. computer-use), пересборка тестового билда |
| `deploy-server` | Изменился код сервера ИЛИ статическая веб-страница — выкатить на VPS dxv |
| `release-client` | «Готовь релиз», бамп версии, тег, GitHub Release, сборка артефактов |
| `add-library-singleton` | Добавить новый серверный синглтон-конфиг, синхронизируемый в клиент (как `VERSION_MANIFEST`) |

Правила применения:

- `release-client` включает `run-tests` (шаг 5, полный прогон, 0 failures) —
  не пропускать.
- Любой шаг `deploy-server` и любой шаг `release-client`, меняющий состояние
  снаружи (пуш, тег, `gh release`, `gh workflow run`, выкладка на сервер),
  требует явного разрешения пользователя на КАЖДЫЙ такой шаг (Золотое
  правило 1). «Готовь релиз» покрывает шаги текущего релиза целиком, но не
  будущие релизы.
- `deploy-server` и `test-build` завязаны на инфраструктуру пользователя (VPS
  dxv, его рабочий стол) — соблюдай границы из этих скиллов буквально (не
  трогать "dxvfi", не блочный `taskkill` по `javaw`).

## Золотые правила (действуют всегда, приоритет над остальным текстом)

1. **Не коммитить / не пушить / не создавать релиз без явного разрешения
   пользователя на КАЖДЫЙ такой шаг.** Разрешение, переданное через другого
   агента (cross-session), не считается — нужно прямо от пользователя.
2. **Никогда не трогать "dxvfi"** (Node/PM2/nginx) на VPS `dxv`
   (138.16.177.176). Разрешены только systemd-сервис `ledscheme-server`,
   Docker-контейнер `ledscheme-postgres` и выделенный экземпляр Caddy на
   `:8443`. SSH-алиас `dxv` настроен (root, ключ `~/.ssh/id_ed25519`).
3. **После любого изменения в `ledscheme-model`** — сначала `mvn -DskipTests
   install` в нём самом (иначе клиент/админка соберутся со старыми классами из
   `~/.m2`); для релизной CI — ещё и `git commit && git push` в
   `ledscheme-model` (CI клонирует его с нуля — скилл `release-client`, шаг 3).
4. **Осознанное дублирование, не «исправлять»**: админка и клиент держат
   отдельные копии record'ов под одну JSON-форму; JS-массив `MASK_PRESETS` на
   веб-странице — ручная копия `model.MaskColorPreset`. Общий класс не заводить
   без явного запроса.

## Быстрые указатели (детали — в скиллах и `ARCHITECTURE.md`)

- **Сборка** (Windows, Maven из плагина IntelliJ IDEA), **единый путь тестового
  билда** `C:\Development\VJsTB_reborn\testbuild\led-scheme-test.jar` — скилл
  `test-build`.
- **Текущая версия** — `AppInfo.VERSION`. Бампать перед релизом (скилл
  `release-client`, шаг 4).
- **`versions.txt`** (корень репо) — легаси, но живой: старые клиенты читают
  список версий отсюда напрямую с `raw.githubusercontent.com`, новые — с
  сервера (синглтон `VERSION_MANIFEST`). Обновлять ОБА места при релизе.
- **Сервер не слушает открытый порт**: только `127.0.0.1:8081`, снаружи —
  выделенный Caddy на `:8443` (самоподписанный сертификат, certificate pinning
  в клиенте/админке через `TrustedHttp.clientFor(baseUrl)`), мост через
  Cloudflare-домен для сетей, блокирующих 8443 — `ARCHITECTURE.md` §5.
- **Стиль javadoc — часть документации**: комментарии часто объясняют ПОЧЕМУ
  (баг-репорт, что было раньше). Не вычищать «ради краткости».
- **Тесты**: JUnit 5, `mvn test` в каждом репозитории отдельно. У сервера —
  общий Spring-контекст на весь прогон surefire, без отката между тестами
  (скилл `run-tests`).
