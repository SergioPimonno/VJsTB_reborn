# Сетевой менеджер (`ui.NetworkManagerPanel`) — статус и решения

Реализовано 2026-08-21 (v2.3), запрос пользователя: "многие устройства
видеосистемы, указываемые в блок схемах объединяются в компьютерные сети для
удобства управления... в сетевом менеджере можно добавить существующие в
схеме сигнала блоки или добавить новые... для каждого блока при ПКМ...
пинговать его... если есть вебинтерфейс — перейти в этот интерфейс... в
рамках одной сцены можно создавать несколько сетей". Референс по стилю
размещения — Cisco Packet Tracer.

## Что реализовано

- Третья вкладка раздела «Сигнал» (`SignalStagePanel` — тот же `JToggleButton`
  + `CardLayout` паттерн, что уже был у «Расключение экрана»/«Общая схема
  сигнала», расширен третьей кнопкой «Сетевой менеджер», не переделан в
  `JTabbedPane`).
- Новая общая библиотека `NetworkDeviceType` (`ledscheme-model`, вид сервера
  `LibraryItemKind.NETWORK_DEVICE`) — каталог типов сетевого оборудования
  (свитч/роутер/точка доступа/файрвол/сервер/прочее, категория —
  `NetworkDeviceCategory`, только для цвета блока на канвасе). Рецепт «добавить
  простой вид библиотеки» (см. `CLAUDE.md` §3) применён по образцу
  `CaseType`/`VehicleType`: без дискриминатора `Kind`, безусловное удаление
  (на id нет персистентного FK нигде в общей библиотеке — только клиентский
  `NetworkDevicePlacement.deviceTypeId`, данные ПРОЕКТА, не библиотеки).
- Модели проекта — ЛОКАЛЬНЫ в `VJsTB_reborn` (`model` пакет), как
  `VehicleLoadPlan`/`Section`/`Placement`: `Scene.networkManagerPlan`
  (nullable) → `NetworkManagerPlan.networks` (`List<Network>`) → `Network`
  (`id`, `name`, `devices`, `links`) → `NetworkDevicePlacement` (`id`,
  `linkedSchemaNodeId` ИЛИ `deviceTypeId`, `customLabel`, `ipAddress`,
  `subnetMask`, `gateway`, `webInterfaceUrl`, `portCount`, `xMm`/`yMm`, `note`)
  и `NetworkLink` (`id`, `fromDeviceId`+`fromPort`, `toDeviceId`+`toPort`,
  `label`) — см. Round 2 ниже.
- `AppModel.saveNetworkManagerPlan(scene, plan)` — тот же приём, что
  `saveVehicleLoadPlan` (`changed()`, без интеграции с undo-стеком — раскладка
  мутирует слишком часто для содержательных записей в отменяемой истории).

## Неочевидные решения (и почему)

**Ссылка на существующий узел схемы — ПО ID, резолвится ЖИВЬЁМ.**
`NetworkDevicePlacement.linkedSchemaNodeId` не копирует имя/тип узла —
`NetworkCanvasPanel.resolveLabel`/`resolveColor` резолвят их заново при каждой
отрисовке через `model.getCurrentScene().getSchemaNodes()`. Переименование
узла в общей схеме сигнала сразу видно в Сетевом менеджере, без ручной
пересинхронизации. Тот же приём, что `Screen#riggingHoistTypeId`/
`screenRefId`/`controllerInstanceRefId`. Если узел с тех пор удалён из схемы —
ссылка молча резолвится в `null` и подпись падает на "(устройство)" (тот же
приём, что `VehicleLoadVisualizerDialog.loadOrInitSections` для устаревших id)
— НЕ падает и НЕ удаляет само размещение (пользователь мог временно скрыть/
переместить узел, терять IP/примечание из-за этого нежелательно).

**Связь со схемой ОДНОНАПРАВЛЕННАЯ.** Добавление нового (не связанного)
устройства в Сетевом менеджере не создаёт ничего в общей схеме сигнала —
менеджер только ЧИТАЕТ `SchemaNode`, никогда не пишет в него и не удаляет
узлы схемы при удалении из сети. Одно физическое устройство может быть
привязано СРАЗУ к нескольким сетям одновременно (например, сервер с двумя
сетевыми интерфейсами) — палитра узлов схемы (`NetworkManagerPanel
.refreshSchemaPalette`) исключает узел только из списка для ТЕКУЩЕЙ выбранной
сети, не глобально.

**Разметка нескольких сетей — список слева + ОДИН активный канвас справа**,
не «стопка канвасов», как у `VehicleLoadVisualizerDialog` (там это подходило
для «распределить кофры между несколькими машинами сразу», здесь у каждой
сети своя топология, которая может быть большой — один активный воркспейс за
раз ближе к референсу Packet Tracer). Осознанный, но дискреционный выбор —
если пользователю в реальном использовании понадобится обзор нескольких сетей
разом, можно будет пересмотреть.

**Пинг — сырой вывод РЕАЛЬНОЙ команды ОС**, не `InetAddress.isReachable()`.
Тот без прав администратора часто откатывается на ненадёжный TCP-echo зонд и
просто врёт. См. Round 2 ниже за тем, как это переросло из разового вызова
в непрерывный живой поток — это описание относится к ПЕРВОЙ версии (уже
устарело в частностях, но сама причина выбора команды ОС вместо
`isReachable()` осталась в силе).

**Добавление устройств — кнопками (drag-n-drop добавлен в Round 2, см.
ниже)** — устройство появляется в углу канваса, дальше перетаскивается мышью
на нужное место (та же механика, что уже была у `VehicleLoadCanvasPanel
#addPlacement`).

**Веб-интерфейс — просто открытие сохранённого URL**, без отдельного
протокола/порта в модели. `NetworkDeviceParamsDialog` подставляет
`http://<ip>` в поле URL ОДИН РАЗ, когда IP заполнен, а поле URL ещё пусто (по
потере фокуса полем IP) — не форсирует на каждое сохранение, пользователь
может стереть/переписать под https или нестандартный порт. `UiKit.openUrl` —
вынесенный из `MainMenuBar.openUrl` общий метод (тот же `Desktop.browse` +
try/catch + `JOptionPane` при ошибке), переиспользуется в обоих местах.

## Явно отложено

- Валидация пересечения подсетей/конфликтов IP между сетями или устройствами
  — поля IP/маска/шлюз — свободный текст, без парсинга/проверки корректности.
- Импорт устройства из общей схемы С АВТОПОДСТАНОВКОЙ IP (например, по MAC/
  DHCP-réservation, если такая информация когда-нибудь появится в модели
  оборудования) — сейчас IP всегда вводится вручную.
- Проверка, что номер порта связи ({@code NetworkLink.fromPort/toPort}) не
  превышает актуальный {@code portCount} устройства (пользователь может
  уменьшить число портов уже ПОСЛЕ того, как создал связь на больший номер) —
  связь просто рисуется за пределами видимых портов, без предупреждения (см.
  javadoc `NetworkLink`).
- Документация фичи для пользователя (раздел в «Руководстве» или шаг в
  «Интерактивных сценариях», см. чеклист `CLAUDE.md` §4 п.2) — не сделана в
  этом заходе, нужно добавить перед релизом v2.3 (в этой сессии нет доступа
  к GUI ledscheme-admin для правки текстов на сервере).

## Round 2 — живой пинг, кодировка, порты/связи, drag-n-drop, экраны исключены — 2026-08-21 (тот же день)

Баг-репорт по первой версии (скриншоты пользователя): (1) пинг нужно
отслеживать в реальном времени, а не ждать фиксированные 4 пакета и видеть
результат одним куском; (2) вывод пинга был "белиберда" — нечитаемая каша
вместо текста; (3) нужно рисовать линки и подключать по портам — для
подробных схем и сложной маршрутизации; (4) у экранов нет IP, их не нужно
предлагать в палитре; (5) сразу добавить drag-n-drop (был осознанно отложен
в Round 1).

**Пинг переписан на непрерывный поток** — `NetworkPingService.startPing`
запускает БЕСКОНЕЧНЫЙ `ping` (Windows `-t`, POSIX без счётчика — по
умолчанию до остановки) и передаёт КАЖДУЮ строку вызывающей стороне по мере
поступления (`Consumer<String> onLine`, вызывается на EDT), вместо старого
одноразового `pingAsync` с 4 пакетами и единственным финальным результатом.
Новый `NetworkPingDialog` — немодальный, с живым `JTextArea` (автоскролл к
последней строке) и кнопкой «Остановить»; закрытие окна ЛЮБЫМ способом
(крестик и т.д., не только кнопкой) останавливает процесс через
`WindowListener#windowClosing` — иначе `ping.exe`/`ping` висел бы в фоне
после закрытия диалога.

**Кодировка (баг "белиберда")** — причина: `ping.exe` на Windows пишет в
OEM-кодировку консоли (обычно CP866 для русской локали) даже при
перенаправлении вывода в канал; старый код декодировал как UTF-8 напрямую,
получалась каша. Жёстко декодировать как CP866 работало бы только для
русской локали — вместо этого команда оборачивается в `cmd /c "chcp
65001>nul && ping -t <host>"`: переключает кодовую страницу КОНКРЕТНОЙ
консольной сессии на UTF-8 ПЕРЕД запуском ping в той же сессии, после чего
UTF-8-декодирование уже надёжно работает независимо от локали ОС.
**Безопасность**: `host` подставляется в строку команды (нужно для
`&&`-цепочки в одной консольной сессии) — чтобы это не стало command
injection через `&`/`|`/`"` и т.п., `host` проверяется по строгому allow-list
`HOST_PATTERN` (`[A-Za-z0-9.:_-]{1,253}`) ДО того, как попасть в команду;
невалидный ввод отклоняется без запуска процесса вообще.

**Порты и связи** — новая модель `NetworkLink` (`fromDeviceId`+`fromPort`,
`toDeviceId`+`toPort`, `label`) в `Network.links`; `NetworkDevicePlacement`
получил `id` (стабильный якорь для ссылок — связи не могут ссылаться на
`linkedSchemaNodeId`/`deviceTypeId` напрямую, т.к. два размещения в одной
сети теоретически могут указывать на один и тот же тип/узел) и `portCount`
(число портов ИМЕННО этого размещения, не библиотечного типа — у связанных
устройств source of truth для этого числа нет вовсе, у каталожных реальная
комплектация в поле иногда отличается от паспортной; редактируется в
`NetworkDeviceParamsDialog`, по умолчанию 4). `NetworkCanvasPanel` рисует
порты мелкими квадратами вдоль нижнего края блока
(`portCenterCanvasUnits`), связи — прямыми линиями порт-в-порт (без точек
излома, в отличие от `SchemaEdge`). Взаимодействие — "клик-клик", не
перетаскивание: клик по порту начинает связь, клик по порту ДРУГОГО
устройства завершает, `Esc` или клик по пустому месту отменяет (`Escape` —
`KeyAdapter`) — перетаскивание уже занято перемещением блока целиком, второй
смысл у него был бы неоднозначным (та же причина, что у `SchemaCanvasPanel`
не пытается их совместить). ПКМ по линии связи (хит-тест — расстояние от
точки до отрезка, `distanceToSegment`) — меню «Удалить связь». Удаление
устройства из сети (`removeDevice`) заодно удаляет все его связи
(`links.removeIf`), а не оставляет их "висящими" на исчезнувшем id.

**Экраны исключены из палитры узлов схемы** — `NetworkManagerPanel
.refreshSchemaPalette` теперь фильтрует `SchemaNodeType.SCREEN` (у экранов
физически нет сетевого адреса — остальные категории, контроллеры/
медиасерверы/конвертеры/..., вполне могут быть сетевыми устройствами, их
фильтр не касается).

**Drag-n-drop добавлен** — `NetworkCanvasPanel` экспонирует `pxToCanvas`,
`addLinkedDeviceAt(node,x,y)`, `addCatalogDeviceAt(type,x,y)` и два публичных
`DataFlavor` (`SCHEMA_NODE_FLAVOR`/`DEVICE_TYPE_FLAVOR`) — сама панель НЕ
ставит свой `TransferHandler` (тот же контракт, что `VehicleLoadCanvasPanel`
— вызывающая сторона настраивает приём drop). `NetworkManagerPanel` ставит
`TransferHandler` на канвас (приём обоих флейворов, определяет позицию через
`pxToCanvas`, центрирует блок под курсором) и drag-source `TransferHandler`
на оба списка палитры (`SchemaNodeTransferable`/`DeviceTypeTransferable`,
тот же приём, что `VehicleLoadVisualizerDialog.CaseTypeTransferable`).
Кнопки «Добавить в сеть» остались — drag-n-drop добавлен КАК АЛЬТЕРНАТИВА, не
взамен.

## Round 3 — порты из типа, видимость построения связи, излом линии, цвет по сети — 2026-08-21 (тот же день)

Баг-репорт: (1) "количество портов ethernet для устройств должно
определяться в параметрах" — раньше редактировалось на каждом РАЗМЕЩЕНИИ
отдельно, даже для каталожных устройств, что бессмысленно (реальный свитч
одной модели физически всегда имеет одно и то же число портов); (2) "при
построении связи выбранные порты никак не выделяются, непонятно строится ли
связь или нет"; (3) "нужно также как в блоксхемах добавить возможность
ломать линию"; (4) "цвет линии должен зависеть от цвета выбранного для
сети".

**Число портов — паспортная величина ТИПА для каталожных устройств.**
`NetworkDeviceType.portCount` (новое поле, `ledscheme-model`, редактируется
в `NetworkDeviceTypeDialog`/`ledscheme-admin`'s
`NetworkDeviceTypeFormPanel`) — для устройства, добавленного ИЗ каталога
(`deviceTypeId != null`), число портов теперь резолвится ЖИВЬЁМ из типа
(`NetworkCanvasPanel.effectivePortCount`), а не хранится по месту.
`NetworkDevicePlacement.portCount` (поле осталось, не удалено — Jackson
back-compat для уже сохранённых проектов, плюс оно и раньше не было
"мусорным": инициализируется из типа при добавлении на случай удаления типа
из библиотеки) используется только как источник числа портов для СВЯЗАННЫХ
устройств (`linkedSchemaNodeId != null`) — у тех нет каталожного типа
вообще, взять число портов больше неоткуда, поэтому для них поле в
`NetworkDeviceParamsDialog` остаётся редактируемым. Для каталожных —
спиннер в том же диалоге показывает значение типа и ЗАБЛОКИРОВАН
(`portCountSpinner.setEnabled(false)`, тултип отсылает в библиотеку). Порт-
рендеринг/хит-тест (`portCenterCanvasUnits`/`portAt`/цикл отрисовки) везде
переведён на `effectivePortCount` вместо прямого `p.getPortCount()`.

**Видимость построения связи — исправлен баг с прозрачностью + добавлены
визуальные акценты.** Причина невидимости: `COLOR_LINK_PENDING = new
Color(0xf0b429, true)` — двухаргументный конструктор `Color(int rgb,
boolean hasAlpha)` трактует `0xf0b429` как ARGB-число, где старший байт
(альфа) РАВЕН НУЛЮ (0xf0b429 как 32-битное — это `0x00F0B429`), то есть
линия/акценты рисовались ПОЛНОСТЬЮ прозрачными. Исправлено на обычный
непрозрачный `new Color(0xffd23f)`. Плюс добавлено: (а) курсор меняется на
crosshair, пока связь строится (`Cursor.CROSSHAIR_CURSOR`, сбрасывается по
завершении/отмене); (б) исходный порт — крупнее (`PORT_HIGHLIGHT_SIZE_PX`
вместо `PORT_SIZE_PX`) и ярче, плюс пунктирная обводка ВСЕГО блока-
источника (мелкий квадрат порта легко не заметить, обводка всего блока —
нет); (в) порт под курсором на ДРУГОМ устройстве (валидная цель) тоже
подсвечивается крупнее, отдельным зелёным цветом
(`COLOR_PORT_TARGET_HOVER`) — виден слушателем `mouseMoved`, который
трекает `hoveredPort`, пока `linkingFrom != null`; (г) сама тянущаяся линия
— толстый яркий пунктир до курсора, поверх всего остального.

**Излом линии — точная копия UX `SchemaEdge`/`SchemaCanvasPanel`.** Новая
модель `NetworkLinkWaypoint` (`x`, `y`, package `model`) —
структурно идентична `EdgeWaypoint`, но своя копия (та же дублирующая
конвенция, что везде в проекте, см. `CLAUDE.md` §3/§6).
`NetworkLink.waypoints` — список, пустой по умолчанию = прямая линия порт-
в-порт, как раньше. `NetworkCanvasPanel`: двойной клик по линии
(`mouseClicked`, `e.getClickCount() == 2`) вставляет новую точку на месте
клика — позиция вставки в списке определяется тем, к какому отрезку
текущей ломаной клик ближе всего (`insertWaypoint`, тот же алгоритм
"ближайший сегмент", что `SchemaCanvasPanel.insertWaypoint`). Точки излома
ВИДНЫ И ПЕРЕТАСКИВАЕМЫ только у ВЫДЕЛЕННОЙ связи (`selectedLink`, обычный
левый клик по линии выделяет) — иначе канвас с несколькими связями сразу
захламляется ручками отовсюду. ПКМ по точке — «Убрать точку»; ПКМ по линии
получил новый пункт «Выпрямить» (полностью очищает `waypoints`) рядом с уже
существовавшим «Удалить связь». Хит-тест связи (`linkAt`, используется и
для выделения, и для ПКМ-меню, и как базовая точка для `insertWaypoint`)
переведён с одиночного отрезка порт-порт на перебор ВСЕХ отрезков полного
маршрута (`routePoints` — источник, все waypoints по порядку, приёмник).

**Цвет линии — по сети, не фиксированный.** `Network.color` (новое поле,
`Integer`, RGB, nullable — `null` = цвет по умолчанию) — при создании новой
сети (`NetworkManagerPanel.addNetwork`) сразу получает цвет по золотому
углу от порядкового индекса сети (`defaultColorForIndex`, тот же приём,
что нередко используется для различимых палетей без ручного выбора —
соседние по порядку сети получают заметно разные оттенки без
дополнительных действий пользователя). Новая кнопка «Цвет…» в списке сетей
открывает `JColorChooser.showDialog` (тот же вызов, что уже был у
`SchemaCanvasPanel` для цвета связи общей схемы) и применяет выбор к
`Network.color`. `NetworkCanvasPanel.setLinkColor(Color)` — новый метод,
вызывается из `NetworkManagerPanel.onNetworkSelected()` при каждом
переключении сети; связи текущей сети рисуются этим цветом (выделенная
связь — всегда белым, для контраста и однозначности выбора, независимо от
цвета сети). Список сетей слева получил цветной квадрат-образец перед
названием (`ColorSwatchIcon`, маленький `Icon`) — сети различимы по цвету
уже в самом списке, не только на канвасе.

## Round 4 — Shift-снаппинг точки излома — 2026-08-21 (тот же день)

Запрос пользователя: "для точек излома линий надо добавить снаппинг при
shift" (после Round 3, где излом линии только появился). Реализовано КАК
ТОЧНАЯ КОПИЯ уже существующего `SchemaCanvasPanel#snapWaypointPosition`
(тот снаппинг точек излома `SchemaEdge` при перетаскивании с зажатым
`Shift`) — не изобретался заново, единственная содержательная разница в
кандидатах для привязки: у общей схемы это края/центры узлов + другие точки
излома, здесь (у портов нет ширины/высоты) — центры ВСЕХ портов ВСЕХ
устройств этой сети + точки излома ЛЮБОЙ связи (кроме самой перетаскиваемой
точки). Порог поиска и сила притяжения берутся из ОДНОЙ и той же настройки
профиля, что и у общей схемы (`SettingsManager#activeProfile()
.getSnapThresholdPx()/getSnapStrengthPercent()`) — не заводилась отдельная
копия настройки для Сетевого менеджера.

`NetworkCanvasPanel` получил новый конструкторный параметр `SettingsManager
settings` (раньше принимал только `AppModel`) — единственный вызывающий код
`NetworkManagerPanel` уже держал `SettingsManager` (нужен был для
`ProposeDialog`), просто прокинут дальше. Направляющие линии
(`snapGuideX`/`snapGuideY`, пурпурный пунктир через весь холст) — те же
координаты, что использует сам снаппинг (координаты КАНВАСА, не px) —
переводятся в px вручную (`PADDING + guide * scale()`) при отрисовке, в
отличие от `SchemaCanvasPanel`, где это не нужно (там весь `Graphics2D`
глобально промасштабирован `g2.scale(...)`, а `NetworkCanvasPanel` считает
px для каждого элемента отдельно, см. `paintComponent`).

## Round 5 — снаппинг блоков, явный флаг веб-интерфейса — 2026-08-21 (тот же день)

Запрос пользователя: "для блоков в менеджере сетевом тоже должен работать
снаппинг к блокам и существующим узлам излома. добавь в параметры блоков
менеджера галочку есть ли веб интерфейс, если стоит галочка — можно
управлять через него".

**Снаппинг блока устройства** — новый `NetworkCanvasPanel#snapDevicePosition`,
точная копия `SchemaCanvasPanel#snapPosition` (три кандидата на измерение —
левый край/центр/правый край по X, верх/центр/низ по Y, у перетаскиваемого
блока сравниваются с такими же координатами ДРУГИХ блоков сети), плюс, по
явному запросу пользователя, ЕЩЁ один источник кандидатов — точки излома
ЛЮБОЙ связи (single-point, без ширины/высоты, как в `snapWaypointPosition` из
Round 4, только тут они цель, а не перетаскиваемая точка). Общая с Round 4
инфраструктура (`snapGuideX`/`snapGuideY`, магентовая направляющая,
настройки профиля) переиспользована без изменений — оба вида перетаскивания
(блок и точка излома) делят один и тот же механизм отрисовки направляющих.

**Явный флаг "есть веб-интерфейс"** — новое поле `NetworkDevicePlacement
.hasWebInterface` (boolean, по умолчанию `false`), отдельное от самого поля
`webInterfaceUrl`. Причина разделения: `NetworkDeviceParamsDialog`
автоматически подставляет `http://<ip>` в поле URL при заполнении IP —
удобно, но означает, что непустой URL сам по себе НЕ гарантирует, что у
устройства реально есть веб-интерфейс (простой конвертер/сплиттер с IP-
адресом для диагностики, но без веб-морды). Новый чекбокс в диалоге параметров
блокирует поле URL, пока не отмечен (текст при этом не стирается — просто
недоступен для правки, чтобы не создавать иллюзию использования), а ПКМ-пункт
«Открыть веб-интерфейс» на канвасе (`NetworkCanvasPanel#showDeviceMenu`)
теперь активен только при ОБОИХ условиях: флаг стоит И URL не пуст — раньше
хватало только непустого URL.

## Round 6 — таблица адресов, конфликты IP, скан диапазона — 2026-08-31

После обсуждения дальнейших доработок менеджера (контекст: используется для
подготовки к мероприятию, многие устройства без веб-интерфейса управляются
через собственные приложения — этот последний пункт пользователь СОЗНАТЕЛЬНО
отклонил как отдельную фичу для менеджера, см. ниже) пользователь выбрал три
доработки из предложенного списка: таблицу адресов ОКОШЕЧКОМ, а не экспортом;
обнаружение конфликтов IP; сканирование диапазона IP для поиска устройств с
неизвестными адресами. Явно ОТКЛОНЕНО в том же обсуждении: «открыть в
приложении» (запуск стороннего .exe для устройств без веб-интерфейса) и
«пинг всей сети разом» — оба валидны как идеи, но не нужны пользователю
сейчас, не реализовывать без нового явного запроса.

**Общий метод резолва имени устройства вынесен в `service.NetworkDeviceLabels`**
(из приватного `NetworkCanvasPanel.resolveLabel`/`findSchemaNode`) — второй
потребитель (таблица адресов) появился, дублировать логику приоритета "своя
пометка > узел схемы > каталожный тип > заглушка" в двух местах рискованно
(правка в одном легко разойдётся с другим). `NetworkCanvasPanel.resolveLabel`
теперь просто делегирует. Покрыто отдельным `NetworkDeviceLabelsTest`.

**Обнаружение конфликтов IP** — `service.NetworkIpConflicts.hasConflict(devices,
target)`: два РАЗНЫХ устройства ОДНОЙ сети с одинаковым непустым адресом.
Намеренно scoped ПО СЕТИ — у разных `Network` совпадающие адреса конфликтом
не считаются (разные логические/физические сегменты, повторное использование
адресного пространства между ними — обычное дело). Подсветка ДВОЯКАЯ: на
канвасе (`NetworkCanvasPanel`) — красная рамка блока + текст "⚠ конфликт IP"
рядом с адресом (просто красной рамки было бы недостаточно — тот же красный
уже занят категорией FIREWALL у каталожных устройств, текст снимает
двусмысленность); в таблице адресов — строка целиком красным текстом.
Проверяется заново при КАЖДОЙ отрисовке/перестройке таблицы (не кэшируется) —
дешёвая O(n²) проверка на реалистичных размерах одной сети (десятки
устройств), кэш не оправдан.

**«Таблица адресов»** (`ui.NetworkAddressTableDialog`) — по прямому уточнению
пользователя НЕ экспорт в файл (в отличие от, например, `SpecXlsxWriter` для
кабельной спецификации), а живое немодальное окно: сводная таблица ВСЕХ
устройств ВСЕХ сетей ТЕКУЩЕЙ СЦЕНЫ разом (Сеть/Устройство/IP/Маска/Шлюз/
Примечание), подписывается на `model.addListener` и перестраивается на КАЖДОЕ
изменение модели — держат открытой рядом как шпаргалку во время монтажа/
настройки, а не смотрят разово. Следует за текущей сценой без ручного
обновления. `NetworkManagerPanel` держит ЕДИНЫЙ экземпляр (кнопка «Таблица
адресов…» в новом верхнем тулбаре панели, `showAndRefresh()` на повторных
открытиях) — у `AppModel` НЕТ метода `removeListener` вообще, повторное
создание диалога на каждый клик плодило бы висящие подписки без ограничения
(тот же приём предосторожности, что неявно уже действует у `PreferencesDialog`/
`HotkeysDialog`, просто здесь применён осознанно, а не случайно — у тех
дилогов переоткрытие тоже технически возможно, но происходит настолько редко,
что риск накопления никогда не всплывал).

**Сканирование диапазона IP** (`service.NetworkScanService` + `ui
.NetworkScanDialog`, кнопка «Найти устройства (скан IP)…» в том же тулбаре) —
по ОДНОМУ короткому пингу (не непрерывному, как `NetworkPingService`) на
каждый адрес диапазона, решение "жив/не жив" — по КОДУ ВОЗВРАТА процесса
ping (0 = ответ получен и на Windows `ping -n 1`, и на POSIX `ping -c 1`), вывод
вообще не читается (`Redirect.DISCARD`) — значит не нужна ни возня с
кодировкой консоли (см. `chcp 65001` у `NetworkPingService`), ни shell-
обёртка вообще: адрес идёт ОТДЕЛЬНЫМ аргументом `ProcessBuilder`, а не
строкой команды — command injection в принципе невозможен, адреса и так уже
провалидированы как целые 0-255 до того, как попасть в команду. Диапазон
сканируется ПАРАЛЛЕЛЬНО ограниченным пулом потоков (32) — последовательно
/24 (254 хоста) занял бы минуты. `expandRange(from, to)` — упрощение под
самый частый случай локальной сети мероприятия: оба конца должны совпадать в
первых трёх октетах (одна /24), меняется только последний.

Отвечающий адрес — кнопка «Добавить как устройство» → новый
`NetworkCanvasPanel.addDiscoveredDevice(ip)` (bare-размещение без каталожного
типа и без связи со схемой, `customLabel` пустой — резолвится заглушкой
"(устройство)", пользователь дозаполняет параметры через ПКМ) в СЕЙЧАС
выбранную в списке слева сеть; без выбранной сети — предупреждение, добавлять
некуда (`canvas.devices` тогда указывает на одноразовый пустой список, не на
реальную `Network`).

**Баг-репорт, пойман и исправлен ДО релиза (не пользователем)**: наивная
реализация `ScanHandle#cancel()` (`pool.shutdownNow()`) выбрасывает из
очереди ещё НЕ НАЧАТЫЕ задачи БЕЗ выполнения — если бы `onDone` полагался
только на то, что каждая из 254 задач сама доведёт `remaining` до нуля,
отмена скана ДО его естественного завершения могла бы вообще никогда не
вызвать `onDone` (кнопки диалога остались бы разблокированными навечно).
Исправлено — `cancel()` форсирует `onDone` явно и один раз (`AtomicBoolean`-
защёлка от гонки с естественным путём завершения).

**Баг-репорт по скриншоту, тот же класс бага, что уже чинили в
`VehicleLoadVisualizerDialog`**: "Сканировать"/"Остановить" сидели в ОДНОЙ
`FlowLayout`-строке с полями "От"/"до" — при фиксированном `preferredSize`
диалога лишние компоненты пропадали за краем окна вместо переноса на вторую
строку. Исправлено тем же приёмом — разбито на две строки (`BoxLayout`,
явный `Box.createVerticalStrut`).

**Диапазон — по IP + выбранной маске, не жёстко /24 (ЗАБРАКОВАНО тем же
заходом, см. следующий абзац)** — доработка по прямому запросу пользователя
сразу следом: "добавь возможность сканировать не 1 подсеть, а в зависимости
от выбранной маски". Поля "От"/"до" были заменены на одно поле IP + `maskCombo`,
`NetworkScanService.expandRange(from, to)` (жёстко /24) — на
`expandSubnet(ip, maskDotted)` (битовая арифметика, `ip & mask` = сетевой
адрес, хостовый диапазон без сетевого/широковещательного, кроме /31-RFC
3021/32). **Пользователь опробовал и вернул интерфейс обратно**: "нет,
диапазон IP выглядел лучше. убирай окошко маски, делай диапазон IP но убери
ограничение на маску /24" — то есть проблема была НЕ в идее (потолок на
размер диапазона остался нужен), а именно в UI "IP + маска" — простая пара
"От"/"до" воспринимается понятнее. Откат: `expandSubnet`/`maskPrefixLength`
удалены целиком (не оставлены мёртвым кодом), `maskCombo`/`COMMON_MASKS`
убраны из `NetworkScanDialog`, `fromField`/`toField` вернулись. **Единственное,
что осталось от этого захода** — само требование "убери ограничение на маску
/24" реализовано в возвращённом `expandRange`: теперь сравнивает `from`/`to`
как простые 32-битные числа БЕЗ проверки совпадения октетов (диапазон может
пересекать границу /24, например `192.168.1.250`..`192.168.2.10`) — раньше
`expandRange` требовал совпадения первых трёх октетов. Потолок
`MAX_SCAN_ADDRESSES=1024` остался без изменений (без него случайно широкий
диапазон занял бы часы даже с параллельным пулом и выглядел бы как зависшее
приложение) — просто теперь считается как `to - from + 1` по 32-битным
числам, а не как разница последнего октета.

## Round 7 — все сети сцены на ОДНОМ канвасе, сетевое оборудование в «Библиотеках» — 2026-09-12

Два независимых баг-репорта в одном заходе: (1) "разные сети представляются
отдельно, а должны быть в одном экране, но визуально отличаться, типа как
отдельные цветные подложки" — правит дискреционное решение Round 1 ("список
слева + ОДИН активный канвас справа", см. выше, там же прямо предполагалось,
что это может понадобиться пересмотреть); (2) "сетевое оборудование не видно
в библиотеках и недоступно для редактирования" — `NetworkDeviceType` был
полноценным участником системы общих библиотек (сервер/синк/`AppModel` CRUD —
`addNetworkDeviceType`/`updateNetworkDeviceType`/`deleteNetworkDeviceType`/
`isSharedNetworkDeviceType`, всё уже было реализовано и покрыто тестами), но
единственная точка входа в клиенте — палитра каталога устройств в самом
`NetworkManagerPanel` (кнопка «+ Новый тип…», ТОЛЬКО создание, без
Изменить/Удалить/Предложить) — вне этапа «Сигнал» → «Сетевой менеджер» типы
были не видны и не редактируемы вовсе.

**Одно устройство — `NetworkCanvasPanel` — на ВСЕ сети сцены разом.**
`setDevices`/`setLinks`/`setLinkColor` (переключали канвас на одну сеть при
клике в списке слева) заменены на `setNetworks(List<Network>, Network
current)` — канвас держит живую ссылку на `NetworkManagerPlan#getNetworks()`
целиком (все мутации — добавление/удаление сети, устройства, связи — сразу
видны, та же ссылка, не копия) плюс "текущую" (выбранную слева) сеть —
единственная её роль теперь: (а) куда попадёт новое устройство при
добавлении кнопкой/drag-n-drop, (б) чья подложка рисуется заметно ярче
остальных. Выбор сети в списке слева больше НЕ переключает то, что нарисовано
на канвасе — там уже видно всё сразу.

**Цветные подложки** (`NetworkCanvasPanel.drawNetworkBackground`/
`networkBoundsCanvasUnits`) — полупрозрачный скруглённый прямоугольник вокруг
фактических координат устройств (плюс точек излома её связей) каждой сети,
цвет — тот же `Network.getColor()`/золотой угол по индексу, что уже
использовался для линий связи и значка в списке слева (то же самое
resolve-правило теперь в одном месте — `NetworkCanvasPanel
.resolveNetworkColor`/`.defaultColorForIndex`, `NetworkManagerPanel
.networkColor` делегирует туда же, вместо собственной копии формулы).
Границы живьём пересчитываются на каждой отрисовке из текущих `xMm`/`yMm`
устройств — не кэшируются и нигде не персистятся (тот же принцип, что у
`resolveLabel`/`resolveColor`/`effectivePortCount`). "Текущая" сеть — сплошная
обводка поярче; остальные — пунктирная, приглушённая.

**Связи между устройствами РАЗНЫХ сетей запрещены.** `NetworkLink` физически
хранится внутри `Network.getLinks()` одной конкретной сети — раньше это было
неявной гарантией (на канвасе одновременно были устройства только одной
сети), с объединением на одном канвасе стало реальным риском. `createLink`
теперь проверяет, что оба порта принадлежат ОДНОЙ сети (`networkOfDevice`),
иначе — предупреждение и отмена построения связи.

**Shift-снаппинг (блока и точки излома) — теперь по устройствам/точкам ЛЮБОЙ
сети**, не только активной (`snapDevicePosition`/`snapWaypointPosition`
переведены с `this.devices`/`this.links` на `allDevices()`/`allLinks()`,
собирающие устройства/связи всех сетей плана) — на одном общем канвасе
выравнивание между сетями так же полезно, как внутри одной; это осознанное
расширение прежнего поведения, не просто техническая необходимость слияния.

**Коллизии позиций новых устройств** — `nextSpotX()` (место для устройства,
добавленного кнопкой, без явного drag-n-drop) раньше считался по числу
устройств ТЕКУЩЕЙ сети; на одном общем канвасе это раскладывало бы первые
устройства РАЗНЫХ сетей друг на друга (обе стартуют с x=0). Исправлено —
считается по `allDevices().size()` (по всем сетям разом), новые блоки всегда
попадают на свободное место независимо от того, к какой сети относятся.
**Уже существующие проекты**, где сети создавались и просматривались по
отдельности (до этого захода) и потому МОГЛИ получить перекрывающиеся
координаты, автоматически не расставляются — если после обновления две сети
визуально накладываются, требуется вручную перетащить блоки (авто-раскладка/
разрешение коллизий сознательно не реализовывались — не было запрошено, и
экраны с более чем считанными устройствами делают это неоднозначной
эвристикой, которую лучше отдать пользователю).

**Владение устройством/связью теперь ищется, а не хранится.** Ни
`NetworkDevicePlacement`, ни `NetworkLink` не получили обратной ссылки на
`Network` — вместо этого `NetworkCanvasPanel.networkOfDevice`/`networkOfLink`
сканируют `networks` (обычно единицы сетей по несколько-десятков устройств —
дёшево), нужны только для операций удаления/создания связи, не для
рендеринга (там уже понятно, чья сеть, т.к. рисуется по группам).

**`NetworkDeviceType` — новая секция в `LibrariesStagePanel`** («Библиотека
сетевого оборудования», в самом конце списка секций этапа «Библиотеки») —
точная копия паттерна `CabinetType`/`ControllerType` (список +
Добавить/Изменить/Удалить/Предложить…, `isSharedNetworkDeviceType` отключает
Изменить/Удалить/Предложить и показывает тултип "Общие элементы
редактируются только через админ-консоль" для элементов общей библиотеки).
Весь backend (CRUD в `AppModel`, диалог `NetworkDeviceTypeDialog` — уже
поддерживал редактирование) уже существовал и был протестирован — не хватало
только ~70 строк UI-подключения. Палитра в `NetworkManagerPanel` (кнопка "+
Новый тип…") осталась как есть — быстрое создание на лету при сборке сети,
без похода на другой этап, теперь это ВТОРАЯ точка входа, не единственная.

## Round 8 — членство в нескольких сетях, растягивание блоков, стороны портов — 2026-09-12

Баг-репорт после Round 7 (один канвас на все сети): "я добавил мктрлки в сеть
админ, но в контенте в списке доступных они таже видны. такого не должно
быть, один блок может добавляться в поле 1 раз, но может принадлежать разным
сеткам при условии, что у него больше 1 порта и соответственно адреса".
Следом, в одном заходе: "занятые порты должны попарно краситься в цвета...
блоки должны мочь растягиваться (как в общей схеме), для сетевого
оборудования давай рисовать порты сверху, а оптические порты — сбоку" +
явное уточнение "в контроллерах ethernet порты для экранов и сетевой порт —
это разные порты" (см. ниже, почему это отменило первоначальный план).

**Устройство/связь переехали на уровень плана — сеть теперь ЧЛЕНСТВО, не
ВЛАДЕНИЕ.** До этого захода `Network` физически хранила свои `devices`/
`links` (см. Round 1-7) — одно физическое устройство, входящее в две сети,
пришлось бы заводить на поле ДВАЖДЫ отдельными блоками с разными id (нельзя
было ни соединить их как один узел, ни увидеть, что это один и тот же ящик —
ровно баг-репорт). Теперь `NetworkManagerPlan.devices`/`links` — общие
плоские списки ВСЕГО плана, `Network` — только `id`/`name`/`color`, а
принадлежность сетям — новая модель `NetworkAttachment` (IP/маска/шлюз/список
портов ЭТОЙ сети) в списке `NetworkDevicePlacement.getAttachments()`. У
обычного устройства одно подключение; устройство с несколькими сетевыми
интерфейсами — несколько, с разными адресами. Владение и хит-тесты внутри
`ui.NetworkCanvasPanel` перестали быть "который список я держу" и стали
"резолвь живьём" — новый `service.NetworkTopology` (устройство/сеть по id,
устройства/связи конкретной сети, сеть конкретного порта/связи) — тот же
принцип "не кэшировать", что `resolveLabel`/`resolveColor` с Round 1.

**Палитра исключает узел ГДЕ УГОДНО на поле, не в текущей сети** —
`NetworkManagerPanel.refreshSchemaPalette` раньше проверял только устройства
ВЫБРАННОЙ сети (`current.getDevices()`), из-за чего узел схемы можно было
перетащить из палитры повторно в другую сеть и получить ВТОРОЙ физический
блок для того же устройства. Теперь проверяется `currentPlan.getDevices()`
целиком — узел пропадает из палитры после ПЕРВОГО добавления НЕЗАВИСИМО от
сети. Чтобы включить уже стоящий блок ЕЩЁ в одну сеть — ПКМ по блоку →
«Подключить к сети…» (см. ниже), а не повторное перетаскивание.

**ПКМ-меню устройства разрослось под множественное членство**
(`NetworkCanvasPanel.showDeviceMenu`) — вместо одного «Убрать из сети» теперь
три подменю по списку сетей блока: «Подключить к сети» (сети БЕЗ подключения;
задизейблено целиком, если у устройства не осталось свободных портов —
см. `hasFreePorts`, не строгая валидация, тултип отсылает ограничить порты
существующего подключения), «Параметры подключения» (сети С подключением —
открывает новый `ui.NetworkAttachmentDialog` на IP/маску/шлюз/список портов
ИМЕННО этой сети) и «Отключить от сети» (снимает ОДНО подключение —
устройство остаётся на поле, если подключений было больше одного; если
последнее — удаляется целиком, `deleteDeviceEntirely`, тот же эффект, что
раньше было единственным поведением). «Пинг…» стал подменю, если подключений
больше одного (по одному пункту на сеть/адрес). Отдельный явный пункт
«Удалить устройство» — из ВСЕХ сетей разом, всегда доступен.

**Связь порт-в-порт по-прежнему только внутри одной сети** — но теперь
резолвится ПО ПОРТУ (`NetworkTopology.networkOfPort`, через покрывающее его
`NetworkAttachment`), не по устройству целиком: у многосетевого устройства
разные порты физически могут принадлежать разным сетям (`NetworkAttachment
.getPorts()` — пустой список значит "все порты", явный список нужен только
когда порты приходится делить между несколькими подключениями одного
устройства). `NetworkCanvasPanel.createLink` отклоняет попытку соединить
порты, резолвящиеся в разные сети, тем же предупреждением, что в Round 7.

**Порты — раздельные ethernet/оптика, сквозная нумерация, разные стороны
блока.** Явное уточнение пользователя "в контроллерах ethernet порты для
экранов и сетевой порт — это разные порты" отменило первоначальный план
резолвить число сетевых портов связанных (со схемой) устройств через
`ControllerType.effectiveEthernetPortCount()` — та величина считает порты
ВЫВОДА ВИДЕО на экран (карты/`CardPort`, отдельное физическое оборудование),
не порты УПРАВЛЕНИЯ контроллера. Вместо этого — два счётчика, полностью
независимых от `CardPort`/`ControllerType`/`InterfaceType`:
`NetworkDeviceType.ethernetPortCount`/`opticalPortCount` (паспортная
величина каталожного типа, правка в `ledscheme-model` — потребовала `mvn
install` там и синхронной правки формы `ledscheme-admin
.NetworkDeviceTypeFormPanel`, см. золотое правило 3 `CLAUDE.md`) и
`NetworkDevicePlacement.ethernetPortCount`/`opticalPortCount` (per-instance,
для СВЯЗАННЫХ устройств — у тех источника в принципе нет). Порты нумеруются
СКВОЗНЫМ номером 1..N (сначала ethernet, потом оптика) — единственное число,
чтобы не менять модель `NetworkLink#fromPort/toPort` (простой int) под пару
(вид, индекс). Отрисовка (`NetworkCanvasPanel.portCenterCanvasUnits`) — по
запросу пользователя "для сетевого оборудования давай рисовать порты
сверху, а оптические порты — сбоку": ethernet вдоль ВЕРХНЕГО края блока,
оптика — вдоль ПРАВОГО, для ВСЕХ устройств одинаково (каталожных и
связанных), не разное правило по происхождению блока.

**Занятые порты — попарно раскрашены по связи** (запрос пользователя:
"занятые порты должны попарно краситься в цвета") — `NetworkCanvasPanel
.linkPairColor` — золотой угол по индексу связи в `plan.getLinks()`,
НЕЗАВИСИМАЯ палитра от цвета сети (тот уже занят подложкой/линией — этот
цвет только про то, какие два порта физически спарены, чтобы на плотном
16-портовом свитче не приходилось прослеживать линию через весь канвас
глазами). Свободные порты — нейтральный серый, как раньше.

**Цвет линии по СТАТУСУ соединения — НЕ реализован в этом заходе.** Вторая
половина того же запроса ("цвета линий должны обозначать текущий статус
соединения, если есть информация") требует источник данных о доступности
(фоновый пинг), которого пока нет — сознательно отложено на следующий заход
вместе с блоком Admin Laptop (см. "Явно отложено" ниже). Пока линия
по-прежнему красится по цвету СЕТИ (резолв живьём через `NetworkTopology
.networkOfLink`, не хранимая ссылка — у связи такой ссылки в модели по-
прежнему нет).

**Растягивание блока** (запрос пользователя: "блоки должны мочь
растягиваться (как в общей схеме)") — точная копия UX `SchemaCanvasPanel`:
хват за юго-восточный уголок, виден только у ВЫДЕЛЕННОГО блока (тот же
принцип, что видимость точек излома только у выделенной связи), Shift-
снаппинг размера к размерам ДРУГИХ блоков (`snapResize`). Размер —
новые поля `NetworkDevicePlacement.width`/`height`, дефолт совпадает со
старыми константами канваса (`MIN_DEVICE_W`/`MIN_DEVICE_H` — переименованы
из `DEVICE_W`/`DEVICE_H`, теперь ещё и минимум при растягивании) — у
сохранённых раньше проектов раскладка не меняется, пока пользователь сам не
потянет за уголок.

**Миграция старых проектов — на СЫРОМ дереве JSON, не после типизированной
привязки.** `Network` больше не объявляет полей `devices`/`links` в модели
вообще — обычная десериализация в `Workspace.class` эти вложенные массивы
просто молча отбросила бы (`FAIL_ON_UNKNOWN_PROPERTIES` выключен), данные
потерялись бы БЕЗВОЗВРАТНО ещё до того, как `migrateLegacyChains` успела бы
чем-то помочь (та работает ПОСЛЕ обычной десериализации, т.к. поля назначения
там всё ещё существуют в модели, просто на другом уровне вложенности того же
объекта — здесь такого поля-мишени для автоматической привязки просто нет).
Поэтому `WorkspaceStore.migrateLegacyNetworkManagerPlans` работает НА JsonNode
ДО вызова `mapper.convertValue(root, Workspace.class)`: поднимает
`networks[i].devices`/`links` в `plan.devices`/`links`, заворачивает
ip/mask/gateway каждого устройства в одно `NetworkAttachment` на сеть, из
которой оно мигрирует. Легаси-геттеры/сеттеры `NetworkDevicePlacement
.getLegacyIpAddress()` и т.п. (`@Deprecated`, с `@JsonProperty` на старое имя
JSON-поля) существуют ТОЛЬКО ради этого промежуточного чтения — новый код их
не вызывает. Покрыто отдельным тестом (`AppModelTest
.migratesLegacyNetworkManagerPlanFromNestedNetworkDevices`, пишет файл
СТАРОЙ формы вручную, не через API). **Побочная находка при написании этого
теста**: Jackson сериализует `getXMm()`/`getYMm()` как `"xmm"`/`"ymm"`
(полностью строчными — оба поля попадают под правило decapitalize
"два заглавных подряд" через внутреннюю логику Jackson), не `"xMm"`/`"yMm"`,
как можно было бы предположить по имени метода — подтверждено эмпирически,
если когда-нибудь понадобится ещё одна ручная миграция/фикстура с этими
полями.

## Round 9 — Admin Laptop, статус связи по фоновому пингу, исправление сторон портов — 2026-09-12

Продолжение того же дня: два пункта, отложенных явно в конце Round 8
("Явно отложено"), плюс баг-репорт по скриншоту на саму реализацию Round 8.

**Баг-репорт: стороны портов перепутаны.** Round 8 положил Ethernet-порты
ВСЕХ устройств на верхний край блока одинаково — но пользователь имел в виду
"для сетевого оборудования [из библиотеки, каталожного] — сверху, а у узлов
схемы — снизу, как было" (в блок-схеме на скриншоте MCTRL4k — узел схемы —
получил порт сверху, хотя должен был остаться снизу, как в Round 1-7).
Исправлено в `NetworkCanvasPanel.portCenterCanvasUnits` — сторона Ethernet-
группы теперь зависит от {@code NetworkDevicePlacement.getDeviceTypeId() !=
null} (каталожное — сверху) против связанного/bare (снизу); оптические
порты — по-прежнему справа в обоих случаях, этого различия правка не
касалась.

**Блок «Admin Laptop»** (запрос: "в поле должен автоматически формироваться
блок Admin Laptop, представляющий текущее устройство и с которого и будет
осуществляться пинг") — новая кнопка «+ Мой компьютер» в тулбаре
`NetworkManagerPanel`. Важное уточнение для реализации: пинг и БЕЗ этого
блока всегда шёл с машины, на которой запущено приложение (`NetworkPingService`
запускает системный `ping` локально) — блок ничего не меняет в МЕХАНИКЕ
пинга, только визуализирует "вот это моя точка входа в топологию". Новый
`service.LocalNetworkInterfaces` (`active()`/`primaryIp()`/`hostname()`) —
берёт ПЕРВЫЙ найденный активный IPv4-адрес, сознательно не пытаясь угадать
"правильный" интерфейс среди нескольких (Wi-Fi/провод/VPN) — однозначного
критерия нет, а `model.Network` не хранит понятие подсети, сопоставлять
интерфейс конкретной сети было бы не по чему. Если у машины несколько
реальных интерфейсов и хочется представить их отдельно — та же общая форма
«Подключить к сети…», что и у любого другого многосетевого устройства
(никакого специального UI для этого случая не заводилось). Новое поле
`NetworkDevicePlacement.adminLaptop` (boolean, персистится) — единственное
структурное отличие от обычного устройства; цвет блока — свой (`
NetworkCanvasPanel.COLOR_ADMIN_LAPTOP`), не путается с категориями каталога/
обычными связанными устройствами. IP синхронизируется — НЕ на каждый
`paintComponent` (опрос `NetworkInterface` не бесплатен, дёргать при
перетаскивании расточительно), а из `NetworkManagerPanel.refresh()`
(`canvas.refreshAdminLaptopAddresses()`, вызывается на КАЖДОЕ изменение
модели, но план персистится только если IP реально изменился — иначе
обычный клик где угодно в приложении гонял бы лишние сохранения). Кнопка
идемпотентна — повторный клик при уже существующем блоке просто сообщает
об этом, не создаёт второй.

**Цвет связи по статусу — фоновый пинг.** Отложенная половина запроса
Round 8 ("цвета линий должны обозначать текущий статус соединения, если есть
информация"). `NetworkManagerPanel` держит `javax.swing.Timer`
(`AVAILABILITY_POLL_MS = 15000`) — каждый тик собирает ВСЕ непустые IP всех
подключений текущего плана в `Set` (дубликаты между сетями опрашиваются один
раз) и пингует их ОДНОКРАТНО и ПАРАЛЛЕЛЬНО уже существующим примитивом
`service.NetworkScanService#scanRange` (тот же, что использует скан
диапазона — короткий пинг по коду возврата процесса, без чтения вывода, без
shell-обёртки; переиспользован БЕЗ ИЗМЕНЕНИЙ — сигнатура уже принимала
произвольный `List<String>`, не только результат `expandRange`). Новый раунд
отменяет НЕЗАВЕРШЁННЫЙ предыдущий (`ScanHandle#cancel()`), не запускает
параллельно — на медленной/загруженной сети опрос может не уложиться в
период. Результат целиком (не по адресу) передаётся в
`NetworkCanvasPanel.setAvailability` по завершении раунда — линии не
перекрашиваются по одной за кадром.

`NetworkCanvasPanel.linkStatusColor` — зелёный, если IP ОБОИХ концов связи (в
СЕТИ, которой принадлежит сама связь — `NetworkTopology.networkOfLink`)
отвечают; красный, если хотя бы один точно не отвечает; `null` — данных
недостаточно (адрес не задан / ещё не опрашивался / сеть не резолвится), и
тогда вызывающий код (`paintComponent`) падает обратно на прежний цвет СЕТИ,
а не рисует нейтральное "серым — неизвестно": пользователь explicitly
оговорил "если есть информация", отсутствие данных сознательно НЕ отдельное
визуальное состояние. Тот же принцип (точка рисуется, только если для этого
IP есть ключ в карте опроса) — маленький индикатор перед строкой адреса на
самом блоке устройства.

**Явно отложено, всё ещё в силе**: Novastar-статус портов экрана (Фаза 5,
после основного, по согласованию), автораздача IP (ответ на уточнение не
получен), подпись порта в тултипе (одобрена, не сделана).

## Round 10 — экспорт карты сети в JPEG, «Выровнять сеть» — 2026-09-12 (тот же день)

Два из трёх пунктов, одобренных в конце Round 9 ("можно"/"давай попробуем").

**Экспорт в JPEG** — точная копия уже существующей схемы (`SignalStagePanel`/

ярче) и без `setAvailability` (статус доступности — для живого вида, не для
сохранённого снимка). `CurrentSchemeExporter` переиспользован БЕЗ ИЗМЕНЕНИЙ
— уже был общим (принимает `Renderer`-лямбду), NetworkCanvasPanel — третий
потребитель после SchemaCanvasPanel/SceneCanvasPanel.

**«Выровнять сеть»** — новая кнопка в списке сетей слева (рядом с «Цвет…»).

верхний угол её же устройств (сеть остаётся примерно там же на канвасе, не
прыгает в (0,0)). Тот же принцип, что уже существующий `AppModel

пытается объехать ДРУГИЕ сети, если они физически перекрываются — авто-
разрешение коллизий МЕЖДУ сетями остаётся отдельной, не реализованной
задачей (см. "явно отложено" выше по тексту, из Round 7).

## Round 11 — подпись порта в тултипе и в таблице, автозаполнение IP по порядку — 2026-09-12 (тот же день)

## Round 12 — статус видео-портов Novastar (Фаза 5) — 2026-09-12 (тот же день)

Последний пункт всего списка Round 8/9, реализован по прямому "делай все
оставшиеся пункты, одобряю" ПОСЛЕ отдельного исследования (см. ниже) —
единственная фича Сетевого менеджера, построенная на НЕДОКУМЕНТИРОВАННОМ
протоколе вендора, поэтому с явной и постоянной оговоркой о статусе доверия
в самом коде, а не только в этих заметках.

**Исследование ДО реализации** — протокол NovaStar (TCP:5200, использует
NovaLCT и такие контроллеры, как MCTRL4k) официально не задокументирован.
Единственный публичный источник — реверс-инжиниренный проект `sarakusha/
novastar` (npm `@novastar/codec`/`@novastar/native`). Отдельное исследование
(не по докам проекта, а по его РЕАЛЬНОМУ исходному коду и Wireshark-
диссектору) установило: (а) формат кадра/контрольной суммы ПОДТВЕРЖДЁН байт в
байт — у исходного проекта есть собственный тест с готовым байтовым вектором
для write-запроса, независимый Wireshark-диссектор согласуется по всем
смещениям полей; (б) конкретные адреса регистров (включён ли порт, число
откликнувшихся приёмных карт) взяты из ДЕКОМПИЛИРОВАННЫХ .dll вендора тем же
проектом — не подобраны вручную; (в) СЕМАНТИКА именно этих двух регистров на
реальном контроллере НЕ подтверждена — ни теста, ни перехваченного трафика
для них в исходном проекте нет. Вердикт: реализовывать стоит, но статус
доверия — "формат верен, поведение непроверено", один реальный контроллер
для проверки нужен, прежде чем полагаться на статус в бою.

**`service.novastar` — новый пакет, три класса.** `NovastarPacket` —
кодирование/декодирование одного пакета (заголовок 18 байт + данные + 2
байта контрольной суммы; "CRC16" в исходном проекте на самом деле обычная
сумма байт с затравкой 0x5555, не настоящий CRC) — `encode`/`encodeReadRequest`
проверены тестом `NovastarPacketTest.encodeMatchesReferenceWriteVector`
против ТОГО САМОГО байтового вектора из исходного проекта (не выведенного из
нашего же кода — независимое подтверждение). `NovastarAddresses` — константы
адресов регистров (порт включён/число карт), взятые из decompiled .dll.
`NovastarClient` — синхронный ОДНОРАЗОВЫЙ TCP-запрос (новое соединение на
каждый вызов, без постоянной сессии — тот же принцип простоты, что
`NetworkPingService`/`NetworkScanService`, никто из них тоже не держит
долгоживущих соединений к устройствам площадки), возвращает `Optional.empty()`
на ЛЮБУЮ ошибку (нет соединения/таймаут/битый ответ), а не бросает исключение
— недоступность контроллера такой же обычный результат, как недоступность
при пинге. `NovastarPortStatusService.readAll` — опрашивает оба регистра для
каждого порта, возвращает статус ТОЛЬКО тех портов, что реально ответили.

**Порт видео vs порт управления — снова разделены, теперь и здесь.** Число
портов для опроса — это `ControllerType.effectivePortCount()` (порты ВЫВОДА
ВИДЕО контроллера, резолвится по цепочке `NetworkDevicePlacement
.getLinkedSchemaNodeId()` → узел схемы → `ControllerInstance` →
`ControllerType`, новый `NetworkManagerPanel.controllerTypeForDevice`) — НЕ
`NetworkDevicePlacement.getEthernetPortCount()` (порт управления самого
Сетевого менеджера, см. Round 9 про то же самое разделение). Опрашивается по
IP ПЕРВОГО непустого подключения устройства (`firstNonBlankIp`) — как и с
Admin Laptop, не пытаемся угадывать, какое из нескольких подключений
"правильное".

**Опрос — в отдельном потоке, не в пуле `NetworkScanService`.** Каждый
включённый контроллер — минимум 2 TCP round-trip'а НА КАЖДЫЙ видео-порт (у
MCTRL4k их может быть много), суммарно способно занять заметное время;
`NetworkManagerPanel.pollNovastarStatuses` (вызывается из того же тика
таймера, что фоновый пинг, см. Round 9) собирает host+число портов на EDT
(модель нельзя трогать вне EDT), затем сам опрос — в отдельном `Thread`, а не
на EDT (иначе подвесил бы весь интерфейс приложения), результат — обратно
через `SwingUtilities.invokeLater`.

**Включается галочкой в «Параметры устройства…»** (`NetworkDeviceParamsDialog
.novastarStatusCheck`) — доступна ТОЛЬКО для устройств, связанных с узлом
схемы (у каталожного сетевого оборудования нет понятия "видео-порт" вообще),
тултип явно предупреждает про экспериментальный статус. На канвасе — ОДНА
сводная строка на блок ("NovaLCT: N/M портов с картами"), не отдельная
геометрия на каждый видео-порт — у Сетевого менеджера и так есть своя система
портов (управления), заводить вторую полноценную визуальную сетку портов для
другого набора портов на том же блоке того же размера — отдельная, более
крупная задача, не входившая в исходный запрос буквально ("показывать
текущий статус" — сводки достаточно).

**Явно отложено, теперь полностью пусто** — весь список Round 8/9 закрыт.

## Round 13 — живая диагностика "ни один порт не видится" (H2/VX1000) — 2026-09-19

Баг-репорт пользователя: реальная площадка (компьютер подключён к сети с
контроллерами H2 и VX1000), Сетевой менеджер настроен, но статус видео-портов
Novastar (Round 12) показывает "NovaLCT: 0/36" и "0/10" для ОБОИХ контроллеров
— именно риск, явно оговорённый в конце Round 12 ("формат верен, поведение
непроверено, нужен один реальный контроллер").

**Диагностика.** Прямой опрос обоих контроллеров тем же кодом, что использует
приложение (`NovastarClient.readRegister` из jshell, в обход UI), подтвердил:
TCP-соединение и разбор пакета (заголовок/checksum) работают штатно, но
регистр "включён"/"число карт" возвращает 0 для КАЖДОГО порта на ОБОИХ
разных семействах контроллеров — статистически маловероятно как настоящее
состояние площадки. Дальше — захват реального трафика Wireshark/tshark
(интерфейс `Ethernet 6`, фильтр по IP контроллеров, ~240 c) с разбором
байтов вручную (см. `NovastarPacket` class-javadoc за деталями) дал точный
ответ: поле `ack` в заголовке ответа (смещение 2) наш код НЕ проверял вообще
— устройство отвечает корректно сформированным пакетом с `ack=2` и данными,
забитыми нулями, на ОБА наших адреса (`PORT_ENABLE_ADDR`/`NUMBER_OF_CARD_ADDR`)
для каждого опрошенного порта — то есть явно ОТКАЗЫВАЕТ в чтении этого
регистра, а не молчит. Подлинный трафик самого NovaLCT к тому же H2 (пойман в
той же сессии, пока NovaLCT сам опрашивал устройство при подключении) отвечает
`ack=0` на совсем другие, гораздо более короткие адреса (0x2/0x6/0x7/0x16,
0x14000000 — в одном из ответов читается строка прошивки
"V1000_V2.4.0_2024-03-05_update.img") — подтверждает, что `ack` реально несёт
статус успех/отказ, не мусорное поле, и что регистровая карта, взятая из
проекта `sarakusha/novastar` (вероятно, снятая с MCTRL4K), для H2/VX1000
просто не совпадает.

**Исправлено** — `NovastarClient.readRegister` теперь проверяет `response
.ack() != 0` и возвращает `Optional.empty()` в этом случае (раньше нулевые
данные-заглушка отказа декодировались как настоящее прочитанное значение 0).
Эффект: для контроллеров с неподдерживаемым адресом регистра строка "NovaLCT:
N/M портов с картами" теперь просто НЕ рисуется (как и было задумано для "нет
данных", см. Round 9/12), вместо лживого "0/N".

**НЕ сделано в этом заходе** — подбор ПРАВИЛЬНЫХ адресов регистров для
H2/VX1000. Через computer-use не удалось продавить UI NovaLCT до экрана
статуса приёмных карт (клики по иконкам тулбара не открывали видимых
диалогов — похоже, всплывающие окна открываются за пределами видимой области,
типичная история для этого legacy-приложения при смене мониторов) — пойманный
трафик NovaLCT относится к базовой идентификации устройства (версия прошивки
и т.п.), не к статусу портов. Чтобы фича заработала по-настоящему (не только
перестала врать), нужен ещё один заход: пользователь вручную открывает в
NovaLCT экран статуса приёмных карт для H2 или VX1000, одновременно снимается
трафик — тогда в захвате будет виден настоящий адрес и его семантика.

## Round 14 — статус портов Novastar убран целиком — 2026-09-19 (тот же день)

## Round 15 — автоперенос сетей из общей схемы — 2026-09-19 (тот же день)

Продолжение того же захода, сразу после отказа от статуса портов Novastar
("нерелевантно... собери план по автопереносу сетей из общей схемы в
менеджер"). Реализовано по плану, согласованному через `EnterPlanMode`
(см. критерии ниже — пользователь выбрал их явно из предложенных вариантов).

**Первый потребитель заготовки T5.4.** `AppModel.networkGraphFromScene`
(`docs/schema-ports-rework/PLAN.md`, D11) существовала с ветки
`schema-ports-rework`, но до этого захода не имела НИ ОДНОГО вызывающего в
основном коде — только тест (`NetworkGraphFromSceneTest`). Round 15 — первое
реальное использование: {@code NetworkCanvasPanel#previewSchemaImport}
строит дифф (граф минус уже размещённые устройства, та же дедупликация
"где угодно в плане", что `NetworkManagerPanel#refreshSchemaPalette`),
{@code #applySchemaImport} — мутирует план.

**Разбивка на сети — по связным компонентам графа** (решение пользователя из
трёх предложенных: по компонентам / всё в одну сеть / спрашивать по каждой
группе). Устройства и коммутаторы, соединённые NETWORK-связями схемы
напрямую или через коммутатор — одна будущая `Network`; коммутатор без
единого кабеля — своя однонодовая группа (тот же случай уже покрыт
`NetworkGraphFromSceneTest.switchAppearsAsASwitchEvenBeforeAnyCableIsConnected`).
Имя группы — метка коммутатора, если он единственный в группе, иначе
«Импорт N» — пользователь правит в диалоге предпросмотра до применения.

**Порт-связи — создаются автоматически, первый свободный порт с каждой
стороны** (решение пользователя, второй из двух вариантов: не создавать
вообще vs занимать первый свободный). `NetworkLink` — целочисленный номер
порта на блоке, не привязан к гнезду схемы, поэтому это ЭВРИСТИКА, не точное
воспроизведение кабельной трассы — пользователь при необходимости
перекладывает связь на нужный порт вручную после импорта. Если у устройства
не осталось свободных портов (например, пятый кабель на четырёхпортовом
устройстве по умолчанию) — связь просто не создаётся, молча пропускается
(тот же принцип, что уже был у ручного случая "связь рисуется за пределами
видимых портов, без предупреждения") — `applySchemaImport` возвращает список
пропущенных связей, `NetworkManagerPanel` показывает их числом в одном
`JOptionPane` после импорта, не блокируя остальной результат.

**UI — кнопка + модальный диалог предпросмотра**, третий вариант из
предложенных (был ещё "кнопка без предпросмотра, сразу применяет"). Новый
`ui/SchemaImportDialog.java` — по группе-строке: чекбокс (включена по
умолчанию), редактируемое поле имени, состав только для чтения. «Перенести
из схемы…» в тулбаре `NetworkManagerPanel` — рядом с «Найти устройства (скан
IP)…», активна всегда (в отличие от других кнопок НЕ требует выбранной сети
слева — импорт сам создаёт сети под каждую группу).

**Однонаправленность — тот же принцип, что весь Сетевой менеджер с Round 1.**
Импорт только ЧИТАЕТ граф схемы и ДОБАВЛЯЕТ новое; повторный запуск на уже
импортированных устройствах — no-op (отфильтровались дедупликацией), никогда
не двигает/не переименовывает/не перепривязывает то, что уже перенесено
раньше, даже если топология схемы с тех пор изменилась (устройство
перекабелировано на другой коммутатор) — осознанный компромисс, а не
недосмотр.

**Реализация — вся мутирующая логика на `NetworkCanvasPanel`, не в
`AppModel`.** Та отдаёт только чистый граф (без побочных эффектов — так и
было задумано в T5.4); канвас уже владеет мутациями плана и геометрией
портов (`autoArrangeNetwork`, `addLinkedDeviceAt`, `effectiveTotalPortCount`,
`linkAtPort` — всё переиспользовано, не продублировано). Связные компоненты
— простой union-find по `NetworkGraphLink` по (уже отфильтрованному от
"известного") множеству id.
