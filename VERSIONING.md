# Версии, теги и релизы — правила

Кратко о том, что значит «текущая версия», когда ставится тег и что можно/нельзя
делать с версиями без прямой команды пользователя. Процедура выпуска —
скилл `release-client`; здесь — **правила**, которым он подчиняется.

## 1. Что такое «текущая версия»

- Источник истины — `AppInfo.VERSION` (`src/main/java/com/vjstb/ledscheme/AppInfo.java`).
  Там всегда стоит версия, **которую готовим** (разрабатываемая, ещё не
  выпущенная или уже выпущенная и дорабатываемая), а не «последняя выпущенная».
- Бамп версии делается один раз на цикл: **когда пользователь назвал номер**
  («меняй на v2.6», «перепрыгнем 2.5»). Сам номер не выбираю и не «исправляю».
  Тестовые билды (`testbuild/`) версию **не меняют**.
- Версии можно пропускать (2.5 пропущена, тег `v2.5` остался на старом коммите
  без релиза). Пропуск — решение пользователя; задним числом «чинить» не надо.
- Экспериментальные выпуски называются `X.Yexp` — **дословно так, как назвал
  пользователь**, в `AppInfo.VERSION`, теге, заголовке релиза, `versions.txt` и
  `VERSION_MANIFEST`. Не нормализовать (`2.5exp` → `v2.5` — ошибка). Неверный
  тег в манифесте ломает автообновление.
- Вместе с `AppInfo.VERSION` меняются: первая строка
  `src/main/resources/whats-new.html` (`<!-- whats-new: X.Y -->`; иначе красный
  `WhatsNewResourceTest`), раздел «vX.Y» в `CHANGELOG.md` (все правки цикла
  обозначаются в нём пунктами текущей версии, нумерация сквозная), счётчик
  тестов в `CLAUDE.md`/`TESTS.md` — по ситуации.

## 2. Теги

- Тег `vX.Y` — **annotated**. При бампе версии он ставится на коммит бампа.
  Последующие правки цикла тег **не двигают** — тег переносится на актуальный
  коммит **только при релизе**, по команде пользователя, способом из скилла
  `release-client` («Перенос тега»): `git tag -f` → `git push origin
  :refs/tags/vX.Y` → `git push origin vX.Y`. `git push --force` на тег не
  проходит и не используется.
- Создание/перенос/удаление тега и его пуш — **каждое по отдельной явной
  команде пользователя**. Разрешение на коммит/пуш кода тег не покрывает.
- Тег, на который уже опубликован GitHub Release (особенно `Latest`), без
  прямой просьбы не трогать: от него зависят обновление клиентов и CI.
- Git-команды запускать **по одной**, не цепочкой `&&` (автоклассификатор
  блокирует составные команды с тегами/пушем).

## 3. Коммиты и пуши

- Коммитить и пушить — только по явной команде («коммить», «пуш»); одно
  разрешение не переносится на следующий раз. Слияния веток — `--no-ff` в
  локальный `master`, пуш — отдельно по команде.
- Сообщение коммита — по сути правки; в конце — строка соавторства из
  системного напоминания. Хуки не обходить (`--no-verify` нельзя).
- Перед коммитом: тесты по теме зелёные; перед релизом — полный `mvn test`.
- Незакоммиченные правки не теряются при откате билда — см. скилл `after-edit`.

## 4. Релиз (сводка; детали — `release-client`)

- Релиз — только когда пользователь сказал «готовь релиз» (он протестировал
  сборку, исправил баги, обновил интерактивные сценарии). «Готовь релиз» — на
  текущий релиз целиком, на будущие не распространяется.
- Релиз клиента = тег + GitHub Release (не draft, не prerelease, `Latest`) +
  артефакты (`.zip`, `.jar`, `.deb`, `.dmg`) + `versions.txt` + `VERSION_MANIFEST`
  (галочка «Доступна»). Windows-сборка — локально с
  `--java-options "-XX:MaxRAMPercentage=75"`.
- Перед релизной CI-сборкой — `ledscheme-model` закоммичен и запушен (в нём
  бывают untracked классы).
- Без `v`-релиза нет «Latest»: версия, не выпущенная релизом, пользователям не
  видна; не объявлять версию «выпущенной», пока не пройдён чеклист.

## 5. Процессы

Закрывать (завершать) можно **только процессы приложения** — командная строка
содержит `led-scheme`, `vjstb`, `ave_tb` или `AVE_ToolBox`. Остальные
`java`/`javaw`-процессы (Minecraft, IDE, Maven, чужие утилиты) не трогаются
никогда; блочный `taskkill`/`Stop-Process` по имени процесса запрещён.
Подробности — скилл `after-edit`.
