## 2. Спецификация

### 2.1 Модель данных

**`ledscheme-model` (задача T1.1):**

```java
public enum InterfaceRole {             // подписи — для UI
    VIDEO("Видео"), LED_DATA("LED-данные"), SYNC("Синхро"), NETWORK("Сеть"),
    CONTROL("Управление"), AUDIO("Аудио"), POWER("Питание"), OTHER("Прочее");
}
// InterfaceType: + private InterfaceRole defaultRole;   // null = не задана
// CardPort:      + private InterfaceRole role;          // null = брать из InterfaceType / эвристики
//                + private Boolean thru;                // null = авто (§2.3), TRUE/FALSE = явно
// copy() обоих классов — копировать новые поля.
```

**Клиент, пакет `com.vjstb.ledscheme.model` (задача T1.2):**

```java
public enum NodeOrientation { RIGHT, DOWN, LEFT, UP }
public enum NodeSide { TOP, RIGHT, BOTTOM, LEFT }
public enum EdgeRouteMode { AUTO, MANUAL, STRAIGHT }

public class PortPlacement {             // раскладка одной группы (CardPort) на блоке
    String portId;

//             + List<PortPlacement> portPlacements

// SchemaEdge: + EdgeRouteMode routeMode (null = legacy: waypoints непусты → MANUAL, иначе STRAIGHT)
```

### 2.2 Стороны по ролям

Таблица для `RIGHT`. Для остальных ориентаций сторона поворачивается:
`DOWN` — по часовой на 90° (LEFT→TOP, TOP→RIGHT, RIGHT→BOTTOM, BOTTOM→LEFT), `LEFT` — на
180°, `UP` — против часовой на 90°.

| Роль | Вход (`IN`) | Выход (`OUT`) | `IN_OUT` |
|---|---|---|---|
| VIDEO, LED_DATA, AUDIO, OTHER | LEFT | RIGHT | RIGHT |
| SYNC | TOP | BOTTOM | BOTTOM |
| NETWORK, CONTROL | BOTTOM | BOTTOM | BOTTOM |
| POWER | LEFT (ввод) | RIGHT (отходящие) | RIGHT |
| любая роль, выход с транзитом (`thru`) | — | BOTTOM | — |

`PortPlacement.side` переопределяет таблицу и **не** поворачивается при смене ориентации
(пользователь поставил группу руками — она остаётся там). Команда «Вернуть раскладку по
умолчанию» сбрасывает `side` и `order` у всех групп блока.

### 2.3 Разрешение роли и транзита

Порядок: `PortPlacement.roleOverride` → `CardPort.role` → `InterfaceType.defaultRole` (тип
интерфейса ищется по совпадению начала `CardPort.connectorType` с `InterfaceType.name`, как в
`WireLabelDialog`) → эвристика. В схеме питания роль всегда `POWER`.

Эвристика по `connectorType` (без учёта регистра, проверять **в этом порядке**):

| Шаблон | Роль |
|---|---|
| `genlock\|blackburst\|tri-?level\|\bsync\b\|ltc\|timecode\|word ?clock` | SYNC |
| `xlr\|aes\|madi\|dante\|\btrs\b\|jack\|speakon` | AUDIO |
| `ethernet\|rj-?45\|cat ?5\|cat ?6\|cat ?7\|\blan\b\|sfp` | LED_DATA, если блок `CONTROLLER`/`CONVERTER`/`SCREEN`; иначе NETWORK |
| `fiber\|opticalcon\|оптик` | LED_DATA, если блок `CONTROLLER`/`CONVERTER`/`SCREEN`; иначе VIDEO |
| `usb\|midi\|dmx\|rs-?232\|rs-?485\|gpio` | CONTROL |
| `hdmi\|displayport\|\bdp\b\|sdi\|dvi\|thunderbolt` | VIDEO |
| иначе | OTHER |

Контрольные случаи (обязательны в тесте, взяты из реального проекта): MCTRL4K
«Cat6/RJ45 OUT» → LED_DATA; CVT4K «Fiber IN» → LED_DATA; Disguise D3 «Ethernet Cat6 OUT» →
NETWORK; PixelHue Q8 (тип CUSTOM) «Ethernet Cat5e IN» → NETWORK, «Fiber OUT» → VIDEO;
Blackmagic «Genlock (SDI) OUT» → SYNC; экран «Ethernet IN» → LED_DATA; «16xBNC» → OTHER.

Транзит: `thruOverride` → `CardPort.thru` → авто: в пределах одной карты (у питания — всего
списка `powerConnectors`) ровно **одна** группа `IN` и ровно **одна** группа `OUT` одного и того
же `connectorType`, у обеих `count == 1` → эта `OUT` — транзит. Контрольные случаи:
«Проходная» CEE 32A IN×1 + OUT×1 → транзит, 6×CEE 16A → нет; MCTRL4K Genlock IN×1 + OUT×1 →
транзит; D3 XLR IN×2 + OUT×2 → нет; Q8 HDMI IN и OUT на разных картах → нет. В UI авто-транзит
помечается «(авто)».

### 2.4 Раскладка блока (`NodePortLayout`)

- **Иерархия:** сторона → отсек карты → группа (`CardPort`) → гнёзда.
- **Отсек:** подряд идущие на одной стороне группы одной карты. Шапка — имя карты; не
  рисуется, если у блока ровно одна карта. Подряд идущие **незадействованные** карты с
  одинаковым именем и составом групп сливаются в «Имя ×N». Разъёмы питания — один отсек без
  шапки.
- **Свёрнута ли группа:** `collapsed == TRUE` → да; `FALSE` → нет; `null` → свёрнута, если на
  группе 0 связей и глобальная настройка «Группы гнёзд» = «авто»; при «всегда развёрнуты» —
  развёрнута.
- Свёрнутая группа — одно гнездо, подпись «N×Тип». Развёрнутая — N гнёзд, номера 1…N, имя
  типа один раз у первого гнезда. `IN_OUT` — одно гнездо на каждый слот (не две точки, как
  сейчас).
- **«Только задействованные»:** группы без связей не рисуются; вместо скрытых — одна строка на
  сторону: «ещё N карт» (если скрыты целые карты) или «ещё: 4×DP, 4×SDI». Скрытые гнёзда
  по-прежнему считаются в ёмкости и проверках.
- **Подписи только горизонтальные.** LEFT/RIGHT: номер у пина внутри блока, имя группы рядом
  на первой строке. TOP/BOTTOM: номера под/над пинами, имя группы строкой ниже/выше со
  скобкой на ширину группы.
- **Название блока:** полоса под подписями верхней стороны; строки левой и правой сторон
  начинаются ниже названия. Мета-строки (статистика экрана, «⚠») — как сейчас.
- **Экраны:** гнёзда-кабинеты на миниатюре расключения (`chainEndpointSocketCabinetIds`) дают
  пин на ближайшей по правилам стороне рамки, на проекции центра кабинета, и тонкую выноску
  от пина к кабинету.
- **Размер:** раскладка возвращает минимальный размер; автоподгон только **растит** ширину и
  высоту (как сейчас), вручную увеличенный блок не уменьшает.

Стартовые метрики — один класс `SchemaLayoutMetrics` (подбирать по эталонным картинкам, не по
месту): шрифт названия 12 bold, подписей 10; шаг строки LEFT/RIGHT — 14; шаг колонки TOP/BOTTOM —
max(16, ширина номера + 6); пин 6×8 (боковые) и 8×6 (верх/низ), центр на рамке; шапка отсека
14; зазор между отсеками 6; внутренний отступ 8.

### 2.5 Трассировка (`OrthogonalRouter`)

- Вход: пин-источник (точка, сторона), пин-приёмник, препятствия — прямоугольники всех
  блоков, расширенные на `margin = 10`.
- Выход: ломаная, все отрезки горизонтальны или вертикальны. Первый и последний отрезок
  перпендикулярны стороне пина, длина стаба ≥ 12.
- Алгоритм: ортогональный граф видимости по координатам сторон препятствий и стабов (Wybrow
  et al., 2009 — ссылка в `DIALOG.md`), кратчайший путь со штрафом за излом
  (`cost = длина + 40 × изломы`). Если пути нет — простой Z-маршрут без обхода, с флагом
  `fallback` для теста.
- `LaneNudger`: совпадающие коллинеарные участки **разных** связей разносятся на 8 px в
  пределах канала; концы на пинах не двигаются. Связи одного пучка (D8) не разносятся — у
  них общий ствол от точки слияния до пина.
- Производительность: фикстура ×3 (≈ 90 блоков, 200 связей) трассируется целиком быстрее
  200 мс — тест с порогом ×5 от замера, чтобы не флапал.

### 2.6 Связи на холсте

- `routeMode`: `AUTO` — маршрут считается при отрисовке и не хранится; `MANUAL` — через
  сохранённые изломы (как сейчас); `STRAIGHT` — прямая (как сейчас без изломов).
- Перетаскивание излома или отрезка у `AUTO`-связи превращает её в `MANUAL` с текущим
  маршрутом в качестве изломов (одна запись отмены).
- Режим «ортогональные связи» (настройка, по умолчанию вкл.): при перемещении блока у
  `MANUAL`-связей первый/последний излом сдвигается по одной оси так, чтобы отрезок к пину
  остался перпендикулярным; Shift+перетаскивание отрезка вставляет излом.
- Команды: меню связи «Маршрут ▸ Авто под 90° / Вручную / Прямая»; меню и кнопка панели
  схемы «Перетрассировать выделенные» / «Перетрассировать все» (ставит `AUTO`).
- Цвет (D9): `edge.color` → стиль схемы (роль гнезда-источника у сигнала; номинал разъёма у
  питания) → цвет стиля по умолчанию.
- Мостики (D10): `computeWireHops` работает на итоговых ломаных всех режимов.
- Стрелка (D15): настройка «у приёмника» (по умолчанию) / «на каждом отрезке».
- Подпись: простой текст с подложкой цвета фона; смещение `labelDx/labelDy` сохраняется
  относительно середины маршрута; чип «+ подпись» — D14.

### 2.7 Стиль схемы (`SchemaStyle`)

- Все цвета холста — только из стиля: фон, заливка блока по `SchemaNodeType`, рамка, текст,
  цвета ролей, цвета номиналов питания, выделение, предупреждение, подпись и подложка.
- Пресеты:
  - «Экранный» — ровно текущие цвета: берёт `Palette.BG`/`BORDER`/`MUTED`/`ACCENT`,
    `nodeColor(type)`, палитру разъёмов, следует теме интерфейса.
  - «Печатный» — белый фон, блоки `#FFCC00` с чёрной рамкой 1px, чёрный текст; линии:
    видео чёрные, сеть `#E01B1B`, синхро фиолетовые пунктиром, LED-данные `#1F6FD1`;
    питание 125A `#C000C0`, 63A `#8B4513`, 32A `#E00000`, 16A и прочее чёрные.
- Выбор пресета — «Предпочтения» → «Оформление схемы». Экспорт использует активный пресет.
  Пользовательские цвета линий (D9) важнее пресета.

### 2.8 Настройки профиля (`UserProfile`)

### Этап 6 — доводка печатного пресета (по желанию)

**T6.1** Сверить «Печатный» пресет с референсами пользователя (жёлтые блоки, красная сеть,

Зависит от: T4.5.

**T6.2** Блок-«шина» (Ring) — **снято** (2026-09-18, `DIALOG.md` реплика 5). При
обсуждении выяснилось, что T4.3 (`EdgeBundles` — точка слияния и подпись "×N" для
нескольких связей в одно свёрнутое гнездо) была реализована и покрыта тестами, но
T4.4 ни разу не вызвала её из отрисовки холста — пользователь не увидел эффекта
именно поэтому, не из-за отсутствия отдельного блока. Пробел закрыт (см. `ui.
SchemaCanvasPanel#drawEdgeBundleMarkers`/`bundleCount`, тест `EdgeBundleRenderTest`)
— несколько силовых/сигнальных линий, сходящихся в одно принудительно свёрнутое
гнездо, теперь визуально сливаются с коротким стволом и подписью количества, что и
есть искомый эффект «шины». Отдельный тип узла-«Ring» не нужен.

## 4. Порядок и параллельность

```
Дорожка A (горячие файлы, строго по очереди):
  T0.1 → T0.2 → T1.1 → T1.2 → T2.2* → T3.1 → T3.2 → T3.3 → T3.4 → T4.4 → T4.5 → T5.4 → T6.1 → T7.1–T7.3
  (* T2.2 — после T2.1)
Дорожка B (новые файлы, параллельно с A после T1.2):
  {T1.3, T1.4, T1.5*, T2.3} → T2.1 → T4.1 → {T4.2, T4.3}
  (* T1.5 трогает горячий UserProfile — не одновременно с задачами A, меняющими UserProfile)
Дорожка C (библиотека):
  T5.2 (сразу после T1.1) → T5.3;   T5.1 (после T1.3)
```

Одновременно — не больше трёх агентов; ни одного горячего файла у двух агентов сразу.

## 5. Точки остановки у пользователя

После каждого этапа координатор:
1. показывает картинки T0.2 «до/после»;
2. спрашивает разрешение на коммит этапа в ветку `claude/schema-ports-rework` (и в ветку
   `ledscheme-model` после T1.1);
3. спрашивает, продолжать ли.

Публикация ролей в общую библиотеку (T5.3), живая проверка через computer-use, слияние в
`master` и релиз — отдельные разрешения.
