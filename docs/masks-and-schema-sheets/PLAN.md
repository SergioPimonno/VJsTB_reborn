## 1. Исходные запросы пользователя (дословно по смыслу)

1. Кнопка «задать размер шрифта для всей схемы» — для всех блоков с дефолтным
   размером; блоки с кастомным размером не трогать.
2. Убрать ограничение 16k на сторону при генерации масок и канвасов.
3. Убрать колонку/настройку «Растр» (не используется); вместо неё — видимость
   плашки с именем экрана; отдельная галочка для разрешения на той же плашке.
4. Параметр маски «сетка»: экран из кабинетов-сеток, маска в 2 раза выше.
5. Предупреждение, если канвас меньше размещённых в нём масок (обрезает их).
6. Своя пара цветов для маски; механизм палитры из общих схем, но память цветов
   масок — отдельная.
7. Программа не открывается, если папку положить на диск D: — почему, как исправить.
8. Несколько блок-схем на сцену. В режиме схемы верхние плашки «Проект» и «Сцена»
   как были, плашка «Экран» меняется на «Схема» со списком схем; окно
   редактирования названия схемы; в сетевом менеджере при импорте из общей схемы —
   выбор схемы сигнала.
9. Переделать сохранение своего блока в библиотеку: сейчас можно сохранить
   ПУСТОЙ пресет. Кнопку «Сохранить как пресет» справа убрать, перенести в меню
   ПКМ по блоку; сохранять в т.ч. все карты и разъёмы, которые пользователь
   добавил блоку на схеме.

## 2. Решения пользователя

| # | Вопрос | Решение |
|---|---|---|
| D1 | Спецификация при нескольких схемах | Каждая схема считается ОТДЕЛЬНО: одни и те же позиции пишутся в разных колонках, подписанных названием схемы. Какие блоки «общие» — узнать нельзя, перестраховываемся. |
| D2 | Автозаполнение экранами/контроллерами | Только в ПЕРВОЙ схеме режима. |
| D3 | «Сетка» | Множитель высоты маски, по умолчанию 2. |
| D4 | Веб-редактор масок на сервере | Повторить изменения масок (п. 3, 4, 6). Деплой — только с явного разрешения. |
| D5 | Старые клиенты открывают новый файл | Схемы одного режима хранятся в файле со сдвигом по X (ширина предыдущих + зазор); новый клиент сдвиг вычитает. Старый клиент видит схемы рядом, а не стопкой. |
| D6 | Спецификация и сцены | Для КАЖДОЙ сцены проекта — отдельная спецификация (свой .xlsx, все листы только по этой сцене); колонки по схемам — внутри спецификации сцены. Общепроектной спецификации больше нет. |
| D7 | Лимит 16k | Реализуем три меры: потоковая запись полосами, увеличенный heap, уменьшенное превью. Сторона маски/канваса ≥ 16384 px — предупреждение; жёсткое ограничение — 30000 px. Разрешение превью — пресеты как в After Effects (Полное, 1/2, 1/3, 1/4, 1/8, Авто). |

Колонки «Итого» по схемам нет — осознанно (суть D1): итог по нескольким схемам
вводил бы в заблуждение, если одни и те же блоки нарисованы на нескольких схемах.

## 3. Установленные факты (проверено по коду 2026-09-30)

- Лимит 16k — только спиннеры `VisualizationStagePanel:148-149`
  (`SpinnerNumberModel(…, 16384, …)`). Реальные ограничения глубже: маски рисуются
  целиком в `BufferedImage` (`PixelGridRenderer.renderMask/renderCanvasMask`, 4 Б/px,
  маска экрана сначала отдельной картинкой, потом `drawImage` в канвас);
  `CanvasEditorPanel.maskCache` держит маски в ПОЛНОМ разрешении; диалог
  предпросмотра (`VisualizationStagePanel.showMaskPreviewDialog`) держит все
  изображения сразу. `ResolumePresetExporter:65` пишет `max="16384"`; After Effects
  ограничивает композицию 30000×30000.
- Растр: `CanvasPlacement.showRaster` (по умолчанию true), рисуется в
  `PixelGridRenderer:137`, в т.ч. в отдельных масках экранов (`defaultForScreen`).
- Цвет маски: `Screen.background` (`MaskColorPreset`), общий на экран во всех
  канвасах; читается в `PixelGridRenderer`, `Structure3DPanel:895-911`, комбобокс
  «Фон» в таблице гридов, комбобокс дефолтов сцены `SetupStagePanel:2630`.
  Миграция legacy per-placement цвета — `AppModel.seedScreenMaskColorsFromLegacyPlacements`.
- Палитра линий: `UiKit.showColorChooser(owner, title, initial, settings)` +
  `RecentColorsChooserPanel` (static список + `UserProfile.recentLineColors`,
  `SettingsManager.rememberRecentLineColor`). Тесты:
  `RecentColorsChooserPanel*Test`, `settings/RecentLineColorPersistenceTest`.
- `model.MaskColorPreset`, `Screen`, `Scene`, `SchemaNode/Edge` — КЛИЕНТСКИЕ классы
  (не `ledscheme-model`). JS-массив `MASK_PRESETS` в
  `ledscheme-server/src/main/resources/static/app.js` — ручная копия (золотое
  правило 4), там же свой редактор масок с галочкой растра.
- Схема: узлы/связи — плоские списки `Scene.schemaNodes/schemaEdges`, режим —
  поле `mode`. Доступ для UI — `AppModel.schemaNodesForCurrentScene(mode)` /
  `schemaEdgesForCurrentScene(mode)` (используют `SchemaPanel`, `SchemaCanvasPanel`,
  `NetworkManagerPanel`, `schemalayout/SchemaUsage`). Прямые `currentScene.
  getSchemaNodes()/getSchemaEdges()` — ~25 мест в `AppModel` (add/paste/delete/
  clearSchema/orphans/autoPopulate/legends/networkGraphFromScene), плюс
  `SchemaLoadCalc`, `NetworkCanvasPanel:1017`, `NetworkDeviceLabels:48`,
  `OutputStagePanel:772,1029,1060` (спецификация).
- Админка `ledscheme-admin/.../project/ProjectSummary.java` читает
  `scene.schemaNodes` из JSON напрямую — поэтому списки остаются плоскими.
- Все места чтения JSON в клиенте выключают `FAIL_ON_UNKNOWN_PROPERTIES` — старый
  клиент откроет файл с новыми полями, но при пересохранении их потеряет.
- `ContextBar` («Проект → Сцена → (Экран)») создаётся в `PowerStagePanel:212`,
  `SignalStagePanel:400` с `includeScreen=true`; вид переключается
  `schemaViewBtn`/`chainViewBtn` (+ `networkViewBtn` в «Сигнале»).
- Спецификация сейчас — ОДИН файл на проект `<Проект>_спецификация.xlsx`
  (`OutputStagePanel.buildEquipmentSpecWorkbook(project)`, ~строка 707; вызовы —
  пакет документации ~526 и кнопка «только спецификация» `exportSpecOnly` ~676);
  все листы («Инфо», «Кабинеты», «Оборудование», «Конструктив», «Фермы»,
  «Общий список», «Коммутация — сводная/сплайсовка») суммируют ВСЕ сцены
  циклом `for (Scene scene : project.getScenes())`. Пакет документации уже
  раскладывает файлы по папкам сцен (`<папка>/<Сцена>/Сила|Сигнал|Маски`, ~383).
- «Сохранить как пресет» (п. 9): кнопка `saveAsPresetBtn` в форме «Добавить
  узел» `SchemaPanel` (~строки 56, 188-190, включение в
  `updateAddFormEnablement` ~301), метод `SchemaPanel.saveAsPreset` (~437)
  вызывает `model.addEquipmentPreset(mode, type, name, "", null)` — берёт только
  подпись из поля ввода, карт нет вообще, отсюда пустые пресеты. Меню ПКМ блока —
  `SchemaCanvasPanel.showNodeMenu`. Обратное направление уже есть:
  `AppModel.addSchemaNodeFromPreset` копирует карты
  (`duplicateCardWithFreshIds`) и разъёмы питания (`duplicatePortWithFreshId`)
  пресета в узел. `EquipmentPreset` (в `ledscheme-model`) хранит карты и
  разъёмы питания, раскладку гнёзд (`PortPlacement`) — нет.
- «Перенести из схемы…»: `NetworkManagerPanel.openSchemaImportDialog` →
  `NetworkCanvasPanel.previewSchemaImport/applySchemaImport` →
  `AppModel.networkGraphFromScene(scene)`; диалог `SchemaImportDialog`.
- Диск D: — в сборке нет привязки к C: (лаунчер jpackage использует `$APPDIR`,
  данные в `~/.led-scheme` через `user.home`). Ошибки старта не видны:
  `App.main` делает `printStackTrace()` под `javaw`. Перезапуск/автообновление
  (`UpdateManager:248, 277`) зовут `javaw -jar` — в сборке jpackage это системная
  Java (если есть), а не встроенный рантайм.
- **В рабочем дереве master — большая незакоммиченная работа v2.6**, и параллельно
  с планированием в том же дереве работала другая сессия (`ContextBar`,
  `EdgeBundles`, `SchemaCanvasPanel`). Работать агентам в одном дереве нельзя.

### 4.3 Правила для всех агентов (вставлены в каждый промпт как «Общие правила»)

- Работа в СВОЁМ git worktree от актуального master, ветка `claude/<трек>`.
- Коммиты в свою ветку разрешены пользователем при запуске агента; push, merge в
  master, теги, деплой — НЕТ.
- До начала: прочитать `CLAUDE.md`, этот план (§2, §3, свой трек), вызвать скилл
  `run-tests`; при необходимости — `test-build`.
- `testbuild/led-scheme-test.jar` — общий для всех worktree: агенты волн его НЕ
  перезаписывают (гонка между параллельными агентами); сборку проверяют
  `mvn -DskipTests package` в своём worktree. Тестовый билд пересобирает трек I
  после мержа. (Осознанное исключение из правила CLAUDE.md на время волн.)
- Полный `mvn test` в своём worktree — 0 failures перед завершением.
- Стиль: javadoc объясняет ПОЧЕМУ (запрос/баг-репорт с датой 2026-09-30), как в
  окружающем коде; русские строки UI; не вычищать старые комментарии.
- Старые проекты должны открываться: новые поля — с дефолтами, сохраняющими
  прежнее поведение, кроме явно заказанных изменений.
- Не трогать файлы чужих треков сверх необходимого; если пришлось — перечислить в
  отчёте.
- Отчёт в конце: что сделано, список файлов, новые тесты, результат `mvn test`,
  открытые вопросы, отклонения от плана. Строки для `CHANGELOG.md`/`TESTS.md`
  дать текстом в отчёте (сами файлы правит трек I, чтобы не было конфликтов).

## 6. Риски и что проверить при приёмке

- **D5 и пересохранение старым клиентом**: разбивка на схемы теряется (узлы
  попадут в одну схему режима, разнесённые по X). Приемлемо по решению D5;
  упомянуть в CHANGELOG.
- **Спецификация без «Итого»** — осознанно (D1). Если пользователь захочет
  итог — отдельный запрос.
- **Общепроектной спецификации больше нет** (D6) — если кто-то собирал закупку
  по проекту целиком из одного файла, теперь это N файлов. Отметить в CHANGELOG.
- **Производительность потоковой записи**: канвас 30000×8000 — сотни МБ
  несжатых данных через Deflater; экспорт должен идти в фоне с прогрессом.
- **Экран шире 30000 px** (или выше с множителем «сетки») — его маска не
  экспортируется (D7), пользователь получает понятное сообщение; сам экран на
  «Сетапе» не ограничиваем.
- **Растр исчезнет и в уже экспортированных ранее форматах** (отдельные маски
  экранов) — это заказанное изменение, в CHANGELOG отметить.
- **Пункт 7 может не воспроизвестись** без данных пользователя — тогда главный
  результат трека D — лог запуска и исправленный перезапуск.
