## 1. Что строим

Экран может собираться из **модулей**. Каждый модуль включается в **приёмную карту** своим отдельным сигнальным
шлейфом (топология «звезда»; число модулей на карту в одном экране может быть разным). Питание модулям и картам дают
**блоки питания**: у блока несколько шлейфов питания, он питает прямоугольную (обычно) группу модулей, рядом с которой
стоит. Пользователь:

1. в **«Сигнале» → «Приёмные карты»** назначает модулям карты и порядок подключения (номер выхода карты);
2. в **«Сигнале» → «Расключение экрана»** ведёт цепочки портов контроллера — как сейчас, но звенья — **карты**;
3. в **«Питании» → «Блоки питания»** назначает модулям блоки питания;
4. в **«Питании» → «Расключение экрана»** ведёт фазы — как сейчас, но звенья — **блоки питания**.

Обычные кабинеты на том же экране остаются звеньями как раньше (смешанный экран допустим). Экран без модулей работает
ровно как сейчас.

## 2. Решения пользователя (не пересматривать без него)

### Общее
| № | Решение |
|---|---|
| D1 | У типа кабинета в библиотеке флаг **«Приёмная карта отдельно»** (`CabinetType.receiverCardSeparate`, по умолчанию выкл.). Такой тип — **модуль**. Экран «модульный», если хоть у одной видимой ячейки эффективный тип — модуль |
| D2 | Новые виды — не отдельный этап: **«Сигнал» → «Приёмные карты»** и **«Питание» → «Блоки питания»**, оба ПЕРЕД «Расключением экрана» в переключателе видов этапа. Кнопки видны, только если в текущей сцене есть модульный экран. Название — «Приёмные карты» (не «Карты», не «Группировка») |
| D3 | Смешанный экран допустим: обычный кабинет — самостоятельное звено расключения и в сигнале, и в питании |
| D4 | **Информация — по месту использования.** «Расключение экрана» (оба этапа) справа — как сейчас в приложении, строго по цепочкам: «Существующие цепочки», строка на цепочку «порт/фаза · число звеньев · пиксели/ватты · ✕», «Очистить цепочки…»; число звеньев — теми словами, что на экране: «3 карты, 2 каб.», «40 каб.», «4 блока, 1 каб.». Ничего о картах/блоках по отдельности здесь нет. О картах — только в «Приёмных картах», о блоках — только в «Блоках питания» |
| D5 | Длины шлейфов и кабелей — **по прямой** между центрами модуля «места» (карты или блока) и модуля. Проверка — только если длина указана у типа |

### Приёмные карты
| № | Решение |
|---|---|
| D6 | **Топология «звезда»**: каждый модуль — свой шлейф до карты. Важен **номер модуля = номер выхода карты**; цепочек внутри карты нет |
| D7 | **Нумерация модулей — шаблон на весь экран** (смешивать порядки на экране нежелательно): 8 вариантов (первый модуль в одном из 4 углов × по строкам / по столбцам) + «змейка». Палитра — **под холстом слева**, одна строка из 8 плиток с цифрами 1…9 в порядке нумерации, подсказка словами и строка «Первый модуль — слева сверху, дальше вправо по строке» |
| D8 | **Порядок вручную** на карте: «Порядок вручную…» — клики по модулям карты = 1, 2, 3…; без номера — «?»; «Сбросить к шаблону». Карта помечается «вручную» |
| D9 | **Назначение карт** без перетаскивания: «Тип карты» (список) — разделитель — **«Вручную»** (протяжка по модулям → одна карта на выделение при отпускании мыши) — разделитель — **«Автоматически»** (поля «Г × В мод.» прямо под ним; фокус в них включает режим; протяжка по области → разбиение на карты Г×В, пунктир-предпросмотр; остаток — карты меньшего размера) |
| D10 | **Правило замены**: карта никогда не перекрывает другую; новая карта целиком заменяет задетые, их модули вне выделения — «без карты» (оранжевые) + строка «Заменено карт: N, модулей без карты: M». Повторная протяжка по той же карте тем же типом — ничего. Клик без протяжки по модулю с картой — выбор карты. «Снять карту» / Delete |
| D11 | **Место карты** — модуль, на котором она стоит (по умолчанию ближайший к центру её модулей; «Место карты…» — клик по модулю). На нём — плашка с именем карты («К3») |
| D12 | **Длина шлейфа** — у **типа карты** (`ribbonLengthMm`). Модуль дальше — красная обводка и линия, «⚠N» в списке карт. Флажок «шлейфы» рисует все шлейфы |
| D13 | **Выходы карты** — у типа карты (`moduleOutputs`): модулей больше — номера сверх лимита красным, в списке «9/8» |
| D14 | **Обозначение номера модуля** — по умолчанию просто число; шаблон — в Предпочтениях (`{n}`, `{card}`: «1», «J1», «P1», «К3.1», свой текст) |
| D15 | **Имена карт К1…КN** — сквозные по экрану, без пропусков, пересчитываются после любой правки; не хранятся. Порядок — **Предпочтения → «Нумерация приёмных карт»**: 8 вариантов (стартовый угол × по строкам/столбцам; якорь карты — её модуль в стартовом углу) или «как нумерация модулей экрана»; по умолчанию «слева направо, сверху вниз». Внутренний `id` карты (на нём цепочки) не меняется |
| D16 | Справа в виде: «Тип карты» → «Как назначать» → **«Карты экрана»** в четыре столбца **«Карта · Модули · Разрешение · Пиксели»** (имя · модель · «вручную»; модули «12/12», «⚠N»; разрешение — ширина×высота прямоугольника модулей карты в px; пиксели — сумма модулей) + опциональный блок статистики |

### Блоки питания
| № | Решение |
|---|---|
| D17 | Блок питает **модули** (не карты). Тип блока: **число шлейфов**, мощность, **длина кабеля**, включаемый параметр **«Отдельный выход на карту»** (+1 выход сверх шлейфов, только под карту, обозначение «К») |
| D18 | **Назначение блоков** — как карт: «Тип блока» — «Вручную» (один блок на выделенные модули) — «Автоматически» (выделенная область дробится на **прямоугольники**, размер **подбирается сам**: прямоугольник не больше числа шлейфов; все модули в пределах кабеля от места блока; карте, стоящей в области, хватает выхода. Из прошедших — с наименьшим числом блоков, при равенстве крупнее и ближе к квадрату; не прошёл никто — 1×1. Неполные блоки у края допустимы). Под переключателем — «Подобрано: 4×2 мод. на блок, блоков: 9». Правило замены — как у карт (остаток — «без питания»). «Снять блок» / Delete |
| D19 | **Карта питается от своего блока** — того, в области которого её место: от «Отдельного выхода на карту», если он есть у типа, иначе **принудительно забирает один из шлейфов** блока (может перегрузить блок — подсветка). Галочки «Выход под карту» в виде нет. Переключение «Отдельного выхода» у типа сразу пересчитывает автоматически разбитые области этого типа; блоки, поставленные вручную, не пересчитываются |
| D20 | **Место блока** — модуль у центра его области; «Место блока…» — клик по модулю внутри области. От места считается длина кабелей |
| D21 | На модуле в виде «Блоки питания» — номер его шлейфа в блоке; контур и цвет области — какой блок питает; плашка «БПn» (+«+К», если блок питает карту) на месте блока; флажок «кабели питания». Список «Блоки питания экрана»: «БП1 · модель · карты · 8/8 +К ⚠N». Имена БП1…БПn — сквозные по экрану, по месту блока в порядке того же параметра «Нумерация приёмных карт» (отдельного параметра не заводим) |
| D22 | **Нагрузка фазы — по мощности блоков** (номинал), а не по сумме модулей |
| D23 | При повторном автоматическом разбиении блоки пересоздаются и **выпадают из фаз** — так и оставить (как карты при замене) |

### Расключение экрана
| № | Решение |
|---|---|
| D24 | **Сигнал**: маршрут по порту — как раньше (клик за кликом, вся существующая логика), звенья — карты и обычные кабинеты; **пиксели карты = сумма пикселей её модулей**. На холсте: модули серым, поверх — карты (цвет «Приёмные карты», рамка — цветом цепочки), поверх — цепочки по центрам карт |
| D25 | **Питание**: звенья — блоки питания и обычные кабинеты; **карты не рисуются**; рисуются **области блоков** — контур по границе модулей блока (может быть непрямоугольной), заливка цветом фазы, плашка «БПn» на месте блока цветом фазы; цепочки фаз — по местам блоков. Клик по модулю = его блок |
| D26 | Модуль без карты (сигнал) или без блока (питание) в цепочку не попадает; подсказка ведёт в нужный вид |

## 3. Термины

| В интерфейсе | Класс | Что это |
|---|---|---|
| Модуль | `CabinetType` с `receiverCardSeparate`; ячейка — `CabinetInstance` | Маски, канвас, Сетап, форма экрана — без изменений |
| Приёмная карта (тип / на экране) | `ReceiverCardType` (`ledscheme-model`) / `ReceiverCardInstance` (клиент) | Набор модулей + порядок + место |
| Блок питания (тип / на экране) | `PowerSupplyType` (`ledscheme-model`) / `PowerSupplyInstance` (клиент) | Набор модулей + место; карту в своей области питает вычисляемо |
| Номер модуля | — | Выход карты 1…N (шаблон экрана или вручную) |
| Звено расключения | `service.ChainUnits.Unit` | Сигнал: карта / обычный кабинет; питание: блок / обычный кабинет |

## 4. Данные

### 4.1. `ledscheme-model` (после правок — `mvn -DskipTests install`; коммит/пуш — по команде)
- `CabinetType.receiverCardSeparate` (boolean, `false`) — в `copy()` / `applyEditedValues()`.
- `ReceiverCardType`: `id`, `name`, `vendor`, `company`, `moduleOutputs` (Integer), `ribbonLengthMm` (Double),
  `maxWidthPx`, `maxHeightPx`, `maxPixels` (Integer), `powerW`, `weightKg`, `physical` (`PhysicalSpec`), `notes`.
- `PowerSupplyType`: `id`, `name`, `vendor`, `company`, `outputs` (Integer — шлейфы модулей), `ratedPowerW` (Double),
  `cableLengthMm` (Double), `cardOutput` (boolean — «Отдельный выход на карту»), `inputVoltage` (String, справочно),
  `weightKg`, `physical`, `notes`.
- Числовые поля необязательны: `null` — «не указано, не проверять» (не ноль). Обе — с `copy()` / `applyEditedValues()`.

### 4.2. Клиент (`com.vjstb.ledscheme.model`), всё в `Screen`
- `receiverCards: List<ReceiverCardInstance>` — `id` (UUID), `receiverCardTypeId`, `moduleIds`,
  `manualPortOrder: List<String>` (`null` — по шаблону), `hostModuleId` (`null` — авто).
- `moduleNumbering: ModuleNumberingPattern` — `corner` (TL/TR/BL/BR), `axis` (ROWS/COLUMNS), `snake`;
  по умолчанию «слева сверху, по строкам, без змейки».
- `powerSupplies: List<PowerSupplyInstance>` — `id`, `powerSupplyTypeId`, `moduleIds`, `hostModuleId` (`null` — авто).
- `powerAutoAreas: List<PowerAutoArea>` — `rect` (строки/столбцы), `powerSupplyTypeId`: области, разбитые
  автоматически (нужны D19 для пересчёта). Ручной блок поверх области удаляет её запись.
- Не хранится, вычисляется: имена карт/блоков (D15, D21), от какого выхода питается карта (D19), номера.
- **Цепочки — формат не меняется**: `SignalChain/PowerChain.cabinetInstanceIds` хранят id звеньев (карт / блоков / 
  кабинетов; UUID не пересекаются). Javadoc полей обновить. Неизвестные id звеньев при чтении молча отбрасываются.
- Старые проекты читаются с пустыми списками (обычная Jackson-сериализация).

### 4.3. Сервер (`ledscheme-server`, не git)
`LibraryItemKind.RECEIVER_CARD`, `LibraryItemKind.POWER_SUPPLY` — обычные повторяемые виды (колонка `VARCHAR(32)`,
миграция не нужна), javadoc формы JSON; права MODERATOR — как у остальных видов (`CallerService`). Тест в
`LibraryControllerTests` по образцу `roomPlannerKinds…`. Деплой — скилл `deploy-server`, по разрешению.

## 5. Логика без Swing (клиент `service`, тестируется без UI)

- `ModuleNumbering.order(card, screen)` — модули карты в порядке номеров: обход прямоугольника модулей карты по
  шаблону экрана (клетки не своей карты и скрытые пропускаются) либо `manualPortOrder` (остальные — без номера).
- `ReceiverCardEditor` (по образцу `service.room.RoomEditor`): `assignManual(screen, rect, typeId)`,
  `assignAuto(screen, rect, typeId, w, h)`, правило замены D10 (отчёт: заменено, без карты), `remove`, `setHost`,
  `setManualOrder` / `resetOrder`, `setPattern`. Инвариант: модуль — максимум в одной карте.
- `PowerSupplyEditor`: `assignManual(screen, rect, typeId)`, `assignAuto(screen, rect, typeId)` (перебор w×h ≤
  `outputs`, проверки и выбор D18, запись `PowerAutoArea`), правило замены, `remove`, `setHost`,
  `onTypeChanged(type)` — пересчёт `powerAutoAreas` этого типа (D19). Инвариант: модуль — максимум в одном блоке.
- `PowerSupplyLayout.compute(screen)` — для каждого блока: выход «К» или шлейф под карту в его области (D19), номера
  шлейфов модулей (сначала карта, затем модули в порядке чтения), занятость, модули дальше кабеля.
- `ReceiverCardChecks` / `PowerSupplyChecks`: модули без карты / без блока; модулей больше выходов карты; шлейф
  длиннее; пиксели карты против `maxWidthPx/maxHeightPx/maxPixels`; блок перегружен; кабель длиннее.
- **`ChainUnits`** — единственный способ развернуть цепочку: `units(screen, mode)`, `unitOf(id)`, `cabinetsOf(unit)`,
  `pixels(unit)` (карта — сумма модулей), `watts(unit)` (блок — `ratedPowerW`), `anchor(unit)` (центр карты / место
  блока / центр кабинета). Для немодульного экрана — ровно прежние кабинеты (регрессия обязана быть нулевой).
- Целостность: удаление/замена карты или блока, скрытие модуля (выпадает из карты и блока), снятие флага модуля у
  типа, удаление экрана — звенья выпадают из цепочек; карта/блок без модулей удаляются. Снятие флага у типа —
  подтверждение «N карт, M блоков и их цепочки будут удалены».
- Каждая операция — одна запись отмены (`AppModel.runBatch`); `ScreenLogic.snapshot/restore` и `UndoEntry` несут
  карты, блоки, автообласти и шаблон (тест по образцу `UndoMaskPropsAndSchemaSheetsTest`).

## 6. Интерфейс (по `prototype-flow.html`)

### 6.1. «Сигнал» → «Приёмные карты»
Над холстом: «Снять карту», «Порядок вручную…», «Место карты…», флажок «шлейфы». Холст: модули серым, обычные кабинеты
тёмным, карты — полупрозрачной заливкой цвета «Приёмные карты», номера модулей (D14), плашка места (D11), оранжевые
модули без карты, пунктир авторазбиения. Под холстом: строка замен, подсказка, палитра нумерации (D7). Справа — D9, D16.
Замечания — полосой снизу (как `WarningsBar` Планнера). Код: `ui.receiver.ReceiverCardsView`, `ReceiverCardsCanvas`
(рендер чистый — им же рисуется экспорт «Карта подключения»), `NumberingPalette`, `CardAssignPanel`.

### 6.2. «Питание» → «Блоки питания»
Над холстом: «Снять блок», «Место блока…», флажок «кабели питания». Холст — D21; модули без блока оранжевые;
перегруз и длинные кабели — красным. Справа: «Тип блока питания» (строка типа: «8+К вых. · 300 Вт · 700 мм»), «Как
назначать» (D18, без полей Г×В — строка «Подобрано…»), «Блоки питания экрана». Код: `ui.receiver.PowerSuppliesView`,
`PowerSuppliesCanvas`, общий с 6.1 каркас вида.

### 6.3. «Расключение экрана» (оба этапа)
Инструменты и логика — существующие, звенья — из `ChainUnits`; отрисовка — D24 (сигнал), D25 (питание); правая панель —
D4; подсказка D26.

- **NovaLCT `.scr`**: карта = «кабинет» NovaLCT размером с прямоугольник её модулей в px, порядок на порту — порядок
  цепочки; разные размеры карт уже поддержаны (`ScreenBlock.cellSizes`, `ScreenLogic.complexReasons` — к картам).
  `.rcfgx` (порядок модулей в карте) не пишем. **Проверка загрузкой в NovaLCT обязательна** (`NOVALCT_EXPORT.md` §9).
- **«Карта подключения модулей»** — новая часть «Состава вывода»: картинка/PDF на экран (рендер `ReceiverCardsCanvas` в
  печатном стиле) + таблицы «карта → модель → место → номер → модуль (строка, столбец)» и «блок → место → шлейф →
  модуль / карта».
- **Спецификация**: приёмные карты и блоки питания по моделям (лист «Оборудование» сцены); сигнальные шлейфы — по числу
  модулей (с длиной `ribbonLengthMm`, если указана); кабели питания — по занятым выходам блоков.
- Вес и мощность экрана в прериге и транспорте — плюс карты и блоки (если заданы у типов).
- Общая схема: узел экрана не меняется; «гнёзда кабинетов» модульного экрана — по картам (сигнал) и блокам (питание).
- Без изменений: маски, канвас, Resolume/After Effects, форма экрана, конструктив.

## 10. Риски

- Перевод цепочек на `ChainUnits` затрагивает почти все этапы — отдельный трек, полный `mvn test`, сравнение
  экспорта до/после.
- `.scr` с картами разных размеров на порту не проверен загрузкой в NovaLCT.
- `.rcfgx` не генерируем: номера модулей техник выставляет в NovaLCT (Smart Settings / Construct Cabinet) — «Карта
  подключения» должна однозначно совпадать с тем, что он увидит.
- Старый клиент при пересохранении проекта потеряет карты и блоки (незнакомые поля), цепочки получат битые id —
  отбрасываются (4.2).
- Пересчёт автообластей (D19, D23) сбрасывает фазы блоков этих областей — пользователь должен видеть это в чек-листе /
  замечаниях.
