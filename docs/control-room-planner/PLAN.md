## 1. Что строим

**Планер пультовой** — отдельный инструмент (не часть схемы и не часть сцены):
из оборудования общей библиотеки собираются башни/стойки/стопки, мебель, мониторы
и станки, раскладываются на плане площадки FOH с трассами кабеля; размеры везде
в юнитах и сантиметрах; проверки; спецификация и список кофров к перевозке.

Что в прототипе (сверху вниз по экрану):

- Шапка: единицы «U / см / U + см», «Руководство», «Отменить», «Сбросить пример».
  Кнопки «Библиотека» и «Спецификация» выдвигают боковые панели (вариант
  «Фокус», выбранный пользователем).
- Полоса итогов: юниты, вес, нагрузка (кВт и А), «Пол станков» (габариты и м²).
- Вкладки «Стойки и башни» и «План пультовой», на каждой переключатель вида
  «Спереди / Сверху».
- Нижняя панель выбранного объекта (контекстные действия).
- Нижнее окошко «Замечания» (ошибки / предупреждения / к сведению).

## 3. Принятые решения и допущения

Решения пользователя (из диалога):

- Оборудование — **из существующих библиотек** (R4). Новую «параллельную»
  библиотеку не заводить.
- Ширины: добавить, по умолчанию 19″ (R5).
- Планер — **отдельный инструмент** (R6), а не вкладка схемы.
- Интерфейс — вариант «Фокус» (R8).
- 2026-10-23: окно планера — **как калькулятор транспорта**: `JDialog` с
  `ModalityType.MODELESS` (так сделан `VehicleCalculatorDialog`), пункт «Планер
  пультовой…» в том же меню рядом с «Калькулятор транспорта…» (A2 подтверждено).
- 2026-10-23: позиции без габаритов помечаются цветом, пользователь вводит их сам,
  затем механизм «предложить на сервер» (R25); админка правит габариты (R26);
  таблица габаритов собрана (R27). Вопрос Q4 закрыт.

Терминология: «**раскладка**» — одна сохранённая раскладка пультовой (башни, мебель,
станки и трассы на одной площадке). У **каждой сцены свой список раскладок, их может
быть несколько** (решение пользователя 2026-10-23). В прототипе и в ранних версиях
этого документа раскладка называлась «планом» — не путать с планом реализации.

Допущения автора плана (**подтвердить у пользователя до старта трека A**):

| № | Допущение | Альтернатива |
|---|---|---|
| A1 | **Решено пользователем 2026-10-23:** раскладки хранятся **в сцене** — `Scene.controlRoomLayouts` (список раскладок сцены), по образцу `Scene.schemaSheets`; у каждой сцены свой список, раскладок может быть несколько | (отвергнуто) список в `Project`; отдельный файл вне проекта |

## 4. Установленные факты о приложении (проверено по коду 2026-10-23)

- Окна-калькуляторы открываются из `MainMenuBar` (`videoTiming`, `vehicleCalc`),
  план пола — неблокирующий `JDialog` (`ui.FloorPlanDialog`, открывается из
  `SetupStagePanel`). Этапы (`MainFrame`): `SetupStagePanel`, `PowerStagePanel`,
  `SignalStagePanel`, `VisualizationStagePanel`, `OutputStagePanel`,
  `LibrariesStagePanel`.
- Данные сцены персистятся обычной Jackson-сериализацией без особого кода
  (`Scene.networkManagerPlan`, `Scene.vehicleLoadPlan`, `Project.vehicleCaseCounts*`);
  все места чтения JSON выключают `FAIL_ON_UNKNOWN_PROPERTIES` — старый клиент
  откроет файл с новыми полями, но при пересохранении потеряет их.
- Библиотека: `model.Library` держит локальные списки (`cabinetTypes`, `caseTypes`,
  `controllerTypes`, `networkDeviceTypes`, `equipmentPresets`, …) и «общие» копии
  (`shared*`), приходящие с сервера (`sync.LibrarySyncClient`,
  `AppModel.applyLibrarySyncItems`).
- **Физические размеры есть только у `CaseType`** (`lengthMm/widthMm/heightMm`,
  `weightKg`, `maxStackCount`). У `ControllerType`, `NetworkDeviceType`,
  `EquipmentPreset` — порты, производитель, категория, карты; **габаритов, веса и
  мощности нет**. Это главный пробел для R4.
- Обычные виды библиотеки (много строк) — настоящие классы из `ledscheme-model`
  (`CaseType`, `VehicleType`, …); у `STRUCTURE_FRAME` один вид с дискриминатором
  `kind` внутри payload — образец для мебели/станков/мониторов.
- Рецепт добавления вида — `ARCHITECTURE.md` §2: константа в `LibraryItemKind`
  (сервер) → Swing-панель в админке (`ledscheme-admin/.../admin/ui/library/`) →
  `case` в `AppModel.applyLibrarySyncItems` → экспорт/импорт
  (`ui.LibraryExportImportPanel`).
- **Предложения на сервер уже есть**: `ui.ProposeDialog` (модальный диалог,
  требует вход в аккаунт) → `sync.ProposalClient` → сервер (`Proposal`,
  `ProposalKind { NEW_ITEM, EDIT_EXISTING }`); модерация — `ui.ModerationDialog`
  (клиент, для модераторов) и `ProposalsPanel` в админке. `EDIT_EXISTING` отправляет
  правку уже общего элемента (`targetItemId`), без изменения локальной копии
  (черновик строится в `LibrariesStagePanel`). Новый вид библиотеки должен
  подключаться к этому же механизму.
- Общая библиотека на сервере сейчас (проверено публичным `GET /api/library/changes`):
  4 контроллера, 32 записи оборудования, 2 кофра, 6 кабинетов, нет сетевых устройств.
  Габариты есть только у кофров и кабинетов; таблица по остальному — в
  `EQUIPMENT_DIMENSIONS.md`.
- `AppModel.pushUndo()` — undo завязан на экран/цепи (`UndoEntry(screenSnapshot,
  powerChainsSnapshot, …)`); для планера **неприменим**, нужен собственный undo
  планера (снимки JSON плана, как в прототипе, глубина 60).
- Спецификации пишет `service.SpecXlsxWriter`; пакет документации и
  `exportSpecOnly` — в `OutputStagePanel`. Версии и теги — только по
  `VERSIONING.md`.
- Рабочее дерево в момент написания плана **грязное** (идёт работа v2.6.x:
  `AppModel`, `Screen`, `StructureCalc`, `SettingsManager` и др.). Реализацию вести
  в отдельной ветке/worktree (`claude/planner`), чужие незакоммиченные правки не
  трогать.

## 5. Библиотеки: как подключаем существующее оборудование

### 5.1. Физический блок `PhysicalSpec`

Новый небольшой класс в `ledscheme-model` (общий с админкой), необязательное поле
`physical` добавляется в `ControllerType`, `NetworkDeviceType`, `EquipmentPreset`.
Старые записи остаются валидными (`physical == null` → «нет габаритов»).

| Поле | Смысл |
|---|---|
| `formFactor` | `RACK` (в стойку), `LOOSE` (настольное/мелочь) |
| `rackUnits` | высота в U (для `RACK`) |
| `widthTwelfths` | доля ширины в двенадцатых: 12 = 19″, 6 = 1/2, 4 = 1/3, 3 = 1/4 (по умолчанию 12) |
| `widthMm`, `heightMm`, `depthMm` | габариты (для `RACK` ширина/высота считаются из U и доли, поле можно не заполнять) |
| `weightKg`, `powerW` | вес и мощность |

Константы: 1U = 44,45 мм; 19″ — ширина лицевой панели 482,6 мм (в прототипе 48,3 см).

### 5.2. Что показывает библиотека планера

Один список с фильтром по типу: `Кофры`, `В стойку`, `Мелочь`, `Мебель`, `Станки`,
`Мониторы` + поиск, как в прототипе. Источники:

| Тип планера | Источник | Примечание |
|---|---|---|
| Кофры | `CaseType` + два новых поля `rackUnits`, `innerDepthMm` (признак «рэк-кофр») | Кофры без рэка остаются для калькулятора транспорта; для планера наружные размеры берутся из `CaseType` (в прототипе приближённая формула — убрать) |
| В стойку / Мелочь | `ControllerType`, `NetworkDeviceType`, `EquipmentPreset` с `physical != null` + новый вид `ROOM_EQUIPMENT` | Новый вид нужен для того, чего нет в схеме: конвертеры, медиасерверы, ИБП, PDU, патч-панели, вентиляторы, полки |
| Мебель, Станки, Мониторы | новый вид `ROOM_FURNITURE` (дискриминатор `kind`: `FURNITURE` / `DECK` / `MONITOR`, образец — `STRUCTURE_FRAME`) | Станок: ширина, глубина, высота, вес. Монитор: диагональ, габариты с подставкой, вес, мощность |

Позиции без `physical` в списке **выделены цветом** (янтарная метка «нет габаритов»,
тот же цвет в списке выбранной позиции и на объектах плана); при добавлении в башню
предлагается ввести габариты (`PhysicalSpecDialog`). Подробности механизма — 5.4.

### 5.3. Что нужно по слоям

- **ledscheme-model**: `PhysicalSpec`, `RoomEquipmentType`, `RoomFurnitureType`,
  поля в `CaseType`; после правки — `mvn -DskipTests install` (золотое правило 3), для
  релизной CI — коммит и пуш в `ledscheme-model` по команде пользователя.
- **Сервер**: константы `ROOM_EQUIPMENT`, `ROOM_FURNITURE` в `LibraryItemKind`
  (`payload_json` сервер не парсит; остальной CRUD подхватывается сам); тест на
  дельту-синхронизацию нового вида. Деплой — только по скиллу `deploy-server` и с
  явного разрешения.
- **Админка**: формы `PhysicalSpec` в существующих диалогах контроллера/сетевого
  устройства/пресета; панели для двух новых видов в `admin/ui/library/`.
  Админка и клиент держат отдельные копии DTO — это осознанно (правило 4).
- **Клиент**: `Library.roomEquipmentTypes` + `shared…`, `roomFurnitureTypes` +
  `shared…`, `case` в `applyLibrarySyncItems`, строки в `LibraryExportImportPanel`,
  защита удаления (`libUsed` из прототипа → `isRoomItemReferenced`, как
  `isHoistTypeReferenced`: на id позиций ссылаются планы проекта).
- **Начальные данные**: список позиций из `planner.html` (`BASE`) — **условный
  пример**; реальные габариты серверных позиций — в `csv/*.csv`
  (проверяет пользователь, см. 5.4). Заливка через админку, не зашивать в код.

### 5.4. Позиции без габаритов: цвет, ввод пользователем, «предложить на сервер»

Решение пользователя 2026-10-23 (R25, R26).

1. **Метка.** В библиотеке планера позиция без `physical` (или без нужных полей:
   для `RACK` — юниты и глубина, для `LOOSE` — три размера) выделена янтарным цветом
   и пометкой «нет габаритов». Фильтр «только без габаритов». Такие позиции можно
   добавлять в башню (с условными размерами 1U × 30 см, помеченными как неточные),
   но в замечаниях появляется строка «К сведению: N позиций без габаритов».
2. **Ввод.** Кнопка «Указать габариты…» (`PhysicalSpecDialog`: форм-фактор, U, доля
   ширины, три размера, вес, мощность; подсказка с примерами, ссылка «Где найти»).
   Введённое сохраняется **локально как личное дополнение** к общей позиции —
   `UserProfile`/`SettingsManager` (карта `libraryItemId → PhysicalSpec`), общая
   запись на сервере не меняется. Личное дополнение действует во всех проектах
   пользователя; позиция больше не помечается цветом, но показывает знак «личное».
3. **Предложить на сервер.** Рядом кнопка «Предложить на сервер…»: открывает
   существующий `ProposeDialog` с `targetItemId = id общей позиции`
   (`EDIT_EXISTING`, как правка общего элемента), payload — позиция с заполненным
   `physical`. Для своих локальных позиций — `NEW_ITEM`. Требует вход в аккаунт (как
   сейчас). После принятия модератором и синхронизации личное дополнение, совпавшее с
   общим значением, удаляется автоматически.
4. **Модерация.** `ModerationDialog` (клиент) и `ProposalsPanel` (админка) показывают
   различие по физическому блоку (было → предлагается); принять можно как правку
   записи `CONTROLLER`/`EQUIPMENT`/`NETWORK_DEVICE`/`CASE`/`ROOM_*`.
5. **Админка правит габариты напрямую.** Формы существующих видов дополняются
   физическим блоком (`CONTROLLER`, `EQUIPMENT`, `NETWORK_DEVICE`, `CASE` — юниты и
   внутренняя глубина); новые виды `ROOM_EQUIPMENT`/`ROOM_FURNITURE` — свои панели.
   Всё сохраняется на сервере обычным upsert (`payload_json` сервер не парсит).
6. **Первичное наполнение — сделано (раздел 0).** Таблица габаритов серверной
   библиотеки лежит в `csv/` по блокам (R27). Кнопка «Импорт габаритов из CSV…» в
   админке сопоставляет строки по полному `id`, показывает предпросмотр, пишет только
   отмеченные в колонке `apply` строки, только после подтверждения и с резервной копией
   прежних payload'ов. **Загружать только проверенное**: значения достоверности B/C и
   записи «нужно уточнить модель» пользователь правит и проверяет сам. Загрузка на
   сервер — только его кнопкой (деплоя сервера не требует: общий CRUD принимает payload;
   сервер поле `physical` не разбирает, клиенты текущих версий его игнорируют).

## 6. Архитектура внедрения

Принцип репозитория: чистая логика в `service` без Swing (тестируется), рисование —
чистые рендереры (`SchemeRenderer`, `PixelGridRenderer`), панели тонкие.

### 6.1. Модель данных (клиент, `model`)

`Scene.controlRoomLayouts: List<ControlRoomLayout>` — **список раскладок у каждой
сцены, их может быть несколько** (решение 2026-10-23; образец — `Scene.schemaSheets` с
`SchemaSheetNameDialog` и выбором схемы в `ContextBar`). Активная раскладка — состояние
окна, не данные. У каждой сцены список свой.

Поведение списка:
- создать (пустая), переименовать, **дублировать** (полная копия с новыми id), удалить
  (с подтверждением; список может стать пустым);
- порядок задаётся `orderIndex`; при открытии окна выбирается последняя использованная
  (хранится в настройках пользователя) или первая;
- окно привязано к **текущей сцене** `AppModel` и перечитывает список при смене сцены
  (диалог неблокирующий); в заголовке показывается сцена;
- при дублировании или копировании сцены раскладки копируются вместе с ней (как схемы);
- раскладки сцены не зависят от её схем и экранов: связей в данных нет.

```
ControlRoomLayout id, name, orderIndex, room{widthCm, depthCm}, towers[], loose[],
                  furniture[], runs[]
RoomTower         id, tag, name, xCm, yCm, rotation, lay (null|ON|UNDER),
                  segments[]            // снизу вверх
RoomSegment       id, kind=CASE|STACK, caseTypeId?, items[]
RoomRackItem      id, libRef, u0?, c0? (в кофре)   // в стопке u0/c0 не используются
RoomLooseItem     id, libRef, mode=FREE|RUN|BOX, xCm?, yCm?, runId?, sCm?
RoomFurniture     id, libRef, xCm, yCm, rotation, onTop (станок-стол), overrides?
RoomRun           id, kind, name, color, points[[x,y]...]
LibRef            kind (CASE|CONTROLLER|NETWORK_DEVICE|EQUIPMENT|ROOM_EQUIPMENT|ROOM_FURNITURE), id
```

Все ссылки — по id библиотеки (`LibRef`), как `Screen.riggingHoistTypeId`.
`overrides` (из «Применить к этому объекту»): `name`, `widthCm`, `depthCm`,
`heightCm`, `weightKg`, `powerW`. Облачное сохранение, архивы и история проекта
получаются бесплатно (раскладки — часть сцены, значит и проекта). Админка
(`ProjectSummary`) читает `scene.*` из JSON напрямую: список остаётся плоским полем
сцены, существующие счётчики он не ломает.

## 7. Правила и константы, которые нужно перенести буквально

### 7.1. Привязки и пороги

| Что | Значение |
|---|---|
| 1U | 44,45 мм |
| Лицевая панель 19″ | 482,6 мм; в долях по двенадцатым |
| Привязка мелочи к трассе | ≤ 30 см |
| Шаг перетаскивания на плане | 5 см; станки — по сетке 50 см (по краям) |
| Привязка точек трассы к стене | ≤ 12 см |
| Подпись трассы | на первом отрезке, если он ≥ 60 см, иначе на самом длинном; поворот по сегменту; нижняя сторона текста к линии |
| Перетаскивание из библиотеки на башню | рэк-блок → в первый подходящий слот кофра, если нет места — в стопку сверху |

### 7.2. Вставка в кофр (`pushLayout`)

Границу вставки округлять до ближайшей границы ряда; если граница режет блок в тех
же колонках — сдвинуть к ближайшему краю этого блока. Блоки ниже сдвигать вниз
минимально (с учётом колонок, каскадом); если какой-то блок выходит за кофр —
вставка запрещена (красный предпросмотр). Прямое попадание в свободное место
сначала проверяется как обычная постановка.

### 7.3. Башня на столе и под ним

Хозяин башни — стол/станок под её центром (стол приоритетнее станка).

- Режим `lay` явно задан → используется он. Иначе: станок → «на»; стол →
  «на», если башня только из стопки без кофров или выше `стол − 5 см`, иначе «под».
- «На столе»: башня целиком в контуре стола (допуск 0,5 см); иначе ошибка.
  Тяжелее 40 кг — предупреждение.
- «Под столом»: высота башни ≤ высота стола − 5 см; иначе ошибка. Под станком: ≤
  высота станка − 8 см.
- Башня, частично залезающая на стол без заданного режима, — ошибка с подсказкой.
- Основание башни на виде спереди: «на» → уровень пола станка под центром + высота
  стола; «под» → уровень пола станка под центром, а под станком — 0.
- Стулья пересекаться с башнями не могут (ошибка); мониторы с башнями/столами —
  могут.

### 7.4. Станки

- Станок-стол (`onTop`): основание = максимальная высота нижних станков под его
  центром; нижние станки друг с другом и станок-стол со станком-столом при
  пересечении — ошибка; станок-стол и нижний — нет.
- Площадь и габариты «Пол станков» — только по нижнему ряду; счётчик штук — все.
- «Висит в воздухе» (ошибка): угол опоры объекта (отступ 0,5 см, 4 угла и центр) вне
  станков; опора на станках разной высоты; станок-стол без станка под любым углом.
  Для мониторов — предупреждение, не ошибка. Башня в режиме «под» из проверки
  исключается.
- Линия глаз: 120 см от пола станка под стулом; если стулья на станках разной высоты
  — отдельная линия у каждой группы; нет стульев — от самого высокого станка.

### 7.5. Перетаскивание на виде спереди (`elevSnap`)

Опоры: для станка — нижние станки; для башни — станки и столы; для монитора — столы,
башни, станки; для остальной мебели — станки. Кандидат — самая высокая опора,
чья верхняя плоскость ≤ базовая высота + 25 см и по `x` под центром. Если базовая
высота ≥ верх опоры − 15 см — поставить сверху (по `y` прижать к опоре, станки по
сетке); для башни на столе — режим «на». Иначе для башни: если под столом и по `y`
уже пересекается со столом и помещается — режим «под». Иначе режим сбрасывается.
Станок, добавленный на виде спереди кнопкой «+» или перетаскиванием выше пола,
ставится сверху на станки пола (`findDeckOnSpot`). Из библиотеки на вид спереди
можно бросать станки, мебель и мониторы; остальное — сообщение с подсказкой.

### 7.6. Замечания (тексты — буквально из прототипа)

| Уровень | Условие |
|---|---|
| Ошибка | объект вне площадки; пересечение башни/мебели/станков; глубина блока больше кофра; башня не помещается под столом/станком или целиком на столе; частичное пересечение со столом без режима; «висит в воздухе» (три случая) |
| Предупреждение | до задней крышки < 5 см; тяжёлое (≥ 15 кг) в верхней половине башни; башня выше 1,5 м; нагрузка > 3680 Вт (16 А); башня на столе тяжелее 40 кг; монитор у края станка |
| К сведению | пустая башня; мелочь «без привязки» (количество) |

Нагрузка: 230 В; единицы замечаний — кликабельные (выделяют объект).

### 7.7. Кейс мелочёвки

Объём предметов × 1,6 против полезного объёма кейса × 0,8; кандидаты
35×25×15, 45×32×20, 60×40×25, 80×50×30 см; больше самого большого — сообщение «разбейте
на два». В приложении кандидаты берутся из `CaseType` с признаком «мелочёвка» (A: если
такого нет — оставить зашитый список).

## 9. Тесты: что переносим из проверок прототипа

Прототип проверялся автоматическим прогоном (jsdom) и вручную. В JUnit переносим как
сценарии на фикстуре «пример проекта» из `planner.html`:

1. Итоги примера: 3 башни, 22/24U; пол станков 7 × 1,5 м, 9 станков (8 нижних + 1 станок-стол).
2. Единственное замечание примера — «до задней крышки 0 см» у медиасервера.
3. Вставка в кофр: `LED-процессор` на ряды 0, 2, `LED-контроллер` 4, `Блок вентиляторов` 5; вставить
   1U на границу 2 → ряды 0, 2 (новый), 3, 5, 6.
4. Слои: вынос кофра в новую башню; вставка кофра между слоями; «+ снизу» ставит слой на индекс 0.
5. Стопка: порядок снизу вверх, вставка по позиции, перенос между сегментами.
6. Башня C (стопка) перетащена на стол: основание 115 см, режим «на», пересечения нет.
7. Станок, добавленный на виде спереди: `onTop`; два станка → оба `onTop`, нижних 8.
8. «В воздухе»: стол сдвинут на край ряда станков → ошибка, `air`; станок-стол без опоры → ошибка.
9. Трасса: рисование 3 точек → трасса добавлена, 2 середины, 3 вершины; разворот меняет
   `s` мелочи на `len − s`; удаление переводит мелочь в «свободно» в той же точке.
10. Пресет мебели: библиотека +1, объект ссылается на новую позицию; удаление используемой позиции
    блокируется.
11. Подпись трассы: первый отрезок ≥ 60 см, угол в диапазоне [−90°, 90°).
12. Линия глаз: 160 см от земли при станках 40 см; без станков — 120.
13. Единицы: `U`, `см`, `U + см` для всех видов позиций.
14. Раскладки сцены: у сцены можно завести несколько, переименовать, дублировать, удалить; у другой
    сцены список свой; при дублировании сцены раскладки копируются с новыми id.
15. Миграция: проект без `Scene.controlRoomLayouts` открывается, после сохранения поле пустое/отсутствует;
    старый клиент открывает новый файл (тест на `FAIL_ON_UNKNOWN_PROPERTIES`).

Плюс GUI-дымовой тест окна (пропускается в headless) и ручная приёмка по таблице раздела 2
(живая проверка через `test-build`).
