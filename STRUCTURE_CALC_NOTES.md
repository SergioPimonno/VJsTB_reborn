# Расчёт наземного конструктива (`service.StructureCalc`) — статус и источники

Реализовано 2026-08-11, Phase 1 из согласованного с пользователем плана (см. секцию
«Явно отложено» ниже про Phase 2/3). Этот файл — то, что план требовал зафиксировать
для других агентов: что сделано, на чём основана методика, что взято ТОЧНО из реального
оборудования пользователя, а что — общая инженерная оценка по открытым источникам.

## Что реализовано

- `model.StructureFrameType` (`ledscheme-model`) — один класс на 4 вида элемента
  конструктива через дискриминатор `kind` (`FRAME`/`SHORT_FRAME`/`CUP`/
  `BALLAST_CONTAINER`), а не 4 отдельных класса — та же экономия, что у `Screen` (поля
  под конкретный способ монтажа, не подклассы). Общая библиотека, вид
  `LibraryItemKind.STRUCTURE_FRAME` на сервере, редактируется через
  `ledscheme-admin` (`StructureFrameTypeFormPanel`) — рецепт (секция 3 главного
  `CLAUDE.md`) применён третий раз в этой сессии (после `INTERACTIVE_SCENARIOS`/
  `VERSION_MANIFEST`/`HOIST`), без отклонений.
- `Screen` — 12 новых полей `structureXxx` (высота/шаг башен, число башен/сегментов
  рамы на башню/рядов обвязки — каждое авторасчитанное ДЕФОЛТ-значение, прямо
  редактируемое пользователем; 4 FK на библиотеку — рама/короткая рама/стакан/балласт;
  расчётная скорость ветра, nullable; заметки), осмысленны только при
  `mountType == STRUCTURE`, тем же принципом, что `riggingXxx` — для RIGGED.
- `service.StructureCalc` — `suggestTowerCount`/`suggestVerticalFramesPerTower`/
  `suggestHorizontalBraceRows` (стартовые предложения) + `compute` (итоговый BOM:
  число вертикальных/горизонтальных/базовых рам, стаканов, болтов, требуемый балласт
  и число контейнеров, предупреждение о высоте >5м).
- `AppModel.updateScreenStructure` — персистит все поля одним вызовом (как
  `updateScreenMount`), плюс полный CRUD+синк личной/общей библиотеки
  (`getStructureFrameTypes`/`add/update/deleteStructureFrameType`,
  `applyLibrarySyncItems`/`applyDeletion` case `"STRUCTURE_FRAME"`) — **защищённое**
  удаление (`isStructureFrameTypeReferenced`), т.к. `Screen` хранит РЕАЛЬНЫЕ FK на эти
  записи (как `HOIST`/`CABINET`, не как `CABLE`/`INTERFACE`), причём сразу по ЧЕТЫРЁМ
  полям (рама/короткая рама/стакан/балласт ссылаются в ОДНУ библиотеку).
- `ui/stage/SetupStagePanel` — новый блок «Наземный конструктив» в «Прериг сцены» (та
  же секция, что и rigging-поля, всегда видимый, как rigging-поля для RIGGED — кнопка
  расчёта активна только при `mountType == STRUCTURE`, тот же принцип, что
  `calcRiggingBtn`): высота/шаг башен, число башен/сегментов/рядов обвязки, чекбокс
  базовой рамы, 4 комбобокса библиотеки (с пустым «Не выбрано»), поле скорости ветра,
  заметки, кнопка «Рассчитать конструктив» → `JOptionPane` со сводкой + предупреждение
  о высоте.
- `StructureCalcTest` (7 тестов) + 3 теста синка в `AppModelTest` (добавление,
  перенос ссылки при "продвижении" личной записи, защищённое удаление при живой
  ссылке экрана — по образцу тестов `HOIST`).

## Источники хозяйства: реальное оборудование пользователя vs общая оценка

**ТОЧНО, не оценка** — пользователь дал прямые числа по своему реальному конструктиву
(3D-модель, скриншоты предоставлены в сессии):
- Элементы: **рама** (950×500×51 мм, ставится вертикально, формирует высоту башни),
  **короткая рама** (859×500×51 мм — горизонтальная обвязка между башнями, ИЛИ плоская
  опорная база на земле, ИЛИ доборный элемент по ширине, чтобы конструктив не торчал за
  краем экрана), **стакан** (соединитель на каждом стыке рам, болт в его 3D-модели не
  показан).
- Формулы: **2 стакана на каждый стык 2 вертикальных рам** (в `StructureCalc` применено
  одинаково и к горизонтальным/базовым стыкам — см. «Допущения» ниже, это единственное
  реальное расширение исходной формулы пользователя). **Болты = число рам × 1.5**
  (применено к сумме ВСЕХ рам — вертикальных+горизонтальных+базовых).
- Балласт — контейнеры с песком, вес берётся из библиотеки (`StructureFrameType.kind ==
  BALLAST_CONTAINER`), не хардкодится.

**СНЯТО В Phase 2.1 (2026-08-14) — см. секцию ниже.** Весь этот подраздел (формула
ветра/балласта) описывает УЖЕ УДАЛЁННУЮ логику — оставлен как есть только для истории
(почему изначально считали именно так), не как действующая документация. Действующее
правило балласта — «требуемый вес ≈ вес экрана», см. «Phase 2.1 — объёмная башня»
внизу файла. Не используй формулу ниже как источник истины.

**ОБЩАЯ ОЦЕНКА, требует независимой инженерной перепроверки** (самое слабое место
расчёта, как и у `RiggingCalc`) — ИСТОРИЧЕСКИ, до Phase 2.1:
- Формула ветровой нагрузки/балласта — динамическое давление ветра
  (`0.5·ρ_воздуха·v²`, ρ=1.225 кг/м³) × коэффициент лобового сопротивления (Cd=1.2,
  типовое значение для плоского щита из ASCE-7-подобных источников, НЕ измерено для
  конкретной модели экрана) × площадь экрана → сила ветра → опрокидывающий момент
  (плечо = половина высоты башни, упрощение) → требуемый балласт через footprint башни
  (используется ШАГ БАШЕН как заменитель ширины опорной базы — у системы пользователя
  нет отдельной "H-базы" с разнесёнными по глубине ногами, в отличие от западных
  touring-систем box truss/mono-truss, которые изначально рассматривались и оказались
  НЕ тем оборудованием, см. ниже) × запас 1.5 (у сырой формулы источника запаса нет
  вовсе).
- Источники (веб-поиск при разработке модели):
  - [How to Calculate Wind Load for Outdoor LED Screens — SightLED](https://sightled.com/outdoor-led-screen-load-calculation-and-structural-safety-design/)
  - [Load Calculation: Engineering Safe Truss Structures For LED Walls — Doremi](https://www.doremievent.com/led-wall-load-calculation/)
  - [Expert Answers on Truss Ballast — JustAnswer](https://www.justanswer.com/structural-engineering/6im5z-engineering-question-i-trussing-towers-upto.html)
  - [James Thomas Engineering — Ground level LED Screen support](https://www.jthomaseng.com/about-jte/news/ground-level-led-screen-support)

**Заход по общей отраслевой терминологии (box truss/mono-truss/H-база с разнесёнными
ногами, ANSI E1.21) ОКАЗАЛСЯ НЕ ТЕМ ОБОРУДОВАНИЕМ** — пользователь показал скриншоты
реального 3D-конструктива (плоские ladder-frame панели, не круглая труба и не box
truss), это единственная причина, по которой формула ветра/балласта построена на
общей инженерной логике (момент/footprint), а НЕ на конкретной паспортной методике
производителя этой системы — такой методики не было под рукой. Если появится
паспортный расчёт производителя рамы — заменить эту формулу на него, не подгонять
общую логику дальше.

## Phase 3 — 3D-превью (`ui.Structure3DPanel`, 2026-08-13)

3D-вид посчитанного конструктива — кнопка «Показать 3D» внутри блока «Наземный
конструктив» (`ui.stage.SetupStagePanel`, видна вместе со всем блоком только при
`mountType == STRUCTURE`, см. правку «ненужное убирать» из предыдущей сессии). Изначально
(2026-08-13, первый заход) был read-only превью — в тот же день, после того как
пользователь протестировал его и запросил Phase 2, стал интерактивным редактором прямо
в этой же панели (см. секцию «Phase 2» ниже) — отдельного 2D grid-редактора по типу
`ui.ShapeEditorPanel`, изначально предполагавшегося для Phase 2, решили не делать —
пользователь явно выбрал редактирование кликом прямо в 3D.

**Библиотека — JOGL, не LWJGL** (согласовано с пользователем): `GLJPanel` рендерит в
offscreen-буфер и встраивается в Swing-layout как обычный компонент — так же, как уже
работают `SceneCanvasPanel`/`ShapeEditorPanel` внутри тех же `JSplitPane`/`JScrollPane`.
LWJGL 3 открывает собственное нативное GLFW-окно без штатной Swing-интеграции — не
вписывался бы в архитектуру этого приложения без обходных путей.

**Конвейер — фиксированный GL2** (`glBegin`/`glTranslatef`/матричный стек), не
GL3+/шейдеры — рисуются несколько десятков коробок для предпросмотра, не
производительная сцена, ради которой стоило бы городить VBO/шейдеры/ручную математику
матриц. Камера — простая орбита (левая кнопка + перетаскивание = yaw/pitch вокруг
центра сцены, колесо = зум), без панорамирования (сцена всегда центрирована — этого
достаточно для sanity-check, панорамирование можно добавить позже, если понадобится).

**Только Windows-нативы упакованы** (`pom.xml`: `natives-windows-amd64` classifier для
`gluegen-rt`/`jogl-all`) — согласовано с пользователем как "Windows first", т.к. CI-сборки
для macOS/Linux (`CLAUDE.md` секция 4, `.github/workflows/release-macos.yml`/
`release-linux.yml`) собирают и тестируют этот проект НЕ на этой машине. Конструктор
`Structure3DPanel` ловит `Throwable` вокруг создания `GLProfile`/`GLCapabilities`/
`GLJPanel` и показывает `JLabel` "3D недоступно на этой системе" вместо падения —
поэтому jar собирается и работает на macOS/Linux как обычно, просто кнопка «Показать
3D» покажет это сообщение вместо картинки. **Если понадобится реальная поддержка
других платформ** — добавить в `pom.xml` classifier'ы `natives-macosx-universal` и
`natives-linux-amd64` (те же `gluegen-rt`/`jogl-all:2.6.0`, координаты подтверждены на
Maven Central при подключении Windows-набора) и проверить, что `release-macos.yml`/
`release-linux.yml` реально прогоняют кнопку 3D хотя бы дымовым тестом — сейчас CI
этого не делает.

**Геометрия — визуальное приближение, не точный CAD** (см. class-javadoc
`Structure3DPanel` за деталями): башни используют реальные габариты выбранного в
библиотеке `StructureFrameType` (рама/короткая рама через `heightMm`/`widthMm`/
`depthMm`, с фолбэком на 950×500×51, если тип не выбран — тот же фолбэк-принцип, что
у `StructureCalc.suggestVerticalFramesPerTower`), но горизонтальная обвязка
растягивается на фактический зазор между башнями (а не буквально на паспортную длину
короткой рамы 859мм — иначе картинка не масштабировалась бы вместе с произвольным
шагом башен, который вводит пользователь), а базовая плита кладётся из габаритов
короткой рамы, положенной плашмя (её "859" трактуется как глубина опоры вперёд-назад).
Экран сцены рисуется отдельной плоскостью для масштаба (реальные `cols×cabW`/
`rows×cabH`).

Прямых тестов на сам GL render loop нет — тот же принцип, что у `SceneCanvasPanel`/
`ShapeEditorPanel` (ни у одного из них тоже нет прямых юнит-тестов, стабильная
конвенция проекта для Swing/GL рисующих компонентов). Но picking-математика Phase 2
(ниже) вынесена в чистый Java-класс без GL-типов именно ради тестируемости — см.
`StructurePickMathTest`.

## Phase 2 — интерактивное редактирование прямо в 3D (2026-08-13)

**Геометрия описанная ниже (плоская башня — одна колонна рам, горизонтальная обвязка
между СОСЕДНИМИ башнями) заменена в Phase 2.1 на объёмную** (см. секцию внизу файла) —
`StructureBraceCell` удалён, `structureBaseFrameTowers`→`structureBaseFrameCells`
получил третье измерение. Раздел оставлен для истории (откуда взялся паттерн
"список ячеек + hidden", почему merge-not-overwrite и picking устроены именно так) —
эти механизмы Phase 2.1 не менял, только СХЕМУ данных поверх них.

В тот же день, сразу после Phase 3, пользователь протестировал read-only превью и
явно запросил продолжение — по итогам `AskUserQuestion` выбрал: (1) полностью
произвольную поячеечную сетку (не просто точечные исключения поверх формулы), (2)
редактирование КЛИКОМ ПРЯМО В 3D-ПАНЕЛИ, не отдельным 2D grid-редактором.

**Источник истины — списки ячеек, не числа-формулы.** `structureTowerCount`/
`structureVerticalFramesPerTower`/`structureHorizontalBraceRows` на `Screen` остались
(спиннеры в `SetupStagePanel` не изменились), но это теперь только НОМИНАЛЬНЫЕ границы
сетки, которые «Рассчитать конструктив» использует для генерации, а РЕАЛЬНО
существующее железо — три новых списка на `Screen`:
- `structureFrameCells: List<StructureFrameCell>` (`ledscheme-model`) —
  `towerIndex`/`segmentIndex`, один вертикальный сегмент рамы.
- `structureBraceCells: List<StructureBraceCell>` — `gapIndex`/`rowIndex`, один ряд
  горизонтальной обвязки между башнями `gapIndex` и `gapIndex+1`.
- `structureBaseFrameCells: List<StructureBaseFrameCell>` — `towerIndex`, базовая рама
  одной башни.

Все три несут `boolean hidden` — точь-в-точь `CabinetInstance.isHidden()` для формы
экрана: клик по существующей ячейке в 3D **не удаляет запись из списка, а прячет её**
(`hidden=true`). Это критично для следующего пункта.

**«Рассчитать конструктив» мержит, а не перезаписывает** —
`service.ScreenLogic.regenerateStructureCells` (вызывается из
`AppModel.updateScreenStructure`) работает ТЕМ ЖЕ приёмом, что `resizeGrid` для
`CabinetInstance`: позиции внутри новых номинальных границ сохраняют свою запись
КАК ЕСТЬ (включая `hidden`), позиции без записи внутри границ получают новую видимую
запись, записи за пределами границ выбрасываются целиком. Если бы `hidden`-ячейка
просто отсутствовала в списке (как в первой, неверной версии этого кода, до фикса в
этой же сессии — баг-репорт по собственному тесту
`recalculatingStructurePreservesManualRemovalsWithinNewBounds`), пересчёт не мог бы
отличить «убрано руками» от «ещё не встречалось» и молча возвращал бы убранное.

**`structureIncludeBaseFrame` — теперь чистый вкл/выкл-фильтр показа/подсчёта, не
источник данных.** Список `structureBaseFrameCells` всегда полностью населён (по одной
записи на башню в номинальных границах, генерируется независимо от чекбокса);
`StructureCalc.compute`/`ui.Structure3DPanel` просто не показывают/не считают базовые
рамы вовсе, если чекбокс выключен — индивидуальные `hidden`-флаги при этом НЕ
стираются и восстанавливаются как были при повторном включении чекбокса.

**`StructureCalc.compute`** читает эти списки напрямую (`.filter(!isHidden)`), а не
`towerCount × verticalFramesPerTower`. Стыки (используются для `cupCount`) считаются
по РЕАЛЬНОЙ смежности: для вертикальных рам — группировка по башне, стык есть только
если ОБА соседних `segmentIndex` присутствуют и видимы в одной башне (убранный из
середины сегмент физически рвёт оба соседних стыка, не один) — горизонтальная
обвязка/базовые рамы остаются в отношении «1 видимый элемент = 1 стык», как и в
исходной формуле, просто по реальному счёту, а не произведению.

**Picking — ручной CPU-side raycast, не `GL_SELECT`/`gluUnProject`** (тем нужен живой
GL-контекст на потоке рендера — их нельзя дёрнуть из обычного обработчика клика мышью
или из теста). Вся математика — в `service.StructurePickMath` (сознательно без
JOGL/GL-типов): `cameraRay(eye, center, up, fovDeg, aspect, pixelX, pixelY, viewportW,
viewportH)` восстанавливает луч через пиксель для той же камеры, что `gluLookAt`/
`gluPerspective` в `Structure3DPanel` (fov/aspect — единственное, что влияет на
НАПРАВЛЕНИЕ луча, near/far не нужны), `intersectAabb` — стандартный slab-тест. Камера
(`eye`/`center`) и геометрия конструктива (`frameW`/`frameH`/`frameD`/`spacing`/
`towerZ`) вынесены в общие приватные методы `Structure3DPanel.computeCamera()`/
`computeGeometry()`, используемые И рендером, И picking'ом — иначе клик целился бы не
туда, куда только что отрисовался кадр.

**Клик vs. орбита-перетаскивание**: левая кнопка мыши уже занята вращением камеры
(перетаскивание) — обработчик мыши в `Structure3DPanel` считает суммарное смещение
между `mousePressed`/`mouseReleased`, и если оно ≤ `CLICK_MOVE_THRESHOLD_PX` (4px),
трактует это как «чистый клик» и запускает picking; иначе — это было вращение, ничего
не трогаем. Раньше «чистый клик без перетаскивания» вообще ничего не делал, поэтому
переиспользовать его для picking'а безопасно (новых модификаторов типа Ctrl не нужно).
**Устарело, см. Round 24** — Ctrl всё же понадобился, не для самого disambiguation'а клика
от орбиты (та часть не изменилась), а как отдельный осознанный гейт на ДОБАВЛЕНИЕ, из-за
БАГА в тай-брейке этого же raycast'а (не просто "на всякий случай" — см. Round 24).

**«Призрачные» (ghost) ячейки** — тускло очерченные контуром (не заливкой) места, где
можно добавить недостающий элемент: диапазон на один ряд/башню ШИРЕ, чем текущая
номинальная сетка и текущий максимум реально существующих ячеек (`frameEnvelope` в
`Structure3DPanel`) — именно так реализовано «добавить лишнюю башню сбоку»: кликаешь
по крайнему призрачному контуру, появляется новая видимая ячейка, а диапазон призраков
сдвигается ещё на один шаг дальше.

**Экран из отдельных кабинетов + маска на лицевой грани** — этой же сессией, ДО
запроса Phase 2, экран в 3D-панели уже был переделан рисовать реальную сетку
`CabinetInstance` (с учётом скрытых/переопределённых по типу ячеек — форма экрана из
`ShapeEditorPanel`) вместо одной сплошной плиты, а лицевая грань каждого кабинета
красится реальной маской экрана (`Screen#getBackground`) через новый `boxFrontColored`
(лицевая грань — цвет маски, остальные 5 граней — нейтральный цвет корпуса).

## Ограничение по высоте

`StructureCalc.MAX_SAFE_TOWER_HEIGHT_MM = 5000` — башни выше этого предела считаются
некорректной практикой без отдельного инженерного расчёта (прямое указание
пользователя: "конструктив выше 5м не строим"). Реализовано как ПРЕДУПРЕЖДЕНИЕ
(`Result.exceedsSafeHeightWarning()`, `JOptionPane.WARNING_MESSAGE`), не жёсткий блок
ввода — тот же принцип, что у `RiggingCalc`/`overCapacity` (показать риск явно, не
мешать пользователю, у которого может быть реальное инженерное обоснование для
исключения). Phase 2.1 добавила ВТОРОЕ, независимое предупреждение —
`Result.exceedsScreenHeightWarning()` — см. ниже.

## Phase 2.1 — объёмная башня (2026-08-14)

Пользователь протестировал Phase 2 (плоская башня — одна колонна рам) и объяснил на
реальных фото + эскизе (согласован в чате перед реализацией), что настоящая башня
ОБЪЁМНАЯ — сборка из горизонтально И вертикально ориентированных рам одного и того же
модульного семейства, а не одна плоскость. Три ключевых факта от пользователя,
определяющих геометрию:
- Вертикальные рамы стоят в ДВА параллельных ряда: передний — прямо у экрана, задний —
  на глубину ОДНОЙ короткой рамы (~0.5м) позади. Вместе они формируют "ядро" башни.
- Горизонтальные рамы-**перемычки** соединяют передний и задний ряд ВНУТРИ одной башни
  (не между соседними башнями — эта роль полностью упразднена, см. ниже) каждые ~1.5м
  высоты — нужны, чтобы залезать на них, и для жёсткости; у рам под это есть перегородка
  посредине.
- **Базовая рама может выноситься назад** дополнительными секциями (каждая — ширина
  короткой рамы) сверх обязательного ядра — чисто ради увеличения площади опоры под
  балласт (рычаг), без вертикальных рам над этими секциями.

### Модель данных — три независимые оси вместо двух

`StructureFrameCell` (`ledscheme-model`) получил третье поле `row` (0 = передний ряд, у
экрана; 1 = задний ряд) — один и тот же класс, что в Phase 2, просто ключ стал тройкой
(`towerIndex`, `row`, `segmentIndex`) вместо пары.

`StructureBraceCell` (горизонтальная обвязка МЕЖДУ соседними башнями) **удалён
целиком** — в описании и фото пользователя горизонтальные рамы никогда не соединяют
разные башни, только перед/зад ОДНОЙ башни (перемычка) или лежат плашмя (база). Заменён
новым `StructurePeremychkaCell { towerIndex; levelIndex; hidden }` — один коннектор на
(башню, уровень).

`StructureBaseFrameCell` получил `sectionIndex` (0 = ядро под объёмом башни, всегда
рассматривается при генерации; 1+ = секции выноса под балласт, считая от ядра назад).

`Screen`: `structureHorizontalBraceRows` и `structureDesignWindSpeedMs` удалены;
добавлены `structurePeremychkaLevels` (номинальная граница сетки перемычек, та же роль,
что `structureVerticalFramesPerTower`), `structureExtendedBaseSections` (номинальное
число ДОПОЛНИТЕЛЬНЫХ секций базы сверх ядра) и `structureScreenElevationMm` (высота
нижнего края экрана над землёй, 0 = на земле).

**Интервал перемычек — глобальная настройка Персонализации, не поле экрана.**
(**СНЯТО В Phase 2.2, см. секцию внизу файла** — интервал больше НЕ настройка в мм,
это коэффициент 1.5 от реальной высоты рамы, `UserProfile.structurePeremychkaIntervalMm`
удалён целиком. Абзац оставлен для истории, не как действующая документация.)
Пользователь явно попросил не хранить его на `Screen`: `UserProfile
.structurePeremychkaIntervalMm` (по умолчанию 1500мм), редактируется в новой группе
«Наземный конструктив» диалога `PreferencesDialog` (тот же паттерн, что `powerUnitKw` —
см. `SettingsManager.setStructurePeremychkaIntervalMm`). `StructureCalc
.suggestPeremychkaLevels(towerHeightMm, intervalMm)` использует его только как
СТАРТОВОЕ предложение количества уровней при «Рассчитать конструктив» — сама
расстановка конкретных перемычек после этого редактируется поячеечно кликом в 3D, как
и всё остальное железо (см. Phase 2 выше про merge-not-overwrite/picking — эти
механизмы не изменились, только схема данных поверх них).

### Балласт — «вес ≈ вес экрана», не ветровая физика

По прямому указанию пользователя вся ветровая формула (`AIR_DENSITY_KG_M3`,
`DRAG_COEFFICIENT`, `BALLAST_SAFETY_FACTOR`, момент/footprint) удалена из
`StructureCalc.compute` — избыточна для этого инструмента. Новое правило: требуемый вес
балласта **≈ суммарный вес отгружаемого экрана** (`ScreenLogic.stats(screen, type,
workspace).totalWeightKg()` — уже существующий помощник, не переизобретён), без запаса
поверх. Число контейнеров — `ceil(requiredBallastKg / containerWeightKg)`, как раньше.
Поле «Расчётная скорость ветра» и весь связанный UI в `SetupStagePanel` удалены.

### Проверка высоты — второе независимое предупреждение

`Result.exceedsScreenHeightWarning()` — `towerHeightMm >= высота_экрана_рядов×heightMm`.
НЕ учитывает `structureScreenElevationMm` (по прямому указанию пользователя — сравнение
именно с СОБСТВЕННОЙ высотой экрана, не с положением над землёй). Тот же
непринудительный `JOptionPane.WARNING_MESSAGE`, что у `exceedsSafeHeightWarning` — оба
предупреждения независимы и могут сработать одновременно.

### Рендер (`ui.Structure3DPanel`)

Геометрия: `frontZ`/`backZ` — Z-позиции переднего/заднего ряда (разнесены на
`sectionDepthMm`, читается из ширины короткой рамы, фолбэк 500мм). Секции базы
продолжают шагать в ту же сторону (`backZ`, `backZ − sectionDepthMm`, …) дальше от
экрана. Перемычки рисуются как сплошной блок между `frontZ` и `backZ` на высоте
`(levelIndex+1) × интервал`. Стаканы (`drawCups`) расставлены на трёх типах реальных
стыков: вертикальные (по рядам независимо — тот же принцип смежности, что в
`StructureCalc.compute`), перемычка↔стойка, база↔стойка/секция↔секция.

Экран рисуется приподнятым на `structureScreenElevationMm` над землёй (сама земля/база
башен остаются на истинном нуле) — визуально виден зазор, если экран поднят на
подиум/платформу, которую конструктив как таковой не рисует.

`Structure3DPanel` теперь принимает `SettingsManager` вторым параметром (нужен для
чтения интервала перемычек при построении геометрии) — `Structure3DDialog` и
`SetupStagePanel` прокидывают его насквозь. (**СНЯТО В Phase 2.2** — `SettingsManager`
больше не нужен здесь, интервал считается от высоты рамы, конструктор снова
однопараметровый `Structure3DPanel(AppModel model)`.)

### Тесты

`StructureCalcTest` — переписан: `suggestPeremychkaLevels`/`suggestExtendedBaseSections`
(новые), `exceedsScreenHeightWarning` (новый), баллистический расчёт заменён на
screen-weight-based версию, adjacency-тест расширен на независимость двух рядов.
`AppModelTest` — toggle/regenerate тесты расширены на третье измерение
(`row`/`sectionIndex`), обвязочный toggle заменён на `toggleStructurePeremychkaCell`.

## Phase 2.2 — правки после первого реального теста (2026-08-14)

Пользователь протестировал Phase 2.1 (объёмная башня) и прислал 4 конкретные правки
по скриншоту + фото башен. Ключевая формулировка, определившая ВСЮ архитектуру этого
захода: **"мы делаем по факту конструктор с предварительным аппаратно рассчитанным
шаблоном"** — «Рассчитать конструктив» даёт только СТАРТОВЫЙ шаблон, конкретные
элементы (в т.ч. ИХ ТИП, не только наличие) должны быть свободно доредактируемы
пользователем, а не жёстко выведены формулой.

### 1. Интервал перемычек — коэффициент от высоты рамы, не мм-константа

Пользователем прямо: *"если интервал в 1.5м не сходится, убирай его чёткое значение,
оставляй только расчёт перемычек с интервалом в 1.5 рамы"* — у рам есть перегородка
ровно посередине для крепления перемычки, поэтому "1.5м" на самом деле "рама + пол-рамы"
(стык двух рам, потом середина следующей). `UserProfile.structurePeremychkaIntervalMm` /
`SettingsManager.setStructurePeremychkaIntervalMm` / группа «Наземный конструктив» в
`PreferencesDialog` — **удалены целиком**. Новый `StructureCalc.peremychkaIntervalMm
(frameHeightMm) = frameHeightMm × 1.5` (константа `PEREMYCHKA_INTERVAL_FRAME_MULTIPLE`),
`suggestPeremychkaLevels(towerHeightMm, frameHeightMm)` теперь принимает высоту рамы
вторым параметром вместо готового интервала в мм. `Structure3DPanel.computeGeometry`
берёт интервал из `StructureCalc.peremychkaIntervalMm(frameH)` — `SettingsManager`
конструктору панели больше не нужен (`Structure3DPanel(AppModel model)`,
`Structure3DDialog(Window owner, AppModel model)` — оба параметра убраны).

### 2. Переопределение типа рамы поячеечно + селектор "Рама для добавления"

По итогам `AskUserQuestion` про край экрана — пользователь ЯВНО отверг оба предложенных
варианта (сдвигать башню / отбрасывать нависающую башню) в пользу третьего:
*"изменяй горизонтальные рамы на короткие, для этого они и нужны. поэтому нужно
добавить какую-то менюшку с выбором текущей рамы для построения, тк вертикально
изредка тоже нужно ставить короткие рамы"*. Реализовано как переиспользуемый
per-cell override (тот же паттерн, что `CabinetInstance.cabinetTypeId`):
- `StructureFrameCell` (`ledscheme-model`) получил `String frameTypeId` (nullable, `null`
  = номинальный тип экрана для этого ряда). Влияет ТОЛЬКО на габариты РЕНДЕРА/pick-бокса
  конкретной ячейки (`Structure3DPanel.resolveFrameDims`) — Y-позиция в стеке для рядов
  0/1 остаётся номинальной (`segmentIndex × frameH`, читается из ГЛАВНОГО типа рамы), т.е.
  подменённая на короткую рама всё равно занимает свой номинальный "слот" по высоте,
  просто не полностью его заполняет — сознательное упрощение, чтобы не городить
  переменную высоту стека ради редкого краевого случая.
- `AppModel.toggleStructureFrameCell` получил 5-арг перегрузку с
  `frameTypeIdForNewCell` — применяется ТОЛЬКО в момент СОЗДАНИЯ новой записи; повторный
  клик по уже существующей ячейке (toggle hidden) тип не трогает. Старая 4-арг сигнатура
  осталась (делегирует с `null`), обратная совместимость для regenerate/тестов.
- `ui.Structure3DDialog` — новый `JComboBox<StructureFrameType>` "Рама для добавления"
  внизу окна (варианты — только `Kind.FRAME`/`Kind.SHORT_FRAME` из библиотеки, плюс
  "(как обычно)" = `null`); выбор сохраняется в `Structure3DPanel
  .activeNewCellFrameTypeId` через `setActiveNewCellFrameTypeId`, читается при КАЖДОМ
  клике по призраку (не персистится на `Screen` — это состояние сессии редактирования,
  не сохранённый выбор).

### 3. Усилительные рамы выноса (row == 2)

Второй ответ на `AskUserQuestion`: *"1 метровая рама на секцию, вкл/выкл как всё
остальное"* — по 1 опциональной вертикальной раме поверх КАЖДОЙ секции выноса (section
1+, у ядра/section 0 уже есть полноразмерные ряды 0/1). Переиспользован
`StructureFrameCell` — **`row == 2`** обозначает "усилительная рама выноса", при этом
`segmentIndex` ПЕРЕИСПОЛЬЗУЕТСЯ как номер секции выноса (1-based), а НЕ позиция в стеке
(усилительные рамы не стоят друг на друге — ровно одна на секцию, независимая от других
секций). Дефолтная высота (если тип не переопределён) —
`StructureCalc.DEFAULT_REINFORCEMENT_FRAME_HEIGHT_MM = 1000` (1м). Генерируются
`ScreenLogic.regenerateStructureCells` автоматически (видимые по умолчанию, как всё
остальное железо) для каждой валидной башни × каждой секции выноса — независимо от
`structureIncludeBaseFrame` в САМОМ списке (та же конвенция, что у ядра/базы: чекбокс
влияет только на подсчёт/показ, не на то, что хранится, см. Phase 2 выше), но
`ui.Structure3DPanel.reinforcementCandidates` НЕ строит кандидатов вовсе, если чекбокс
выключен (то же, что `baseCandidates`). Стыки/счёт: `StructureCalc.compute` считает
усилительные рамы в общем `verticalFrameCount`, но ИСКЛЮЧАЕТ их из adjacency-подсчёта
рядов 0/1 (иначе `segmentIndex`-переиспользование ложно засчитало бы соседние секции как
"стык друг с другом") — вместо этого 1 видимая усилительная рама = 1 стык с базовой
секцией под ней (та же схема "1 элемент = 1 стык", что у перемычек/базы).

### 4. Башни не строятся там, где на экране нет кабинетов

*"Если в экране есть отсутствующие кабинеты, то для них башни не строятся"* —
`ScreenLogic.regenerateStructureCells` получил параметр `CabinetType type` и новый
приватный `towerHasCabinetContent(screen, type, towerX, spacing)`: башня валидна, только
если хотя бы один ВИДИМЫЙ кабинет пересекается с её зоной ответственности (`towerX` ±
`spacing/2`). Невалидные башни ПОЛНОСТЬЮ исключаются из всех генерируемых осей (рамы
ядра, перемычки, база, усиление) — в т.ч. если башня СТАЛА невалидной после изменения
формы экрана, её (возможно, вручную отредактированные) ячейки выбрасываются при
следующем «Рассчитать». Правило действует ТОЛЬКО при автогенерации — ручное добавление
кликом по призраку в 3D (`AppModel.toggleStructureFrameCell`) ему не подчиняется,
пользователь может поставить башню где угодно вручную. `AppModel.updateScreenStructure`
резолвит тип через уже существующий `typeOf(screen)`.

Четвёртая правка пользователя ("рама не должна быть видна за силуэтом экрана спереди —
значит башни нужно сдвигать/убирать") оказалась ТЕМ ЖЕ вопросом, что и правка #2 (край
экрана) — после уточняющего вопроса пользователь остановился на решении #2
(переопределение типа рамы), а не на автоматическом сдвиге/удалении башен, так что
отдельного механизма под пункт 4 не добавлялось.

## Phase 2.3 — форма рамы "восьмёркой" + CAD-виды (2026-08-14, тот же день)

Пользователь протестировал Phase 2.2 и прислал 2 CAD-референса (скриншот реальной
модели рамы + фото готовой башни с подсветкой одной вертикальной рамы и прицепленной
к ней перемычкой). Итог, дословно: *"Каждая рама 8-образная. имеет 2 боковые трубы,
соедниенные 3 перекладинами - по краям и посередине. рамы-перемычки цепляются к
вертикальным как раз к этим перекладинам, никуда более."*

**Что было не так с Phase 2.2 рендером** (`drawTowerSegment`/`drawPeremychkaFrame` в
`Structure3DPanel`): рама рисовалась как 2 рельса + ОДНА средняя перекладина ("Н"-форма,
не "8"). Жалоба "стандартная рама рендерится как столбик" — скорее всего НЕ логическая
ошибка (код одинаково рисовал ряды 0/1 и усилительные row==2 через одну и ту же функцию),
а эффект масштаба: у полноразмерной рамы (~950мм) единственная средняя перекладина
толщиной ~20-50мм из камеры на типичной дистанции визуально почти не читается, тогда как
у явно переопределённых (короче) ячеек та же абсолютная толщина — заметная доля высоты.
Крайние (верх/низ) перекладины эту проблему снимают структурно: они всегда лежат ровно на
силуэте рамы (там, где рама иначе просто обрывается пустотой), поэтому видны при любом
масштабе/угле, а не только вблизи.

**Новая форма** (`drawTowerSegment`) — 2 рельса на всю высоту + 3 перекладины: у самого
низа ({@code baseY}), ровно посередине ({@code baseY + frameH/2}), у самого верха
({@code baseY + frameH}) — та же логика применена к перемычке (`drawPeremychkaFrame`,
повёрнута на 90°, 3 перекладины по краям/середине span). У соседних составленных друг на
друга сегментов верхняя/нижняя перекладина технически рисуется дважды в одной и той же
точке (верх сегмента N = низ сегмента N+1) — это ожидаемо, тот же физический стык, не
дефект.

**Геометрическое обоснование интервала перемычек = 1.5×frameH** (уже было в Phase 2.2,
здесь только подтверждено референсом): у башни из составленных друг на друга рам
перекладины лежат на каждой отметке {@code n × frameH/2} (низ/середина/верх каждого
сегмента). 1.5×frameH = 3×(frameH/2) — то есть каждый уровень перемычки в
`peremychkaCandidates`/`StructureCalc.peremychkaIntervalMm` автоматически попадает РОВНО
на одну из этих трёх типов перекладин, никогда между ними — данные не менялись, только
подтверждена согласованность с новым рендером.

**CAD-виды**: `Structure3DDialog` получил панель кнопок "Вид: Спереди/Сбоку/Сзади/Сверху"
над GL-канвасом — каждая зовёт новый `Structure3DPanel.setViewAngle(yawDeg, pitchDeg)`

функциональным эффектом.

## Round 4 — поворот рамы, "рамы не пересекаются", опора всегда строится (2026-08-14)

Пользователь протестировал Round 3 (фигура-8) и прислал 2 находки + 1 явный принцип +
1 требование:

**Находка 1 — библиотека, не код**: у стандартной "рамы" в личной библиотеке пользователя
оказалось `widthMm: 50` вместо `500` (нашёл прямым чтением `~/.led-scheme/library.json`) —
рельсы при такой ширине перекрывали друг друга и схлопывались в "столбик". Не правка кода,
а инструкция пользователю поправить значение в админ-консоли; защитный клэмп в рендерере
(рельсы не могут "съесть" друг друга) добавлен на этот же случай.

**Находка 2 — башни не убирались после пересчёта**: тоже нашёл на реальных данных
пользователя (screen с проёмом-аркой, вырезаны НИЖНИЕ ряды столбца, верхние остались
видимы) — `ScreenLogic.towerHasCabinetContent` смотрела "есть ли хоть один видимый кабинет
в столбце", а не именно НИЖНИЙ (опорный) ряд — башня растёт от земли, ей нечего
поддерживать под проёмом, даже если выше снова есть экран. Поправлено на проверку именно
нижнего ряда.

**Поворот рамы на 90°** (подтверждено ответом на прямой вопрос): узкая грань (frameD,
~51мм) теперь смотрит на зрителя/экран, широкая грань (frameW, ~500мм) с перекладинами
уходит В ГЛУБИНУ башни вдоль Z — перекладины видны сбоку/изнутри башни (тому, кто стоит
между передним и задним рядом), как у настоящей лестницы, а не в лицо зрителю. `bounds`
кандидатов переведены на чистую схему "угол + протяжённость" (без скрытого "центра"
внутри `drawTowerSegment`) — исключает рассинхрон с призрачным wireframe, который рисует
тот же самый bounds.

**"Рамы — это конструктор, они не пересекаются"** — ключевой принцип, явно сформулированный
пользователем, определивший все остальные правки этого захода:
- Раньше `backZ = frontZ - sectionDepthMm` (расстояние между ЦЕНТРАМИ переднего/заднего
  ряда) — при повёрнутой (широкой по Z) раме передний и задний ряд ХОРОНИЛИ друг друга
  (frameW сопоставим с sectionDepthMm). Исправлено: `backZ = frontZ - frameW -
  sectionDepthMm` — теперь `sectionDepthMm` это ЧИСТЫЙ ЗАЗОР между гранями рядов, а не
  расстояние между центрами.
- Перемычка (`peremychkaCandidates`) теперь занимает РОВНО этот зазор (от дальней грани
  переднего ряда до ближней грани заднего) — не залезает ни в один из рядов.
- Опорная рама (`baseCandidates`) секция 0 ("ядро") — раньше была отдельной плитой ровно
  под зазором и физически пересекалась с обоими рядами; теперь это ОДНА большая плита,
  накрывающая ВЕСЬ объём: от ближней грани переднего ряда до дальней грани заднего
  (`baseSectionZRange`, новый общий хелпер для base/reinforcement/drawCups — избегает
  рассинхрона формул позиционирования секций между тремя местами, где они раньше
  дублировались). Секции выноса (1+) продолжают от дальней грани заднего ряда назад, той
  же глубины `sectionDepthMm`.
- Опорная/усилительная рама тоже НЕ пересекается с землёй: `drawGroundPlane` теперь берёт
  толщину опоры и рисует земляную плоскость СТРОГО НИЖЕ неё (`groundTopY = -baseThicknessMm`)
  — раньше и земля, и опора занимали `Y≈[-51..0]`/`[-20..0]` одновременно, класический
  Z-fighting ("рендерятся с переменным успехом", баг-репорт).

**Перемычки и опоры — тоже "8"-рамы, не сплошные плиты**: `drawPeremychkaFrame` и новый
`drawBaseFrame` — обе теперь просто разные цветовые обёртки одного общего
`drawHorizontalLadderFrame` (2 рельса + 3 перекладины вдоль Z, тот же принцип, что у
`drawTowerSegment`, просто "лёжа"). Опора — серая (под цвет вертикальных рам), перемычка —
бежевая, чтобы не путать визуально.

**Опорная рама теперь ВСЕГДА строится** — прямое указание пользователя ("опорные рамы
должны быть всегда"). `Screen.structureIncludeBaseFrame`/чекбокс "Базовая (опорная) рама
под каждой башней" в `SetupStagePanel` убраны целиком (не оставлены как
неработающий/задизейбленный UI) — `AppModel.updateScreenStructure` потерял параметр
`includeBaseFrame`, `StructureCalc.compute` считает `baseFrameCount` безусловно,
`Structure3DPanel.baseCandidates`/`reinforcementCandidates` больше не проверяют флаг.

### Round 2 — реальная причина "рама рендерится как столбик" НЕ в масштабе (2026-08-14)

Гипотеза выше ("единственная средняя перекладина не читается на большой высоте") оказалась
**неверна** — после 3-крестовинного редизайна проблема осталась для СТАНДАРТНОЙ рамы,
пока переопределённые (короткие) ячейки продолжали рендериться правильно. Пользователь
прислал скриншот, где стандартная рама так и осталась "столбиком", а у переопределённых
ячеек виден правильный "8"-профиль — попросил проверить не только рендерер, но и реальные
данные библиотеки.

**Реальная причина — не код, а данные пользователя**: прочитал `~/.led-scheme/library.json`
напрямую (не спрашивая — файл на диске этой же машины) и нашёл, что запись
`sharedStructureFrameTypes` с `kind: FRAME` ("основная" рама, используется как
`Screen.structureFrameTypeId` во всех активных сценах) имеет `widthMm: 50.0` вместо
ожидаемых ~500 (короткая рама рядом в том же файле корректна: `widthMm: 500.0`) —
похоже на опечатку/перепутанные поля при заполнении в админ-консоли. При `frameW=50`:
`rail = max(30, min(70, 50*0.12=6)) = 30` — то есть КАЖДЫЙ из двух рельсов толщиной 30мм
при общей ширине рамы 50мм, они физически ПЕРЕКРЫВАЮТ друг друга (rail1 занимает [-25,+5],
rail2 занимает [-5,+25] относительно центра) — визуально сливаются в один сплошной
"столбик", а сама перекладина (`crossW = frameW - 2*rail = -10`, отрицательная ширина)
тонет в этом перекрытии. Это НЕ баг рендерера в строгом смысле — рендерер честно
отрисовывает то, что задано в библиотеке, — но сам рендерер тоже не был устойчив к такому
значению: **добавлен защитный clamp** — `rail` теперь не может превышать 45% от `frameW`
(`Math.min(Math.max(20, Math.min(70, frameW * 0.12)), frameW * 0.45)`), так что даже при
ошибочно узкой раме рельсы не перекрываются и крестовина остаётся видимой (тонкой, но не
вырожденной). **Пользователю нужно поправить саму запись в библиотеке** (админ-консоль,
`StructureFrameTypeFormPanel`, ширина основной "рамы" 50→500мм) — clamp это маскирует
визуально, но не исправляет физически неверные данные.

### Round 2 — причина "лишние башни не убираются после Рассчитать"

Тоже НЕ логическая ошибка в смысле "код не фильтрует вообще" — прочитал сохранённый
`workspace.json` пользователя (реальный проект с прорезанной формой экрана) и нашёл
конкретный кейс: у экрана вырезан ПРОЁМ-АРКА (9 из 12 нижних рядов скрыты в нескольких
столбцах), а ВЕРХНИЕ 3 ряда того же столбца остались видимы. Старая версия
`towerHasCabinetContent` (`ScreenLogic`) проверяла "есть ли видимый кабинет НА ЛЮБОМ
ряду в зоне башни" — раз где-то выше в столбце кабинет виден, башня считалась нужной,

верхние ряды, опорный виден — башня всё равно строится) в `StructureCalcTest`.

## Round 5 — короткий задний ряд, поворот коротких рам, индикатор осей (2026-08-14)

Три отдельные правки по итогам ещё одного теста с фото/скетчем от пользователя.

### Индикатор осей

Запрошено явно: "чтобы я хотя бы мог сказать вокруг какой оси тебе надо элементы
выстраивать и вращать". `Structure3DPanel.drawAxisGizmo` — крохотный (84×84px) отдельный
вьюпорт в углу главного вида, своя ортографично-перспективная проекция, камера повторяет
ТОЛЬКО поворот главной камеры (yaw/pitch), без позиции/зума/панорамы — 3 цветные линии из
общего начала (X=красный, Y=зелёный, Z=синий). GL-текст не заводили ради 3 подписей —
цветовая легенда текстом в `Structure3DDialog` рядом с кнопками видов.

### Короткие рамы (перемычка/основание) повёрнуты на 90° по вертикальной оси

Баг-репорт с эскизом: короткая рама (859×500×51мм в библиотеке) лежала неправильной
гранью к зрителю — раньше `drawPeremychkaFrame`/`drawBaseFrame` брали X-протяжённость
(то, что видно спереди) из `frameW` ГЛАВНОЙ рамы (~500мм). Нужно было — из СОБСТВЕННОГО
длинного ребра короткой рамы (её `heightMm` в библиотеке, ~859мм), лежащего в
горизонтальной плоскости. Новое поле `StructureGeometry.shortFrameLengthMm` (источник —
`shortType.getHeightMm()`, фолбэк 859мм) заменило `g.frameW()` в
`peremychkaCandidates`/`baseCandidates`/соответствующих местах `drawCups`.

### Задний ряд (row=1) — короткая опора, не вторая полноразмерная башня

Ключевая находка по фото реальной башни, обведённой пользователем: с фронта видна ОДНА
полноразмерная лестничная рама (передний ряд), а всё, что дальше от зрителя — это
вынос/опора, и не должно быть таким высоким. Уточняющий вопрос закрыл неоднозначность:
задний ряд (`row == 0`/`row == 1` в {@code StructureFrameCell}) должен стать КОРОТКИМ
(~1-2м), а не оставаться зеркальной полноразмерной копией переднего.

Реализовано без удаления оси `row` (передний/задний ряд остаются двумя разными списками
ячеек — концепция не убрана, просто перестала быть симметричной по высоте):
- `Screen.structureBackRowSegments` — новое поле, номинальная граница сетки ТОЛЬКО для
  `row == 1`, независимая от `structureVerticalFramesPerTower` (только `row == 0`).
- `StructureCalc.suggestBackRowSegments(frameHeightMm)` — сколько сегментов рамы
  укладывается в ~1.5м (середина диапазона "1-2м"), не меньше 1 — та же
  "формула-как-стартовое-предложение" конвенция, что у остальных `suggestXxx`.
- `ScreenLogic.regenerateStructureCells` получил параметр `backRowSegments` — `row == 0`
  по-прежнему ограничен `verticalFramesPerTower`, `row == 1` — отдельно `backRowSegments`.
- `Structure3DPanel.FrameEnvelope` разделён на `maxFrontSegment`/`maxBackSegment` (раньше
  был один `maxSegment` на оба ряда) — `frameCandidates` использует нужный по `row`.
- `SetupStagePanel.calculateStructure()`: уровни перемычек теперь считаются от ФИЗИЧЕСКОЙ
  высоты заднего ряда (`backRowSegments × frameHeightMm`), а не от полной высоты башни —
  перемычка крепится к перекладине заднего ряда, выше короткого заднего ряда крепить не к
  чему. Если пользователь вручную поднимет число уровней перемычек в спиннере выше
  физического предела, генератор это не пересчитывает автоматически — увидит перемычку
  "в воздухе" мимо заднего ряда и поправит число сам (осознанное упрощение, не жёсткая
  валидация формы).

`AppModel.updateScreenStructure` получил параметр `backRowSegments` (между
`verticalFramesPerTower` и `peremychkaLevels`) — сигнатура снова изменилась, все вызовы в
тестах поправлены. Новые тесты: `StructureCalcTest.backRowIsIndependentAndShorterThan
FrontRow` (короткий задний ряд не зависит от изменения переднего),
`suggestBackRowSegmentsTargetsAboutOneAndHalfMeters`.

## Round 6 — перемычка соединяет СОСЕДНИЕ БАШНИ, не передний/задний ряд (2026-08-14)

Пользователь протестировал Round 5 и прислал вид сверху с обводкой (красные прямоугольники
+ стрелки) и референсное фото башни. Итог, дословно: *"перемычки должны находиться между
вертикальными рамами ОДНОГО ряда (красные прямоугольники), разные ряды вертикальных рам
примыкают друг к другу вплотную (стрелки)"*.

**Это разворот того, что считалось верным с самого Phase 2.1**: раньше перемычка соединяла
передний и задний ряд ВНУТРИ одной башни (через зазор `sectionDepthMm`). Теперь — наоборот:
передний и задний ряд примыкают друг к другу БЕЗ ЗАЗОРА, а перемычка соединяет ДВЕ
СОСЕДНИЕ БАШНИ в пределах ОДНОГО ряда (по факту — по смыслу это то же самое, что делал
упразднённый на Phase 2.1 `StructureBraceCell`, просто теперь раздельно для переднего и
заднего ряда, а не одной плоскостью).

- `StructurePeremychkaCell` (`ledscheme-model`) получил поле `row` (0/1) — ключ стал тройкой
  `(towerIndex, row, levelIndex)`, где `towerIndex` теперь означает ЛЕВУЮ башню пары
  (соединяет `towerIndex` и `towerIndex+1`).
- `Structure3DPanel.computeGeometry`: `backZ = frontZ - frameW` (было `- frameW -
  sectionDepthMm`) — ряды теперь буквально касаются (дальняя грань переднего = ближняя
  грань заднего).
- `peremychkaCandidates` перестроен на пары башен: X-протяжённость = реальный зазор между
  соседними башнями (`spacing - frameW`, НЕ `shortFrameLengthMm` — та константа была нужна
  для СТАРОЙ ориентации и здесь больше не при делах, поскольку длина перемычки теперь
  определяется физическим расстоянием между башнями, а не размером самой рамы), Z-глубина =
  `frameW` (совпадает с footprint-ом ряда). Новая функция рендера
  `drawInterTowerPeremychka` — тот же "8"-каркас, третья axis-permutation (рельсы вдоль X,
  перекладины вдоль Z).
- `ScreenLogic.regenerateStructureCells`: перемычка генерируется для зазора
  `(t, t+1)`, только если ОБЕ башни валидны (см. `towerHasCabinetContent`) — нет соседней
  башни, нечего соединять.
- `AppModel.toggleStructurePeremychkaCell`/`StructurePeremychkaCell.matches` получили
  параметр `row`.

**Два попутных UI-бага в 3D-диалоге**, найденные на том же скриншоте:
- *"вид на сцену обрезался"*: `drawAxisGizmo` восстанавливал вьюпорт через
  `gljPanel.getWidth()/getHeight()` (логические пиксели), а `reshape()` настраивает и
  проекцию, и `viewportW`/`viewportH` в ФИЗИЧЕСКИХ (на HiDPI это разные числа) — сцена
  рендерилась только в урезанный угол окна. Исправлено: используются те же
  `viewportW`/`viewportH`, что и `reshape()`, размер самого индикатора масштабируется тем
  же отношением физических/логических пикселей.
- *"текстовая легенда не видна"*: делила один `FlowLayout`-ряд с 4 кнопками видов — в узком
  окне ряд сжимался/переносил легенду за пределы видимой области. Теперь у легенды своя
  строка (вертикальный `Box` над GL-панелью).

Теперь оба элемента используют одну и ту же "gap-based" геометрию:

- `baseCandidates`/`ScreenLogic.regenerateStructureCells` (базовая часть) переписаны по
  образцу `peremychkaCandidates`/перемычечной части: `towerIndex` в `StructureBaseFrameCell`
  теперь означает ЛЕВУЮ башню зазора (как у `StructurePeremychkaCell`), X-протяжённость =

  независимо от того, что X теперь завязан на зазор, а не на одну башню.
- Следствие для подсчёта: N башен теперь дают N−1 базовых записей на секцию (по числу
  зазоров), а не N — раньше было "1 база на башню". Три теста в `StructureCalcTest` с
  захардкоженными числами базовых секций (`countsFollowUserSuppliedRatios_withBaseFrame`,

  `removingMiddleSegmentBreaksItsRowJointsButNotTheOtherRow` использует towerCount=1 — при
  одной башне зазоров нет вообще, поэтому база там теперь 0, а не 1). Усилительные рамы
  (`row == 2`, секции выноса) НЕ переведены на gap-based — они как были, так и остались
  привязаны к ОДНОЙ башне (это отдельная сущность в `StructureFrameCell`, не
  `StructureBaseFrameCell`, физически стыкуется с базовой секцией снизу, а не соединяет
  соседние башни).
- Рендер: `drawBaseFrame`/`drawInterTowerPeremychka` — теперь оба тонкие обёртки над общей
  `drawGapSpanningLadderFrame` (рельсы вдоль X на весь `xSpan`, 3 перекладины вдоль Z),
  отличаются только палитрой (перемычка — бежевая, база — серая, под цвет вертикальных
  рам, чтобы не путать визуально). Мёртвое поле `StructureGeometry.shortFrameLengthMm`

- `drawCups` (стаканы-соединители в стыках): база использует тот же паттерн лево/право по
  X от зазора (`c.getTowerIndex()*spacing + frameW/2`, `(c.getTowerIndex()+1)*spacing -

### Корень (1) и (2) — X-пролёт считался от НЕ ТОЙ грани рамы

Открытый вопрос из Round 7 закрыт — дело было не в замене `shortFrameLengthMm` на
геометрический зазор (это осталось верным решением, перемычка ДОЛЖНА тянуться на весь
физический зазор между башнями), а в том, ОТ ЧЕГО этот зазор считался. Round 3 (гораздо
раньше в этой же сессии) повернул вертикальную раму на 90°: узкая грань (`frameD`,
~51мм) стала смотреть на зрителя вдоль X, широкая (`frameW`, ~500мм) ушла В ГЛУБИНУ вдоль
Z. Но код перемычки/базы, добавленный в Round 5-7 уже ПОСЛЕ этого поворота, по ошибке
продолжал вычитать `frameW` из шага башен для X-пролёта (`xSpan = spacing - frameW`) и
сдвигать X-положение на `frameW/2` — как будто стойка всё ещё занимает по X ту же ширину,
что и её широкая грань. Реально стойка занимает по X только `frameD` (~51мм). При
`spacing=1000`, `frameW=500`, `frameD=51`: код давал `xSpan=500мм` вместо настоящих
`949мм` — ровно вдвое короче, с полями по ~225мм с каждой стороны вместо честного
прилегания к обеим башням. Тот же самый заниженный `xSpan` (узкий по X при том, что
Z-глубина секции у базы может быть ~1000мм+) объясняет и "неправильно развёрнута" —
несоразмерно узкая по X, вытянутая по Z плита в перспективе читается как повёрнутая на
90° не туда.

**Исправлено** (`Structure3DPanel.java`) — все X-величины `peremychkaCandidates`,
`baseCandidates` и обе пары left/right-стаканов в `drawCups` переведены с `frameW` на
`frameD`: `xSpan = spacing - frameD`, `x = gapIdx*spacing + frameD/2` (и симметрично для
левого/правого стакана). Z-величины (глубина ряда/секции, `frontZ`/`backZ`/
`baseSectionZRange`) НЕ трогали — там `frameW` был и остаётся верным, это другая ось.

(в отличие от стыков вертикальных/базовых рам, которые действительно наращиваются через

### "почему в основании появились рамы 1х1м, таких не существует в библиотеке"

Усилительные рамы выноса (`StructureFrameCell.row == 2`, по одной на каждую секцию
выноса за пределами ядра) без явного per-cell override брали высоту из
`StructureCalc.DEFAULT_REINFORCEMENT_FRAME_HEIGHT_MM` — константа `1000` (буквально "1
метровая рама", как и было написано открытым текстом в комментарии при добавлении этой
фичи), НИКАК не привязанная к реальной записи библиотеки. Остальные размеры короткой
рамы/базы/перемычки (`sectionDepthMm`, `baseThickness`, `peremychkaThickness`) уже
давно берутся из `shortType` (реального "рама короткая" из библиотеки) с этой же
константой лишь как крайний fallback — усилительную высоту просто забыли перевести на
тот же паттерн, когда его вводили. Исправлено: `StructureGeometry` получил поле
`reinforcementHeightMm = dim(shortType.getHeightMm(), DEFAULT_REINFORCEMENT_FRAME_HEIGHT_MM)`,
`resolveFrameDims` берёт `fallbackH` оттуда вместо константы напрямую — усилительная
рама без override теперь той же высоты, что и "рама короткая" в библиотеке пользователя
(859мм), а не выдуманного 1000мм.

### "при добавлении рам вглубь (увеличиваю вынос) появляются стаканы вверх в воздухе"

`drawCups` группирует `StructureFrameCell` по `(towerIndex, row)` и трактует
`segmentIndex` как позицию В СТЕКЕ по высоте (`y = (seg+1) * frameH` между двумя
"смежными" индексами) — это верно ТОЛЬКО для `row` 0/1 (передний/задний ряд, где
`segmentIndex` действительно номер яруса снизу вверх). Для `row == 2` (усилительные рамы
выноса) `segmentIndex` в этом же списке означает НОМЕР СЕКЦИИ ВЫНОСА, а не позицию по
высоте (см. class-javadoc `StructureFrameCell`) — но группирующий код группировал ВСЕ
строки без разбора по `row`, включая `row == 2`. Как только пользователь увеличивал
число секций выноса (появлялись усилительные рамы с соседними номерами секций, например
1 и 2), этот код принимал их за "смежный стык вертикального стека" и рисовал стакан на
`y = (2+1) * frameH ≈ 2850мм` — в воздухе, без всякой рамы рядом. `StructureCalc.compute`
уже правильно фильтрует `c.getRow() < 2` при подсчёте `verticalJoints` — рендер-версия в
`drawCups` просто не была приведена в соответствие при добавлении усилительных рам
(Phase 2.2, задолго до этой сессии). Исправлено тем же фильтром `c.getRow() < 2` при
построении `segmentsByTowerRow`.

Оба фикса — в `Structure3DPanel.java`, без изменений в `StructureCalc.compute` (там
подсчёт уже был верным) — новых тестов не потребовалось, `StructureCalcTest` не менялся
в этом раунде.

## Round 11 — ядро базовой рамы = НЕСКОЛЬКО реальных независимых секций (2026-08-14)

Round 10 исправил "метр на метр" только визуально: `Structure3DPanel.drawSlicedBaseFrame`
резал ОДНУ `StructureBaseFrameCell` на несколько нарисованных кусков при рендере, сама
ячейка в данных оставалась одной. Пользователь тут же указал на неполноту: *"эта пластина
должна не рендериться как 2 рамы, а являться 2 отдельными рамами. Башни могут быть
глубиной 0.5, в таком случае текущее основание не будет подходить по габаритам"* — то
есть (1) деление на модули должно быть НАСТОЯЩИМ (независимые записи, каждую можно
включить/выключить отдельно — ровно то, что "быть 2 отдельными рамами" и означает), и
(2) число модулей должно считаться от РЕАЛЬНЫХ габаритов рамы, а не быть жёстко "2" —
при другой глубине рамы 2 модуля по `sectionDepthMm` могут не покрыть ядро точно
(или наоборот, для очень тонкой рамы хватит одного).

**Новая функция `StructureCalc.coreBaseSectionCount(frameW, sectionDepthMm)`** — сколько
ЦЕЛЫХ модулей глубиной `sectionDepthMm` нужно, чтобы покрыть полную глубину ядра
(`2 * frameW`, оба ряда без зазора), округляя ВВЕРХ (`Math.ceil`) — при
`frameW=sectionDepthMm=500` (данные пользователя) даёт ровно 2; при нечётном отношении
(например, `frameW=400`) даёт 2 модуля на `800мм` требуемой глубины (не делится нацело
на 500, но 1 модуль не покрыл бы всю глубину). Не меньше 1 (защита от нулевой/
отрицательной `sectionDepthMm`).

**`ScreenLogic.regenerateStructureCells` получил новый обязательный параметр
`coreBaseSectionCount`** — секции `[0, coreBaseSectionCount)` теперь ВСЕ полноценные,
независимо переключаемые `StructureBaseFrameCell` (как и было для секций выноса, просто
границу "где кончается ядро" раньше жёстко считали равной 1). Усилительные рамы выноса
(`row == 2`) генерируются начиная с индекса `coreBaseSectionCount`, а не жёстко с `1` —
раньше при `coreBaseSectionCount > 1` усилительная рама могла бы попасть ВНУТРЬ ядра, что
физически бессмысленно (ядро уже полностью занято полноразмерными рядами 0/1).
`ScreenLogic` сам не знает габаритов рамы (нет доступа к `Workspace`) — параметр всегда
приходит уже вычисленным от вызывающей стороны, как и остальные номинальные счётчики.

**`AppModel.updateScreenStructure`** — единственное место с одновременным доступом и к
`Workspace` (резолвит `frameTypeId`/`shortFrameTypeId` в реальные `StructureFrameType`),
и к вызову `regenerateStructureCells` — считает `frameW`/`sectionDepthMm` из выбранных
типов (фолбэк на `StructureCalc.DEFAULT_FRAME_WIDTH_MM`/`DEFAULT_SECTION_DEPTH_MM` = 500/
500, если тип не выбран) и передаёт `coreBaseSectionCount` дальше.

**`Structure3DPanel`**:
- `drawSlicedBaseFrame` (Round 10, визуальный хак) удалён целиком — больше не нужен,
  каждая секция уже РОВНО `sectionDepthMm` глубиной на уровне данных, рендер вернулся к
  простому `drawBaseFrame` на кандидат.
- `baseSectionZRange` упрощена — больше не различает "ядро"/"вынос", ЛЮБАЯ секция теперь
  одинаковой глубины `sectionDepthMm`, считая от ближней грани переднего ряда назад.
- `frameEnvelope` получил параметр `StructureGeometry g` (был только `Screen`) — нужен,
  чтобы посчитать `coreBaseSectionCount` для нижней границы `maxSection` (у всех 4

### Изменения

- **`StructureCalc.suggestTowerCount`** — было `ceil(width/spacing)+1` (столб каждый шаг

  требует инженерной перепроверки как и весь калькулятор) больше шага башен.
- **`ScreenLogic.regenerateStructureCells`** — циклы, автоматически заполнявшие ЛЮБОЙ
  валидный зазор между соседними башнями перемычкой/базой (Round 5-7), убраны целиком.
  Остался только код СОХРАНЕНИЯ уже расставленных пользователем записей (обрезка по
  новым границам при "Предварительном расчёте" — та же логика, что уже была для
  вертикальных рам). Пустой список при первом расчёте — ожидаемое поведение, не баг.
- **Побочный, отдельный баг-репорт в этом же заходе**: *"при выставленной высоте 2м
  строится башня 3м высотой... высота башни считается от пола до верхней грани верхней
  рамы"* — `StructureCalc.suggestVerticalFramesPerTower` использовал `Math.ceil`, который
  ВСЕГДА округляет число сегментов ВВЕРХ и, соответственно, всегда даёт башню ВЫШЕ
  запрошенной высоты (2000мм при раме 950мм → 3 сегмента = 2850мм). Исправлено на
  `Math.floor` — собранная высота теперь никогда не превышает запрошенную (может быть
  чуть НИЖЕ, если высота рамы не делит запрошенную высоту нацело — это ожидаемо и
  безопаснее, чем перебор).

## Round 15 — тесные pick-box'ы для perемычки/базы/усилительных рам (2026-08-15)

Баг-репорт без скриншота: *"сейчас определение того, на что нацелен курсор считается
криво, проверь"*. Расследование (foreground Explore-агент, т.к. репорт слишком расплывчат
для угадывания) нашло точную причину: `Structure3DPanel.peremychkaCandidates`,
`baseCandidates` и `reinforcementCandidates` использовали ПОЛНУЮ номинальную
bounding-box (`bounds`) как `pickBoxes` для луча-теста, хотя реальная отрисовка
(`drawGapSpanningLadderFrame`/`drawTowerSegment`) — полая "8"-образная лестничная рама:
два тонких рельса + 2-3 перекладины, с большими пустыми промежутками между ними. Клик по
визуально пустому месту внутри `bounds` ошибочно засчитывался как попадание в сплошной
элемент.

`frameCandidates` уже был исправлен под этот же класс бага в одном из более ранних
раундов (см. историю выше, «тесные post-boxes») — тесные pick-box'ы по толщине рельса
(`railThickness(...)`), а не по полной ширине/глубине элемента. Этот раунд просто
распространил тот же приём на оставшиеся три конструктора кандидатов, которые были
добавлены позже и этот фикс не унаследовали:

- `reinforcementCandidates`: `rail = railThickness(dims[0])`, два pickBox'а по Z —
  `z..z+rail` и `z+dims[0]-rail..z+dims[0]`.
- `peremychkaCandidates`: `rail = railThickness(xSpan)`, два pickBox'а по Z (в пределах
  `g.frameW()`), та же логика.
- `baseCandidates`: `rail = railThickness(xSpan)`, два pickBox'а по Z в пределах
  `sectionSpan` (`zr[1]..zr[1]+rail` и `zr[1]+sectionSpan-rail..zr[1]+sectionSpan`).

Во всех трёх случаях `pickBoxes = bounds` целиком (без сужения) сохраняется для
несуществующих ("призрачных") кандидатов — там нет полой геометрии, надо кликать по всей
номинальной области, чтобы добавить новый элемент; сужение применяется только когда
`exists == true`.

генерация ячеек не изменились, поэтому все существующие тесты (включая

именно боксы строит `Structure3DPanel`) прошли без изменений: `mvn test` — 248/248.

## Round 16 — перемычка/база теперь реагируют на per-cell override типа рамы (2026-08-15)

Вопрос-баг-репорт: *"какие сейчас рамы применяются в качестве перемычек? изменение типа
рамы не влияет на перемычки. а должно, башня может быть уже за счет коротких рам"*.

**Что применяется сейчас (не изменилось этим раундом)**: поперечное сечение (толщина по
Y) перемычки/базы всегда берётся из `structureShortFrameTypeId` (короткая рама,
`shortType.getDepthMm()`) — реальный физический смысл: перемычка/база — это изделие из
короткой рамы, независимо от того, из каких рам собрана сама башня. Это НЕ баг, менять не
стали.

**Баг, который был**: длина зазора по X (`xSpan`) и глубина по Z (footprint ряда) у
перемычки/базы считались от НОМИНАЛЬНОГО типа рамы экрана (`g.frameD()`/`g.frameW()`,
т.е. `screen.getStructureFrameTypeId()`), а не от РЕАЛЬНЫХ габаритов конкретных стоек
соседних башен. Каждая ячейка `StructureFrameCell` может иметь per-cell
`frameTypeId`-override (см. Round про "Frame-type-for-new-cells selector") — например,
собрать конкретную башню из более узких коротких рам вместо номинального типа, тогда её
реальная стойка `frameD` меньше номинала. `frameCandidates` уже учитывал такой override
при отрисовке САМОЙ стойки (`resolveFrameDims`), но `peremychkaCandidates`/
`baseCandidates` игнорировали его при расчёте зазора между стойками — перемычка/база не
сужались/расширялись вслед за реально более узкой башней, оставаясь привязанными к
номинальному зазору.

**Фикс** (`Structure3DPanel.java`):
- Новый метод `resolveTowerPostDims(screen, g, towerIndex, row)` — берёт `frameTypeId`
  первой существующей (не hidden) ячейки этой башни+ряда, если он задан, резолвит её
  реальные габариты из библиотеки; иначе — номинальные `g.frameW()/frameH()/frameD()`.
  Та же идея, что `resolveFrameDims`, но без ветки "призрака" (для факта существующей
  конструкции, не превью нового клика).
- `peremychkaCandidates`: `xSpan`/`x`/`zDepth` теперь считаются от
  `resolveTowerPostDims(..., gapIdx, row)` и `resolveTowerPostDims(..., gapIdx+1, row)`
  ЛЕВОЙ и ПРАВОЙ башен ИМЕННО ТОГО ряда, который соединяет перемычка (`frontZ`/`backZ`
  различаются по ряду) — `xSpan = spacing - leftD/2 - rightD/2`, `zDepth = min(leftD_Z,
  rightD_Z)` (не даёт перемычке торчать за пределы более узкой из двух стоек).
- `baseCandidates`: база лежит ПОД ОБОИМИ рядами сразу (секции по Z шагают через footprint
  и переднего, и заднего ряда), поэтому для каждой башни берётся МАКСИМУМ `frameD` среди
  обоих рядов (`Math.max(front, back)`) — плита гарантированно не перекрывает более
  широкую из двух стоек, даже если переопределён только один ряд.
- `xSpan <= 0` теперь пропускает (`continue`) конкретную пару башен/ряд, а не выходит из
  всего метода (`return`) — раньше проверка была одна на весь набор кандидатов (`xSpan`
  был общим для всех), сейчас у каждой пары свой `xSpan`, поэтому одна слишком тесная пара
  не должна скрывать остальные валидные.

Тесный pick-box (Round 15, `railThickness(xSpan)`) продолжает работать корректно — он
считается ПОСЛЕ пересчёта реального `xSpan`, так что толщина рельса пикинга тоже следует
за реальной шириной зазора.

Не тронуто: сама толщина перемычки/базы (короткая рама, см. выше), Y-позиционирование
сегментов вертикальной рамы (`seg * g.frameH()`, всё ещё номинальное — известное
упрощение, не входит в этот баг-репорт), reinforcement-рамы выноса (`row == 2`) — они уже
и раньше корректно резолвили свои габариты через `resolveFrameDims` per-cell.

Чисто геометрический фикс рендера/пикинга — `StructureCalc`/`ScreenLogic` не менялись
(BOM-подсчёт count'ов идёт по числу реальных ячеек, не по их физическим размерам).
`mvn test` — 248/248 без изменений.

## Round 17 — "короткая рама" как отдельный тип упразднена целиком (2026-08-15)

Прямое указание пользователя: *"чаще всего перемычка делается из обычной рамы. давай
вообще уберем короткие рамы, их количество будет определять инженер отдельно.
переделываем все под обычные рамы"* — прямое продолжение Round 16 (там выяснилось, что
перемычка/база вообще не реагируют на реальные габариты стойки при per-cell override).
Теперь убран сам отдельный селектор "короткой рамы" на уровне экрана, а не просто
починена реакция на неё.

**Что убрано**: поле `Screen.structureShortFrameTypeId` (геттер/сеттер/`copy()`),
параметр `shortFrameTypeId` в `AppModel.updateScreenStructure` (сигнатура сократилась с
14 до 13 позиционных аргументов), комбобокс "Тип короткой рамы (библиотека)" в
`SetupStagePanel` (`pStructureShortFrameType`) и его заполнение
(`populateStructureFrameCombo(..., Kind.SHORT_FRAME, ...)`), проверка/перенос ссылок в
`AppModel.isStructureFrameTypeReferenced`/`migrateStructureFrameTypeReferences` (было 4
FK-поля STRUCTURE_FRAME на экран — рама/короткая рама/стакан/балласт, стало 3).

**Что заменило её роль** (`ui.Structure3DPanel#computeGeometry`) — все производные
величины, раньше бравшиеся из `shortType`, теперь берутся из ОДНОГО обычного
`frameType` (`screen.getStructureFrameTypeId()`), причём буквально совпадают с уже
посчитанными `frameW`/`frameH`/`frameD` этого же типа:
- `sectionDepthMm` (глубина одной секции выноса базы) = `frameW` (была
  `shortType.widthMm`).
- `baseThickness`/`peremychkaThickness` (толщина рельса базы/перемычки) = `frameD` (была
  `shortType.depthMm`).
- `reinforcementHeightMm` (высота усилительной рамы выноса, `row == 2`) = `frameH` (была
  `shortType.heightMm`, с фолбэком на `StructureCalc.DEFAULT_REINFORCEMENT_FRAME_HEIGHT_MM`
  — этот фолбэк теперь недостижим на практике, т.к. `frameH` уже сам фолбэкается на
  `DEFAULT_FRAME_HEIGHT_MM`, но константа/её использование в `StructureCalc` оставлены —
  безвредный мёртвый путь, не стоит того, чтобы трогать публичный API ради этого).

`AppModel.updateScreenStructure`: `sectionDepthMm` для `StructureCalc
.coreBaseSectionCount(frameW, sectionDepthMm)` аналогично заменён на `frameW` —
`coreBaseSectionCount(frameW, frameW)` математически всегда даёт РОВНО 2 (`ceil(2*frameW /
frameW) = 2`), что и есть корректный смысл: ядро базовой рамы = ровно 2 модуля (под
передним и задним рядом), когда обе величины взяты из одного типа. Функция
`coreBaseSectionCount` сама не тронута (генеральна, тестируется отдельно с разными
соотношениями — `StructureCalcTest.coreBaseSectionCountCoversFullFrameDepthInWholeCatalogModules`
не менялся и остаётся валиден как тест чистой функции).

**"Их количество определит инженер отдельно" — куда делась гибкость**: библиотечные
записи `Kind.SHORT_FRAME` НИКУДА не делись из общей библиотеки конструктива — просто
экран больше не имеет ОТДЕЛЬНОГО номинального FK-поля под них. Если на месте нужна именно
короткая рама в конкретной точке (например, крайняя башня, где обычная не влезает
впритык к краю экрана) — это по-прежнему доступно через существующий per-cell механизм:
комбобокс "Рама для добавления" в `Structure3DDialog` (уже включает и `Kind.FRAME`, и
`Kind.SHORT_FRAME`, не менялся) выбирает тип для СЛЕДУЮЩЕЙ создаваемой ячейки
(`StructureFrameCell#getFrameTypeId()` override) — именно так инженер теперь "определяет
отдельно", кликами, а не номинальным расчётом на весь экран.

**Тесты**: 8 вызовов `AppModel.updateScreenStructure(...)` в `AppModelTest` сокращены с
14 до 13 позиционных аргументов (убран один `null` — бывший `shortFrameTypeId`), значения
и ожидаемые assert'ы не менялись (дефолтные габариты и раньше давали `sectionDepthMm ==
frameW` численно, т.к. `StructureCalc.DEFAULT_SECTION_DEPTH_MM ==
StructureCalc.DEFAULT_FRAME_WIDTH_MM == 500` — совпадение чисел уже тогда, теперь это не
совпадение, а прямое равенство по коду). `StructureCalcTest` не менялся — `compute`/
`coreBaseSectionCount` не затронуты. `mvn test` — 248/248.

Не тронуто в этом раунде: сам факт, что перемычка/база резолвят реальные per-cell
габариты соседних стоек (`resolveTowerPostDims`, Round 16) — эта логика остаётся, просто
теперь "номинальный" источник, от которого она отталкивается по умолчанию, один и тот же
для всех ролей.

## Round 17 — «Шаг башен» → «Вынос», редактируемый коэффициент балласта, авто-высота башни (2026-08-19)

Три независимые правки предварительного расчёта конструктива по прямому запросу
пользователя. Перед реализацией — уточняющий `AskUserQuestion` про физический смысл
«выноса» (см. ниже), т.к. неверная догадка стоила бы дорого (несколько взаимосвязанных
файлов: модель, сервис, UI, тесты) — пользователь выбрал «вынос базы под балласт, мм».

### 1. «Шаг башен» убран целиком — оказался параметром, ни на что не влияющим

Пользователь: *"убирай параметр шаг башен, он ни на что не влияет"*. Подтверждено чтением
кода перед правкой: `Screen.structureTowerSpacingMm` использовался ТОЛЬКО в
`StructureCalc.suggestTowerCount` (стартовое число башен) и в X-позициях 3D-рендера/picking
(`ui.Structure3DPanel`) — сам `StructureCalc.compute()` (итоговая ведомость материалов:
рамы/стаканы/болты/балласт) от него не зависел вовсе (ветровая формула, которая когда-то
использовала шаг как заменитель ширины опорной базы, была удалена ещё в Phase 2.1). Убран:
поле `Screen.structureTowerSpacingMm` (геттер/сеттер/`copy()`), спиннер
`pStructureTowerSpacing`/строка формы «Шаг башен, мм» в `SetupStagePanel`, параметр
`towerSpacingMm` у `AppModel.updateScreenStructure`. Заменён новой внутренней константой
`StructureCalc.DEFAULT_TOWER_SPACING_MM = 1000.0` (тот же прежний дефолт) — используется
там же, где раньше читалось поле (`suggestTowerCount`, `ScreenLogic
.regenerateStructureCells`, `Structure3DPanel.computeGeometry`), но больше не выставляется
пользователем. Освободившееся место в форме занял «Вынос базы под балласт, мм» (см. ниже).

### 2. «Вынос базы под балласт» — ручной мм-ввод вместо эвристики по высоте/ширине экрана

Уточняющий вопрос пользователю дал точный физический смысл: не шаг между башнями и не
горизонтальный вынос крайних башен за край экрана, а именно РАССТОЯНИЕ, на которое база
дополнительно выступает под балласт (площадь опоры/рычаг устойчивости) — тот же смысл, что
уже был у `Screen.structureExtendedBaseSections` («число ДОПОЛНИТЕЛЬНЫХ секций выноса»), но
раньше это число ПРЕДЛАГАЛОСЬ эвристикой `StructureCalc.suggestExtendedBaseSections
(screenHeightMm, screenWidthMm)` («для экрана до 3м — 1 секция, от 3.5м — 2, от 4.5м — 3,
+1 для очень широких») — по прямому указанию пользователя: *"аппаратно не получается его
просчитывать эффективно, будем указывать руками"*, эвристика признана ненадёжной и удалена
целиком.

Новое поле `Screen.structureBaseExtensionMm` (double, дефолт 500мм — одна каталожная
секция) — вводится напрямую в мм, спиннер «Вынос базы под балласт, мм» в
`SetupStagePanel` (заменил «Шаг башен» в том же месте формы). Число РЕАЛЬНЫХ секций
(`Screen.structureExtendedBaseSections`, персистентное поле, читается
`ScreenLogic.regenerateStructureCells` как и раньше) теперь ВЫВОДИТСЯ из мм-значения новым
`StructureCalc.extendedBaseSectionsFromOverhang(baseExtensionMm, sectionDepthMm)` (простое
`ceil(вынос / глубина модуля)`, не инженерная оценка — вся инженерная оценка теперь на
стороне пользователя) внутри `AppModel.updateScreenStructure`, переиспользуя ТОТ ЖЕ `frameW`,
что уже вычисляется там для `coreBaseSectionCount` (не считается заново).

### 3. Коэффициент балласта — редактируемый, дефолт 0.6 вместо жёсткого 1:1

Пользователь: *"для расчёта количества отгрузов вводим изменяемый коэффициент соотношения
отгруза к массе экрана. сейчас он 1:1, в реальности хорошо если 6:10"*. Новое поле
`Screen.structureBallastRatio` (double, дефолт 0.6 = 6:10) — `StructureCalc.compute()`
теперь считает `requiredBallastKg = ScreenLogic.stats(...).totalWeightKg() ×
screen.getStructureBallastRatio()` вместо жёсткого `= totalWeightKg()`. Спиннер «Коэфф.
отгруз/масса экрана» в `SetupStagePanel`, рядом с комбобоксом типа контейнера балласта.
«Отгруз» пользователя — то же самое понятие, что уже называлось «балласт» по всему
существующему коду/документации (контейнеры с песком, `StructureFrameType.kind ==
BALLAST_CONTAINER`) — переименования не делалось, только сам коэффициент стал полем, не
константой.

### 4. Высота башни автоматически приравнивается к высоте экрана; предупреждение — строго выше, не `>=`

Пользователь: *"высота башни автоматически приравнивается к высоте экрана, если высота
башни == экрану, то расчет производим, если выше - выдаем предупреждение"*. Раньше
`Screen.structureTowerHeightMm` был свободным полем с фиксированным дефолтом 3000мм, а
`Result.exceedsScreenHeightWarning()` предупреждал уже при РАВЕНСТВЕ (`towerHeightMm >=
screenHeightMm`, комментарий в коде прямо гласил «строго меньше — равно уже нарушение») —
то есть нормальный, ожидаемый случай (башня вплотную под экран) раньше ошибочно считался
поводом для тревоги.

Новый `StructureCalc.suggestTowerHeightMm(screen, type) = screen.getRows() ×
type.getHeightMm()` — `SetupStagePanel` вызывает его при КАЖДОМ выборе экрана в форме,
подставляя результат в спиннер «Высота башни, мм» ВМЕСТО ранее персистированного значения
(фолбэк на персистированное — только если тип кабинета не резолвится). Поле остаётся
редактируемым — пользователь по-прежнему может вручную поднять его выше. Граница
предупреждения изменена с `>=` на строго `>` (`compute()`): равенство — теперь нормальный
автоматический случай, предупреждение только если башня РЕАЛЬНО выше экрана.

### Тесты

(новый, заменил удалённый `suggestExtendedBaseSectionsGrowsForTallOrWideScreens`),
`requiredBallastApproximatelyEqualsScreenWeightAtRatioOne` (переименован, явно

## Round 18 — баг-репорт того же дня: пересчёт "не менял модель" (2026-08-19)

Пользователь: *"калькулятор должен держать в памяти свои стартовые значения и сравнивать
с текущими. если текущие изменились (пользователь их изменил) то кнопка предварительного
расчёта должна перерасчитывать конструктив под пользовательские параметры и изменять
модель. сейчас как минимум модель после перерасчёта не меняется"*.

**Диагностика**: написан временный (не оставлен в дереве тестов) прямой прогон
`AppModel.updateScreenStructure(...)` дважды подряд с разными `baseExtensionMm`/
`ballastRatio` — персистентные поля `Screen` менялись КОРРЕКТНО между вызовами (в т.ч.
число реально сгенерированных ячеек базы). То есть слой данных/сервиса работал верно —
баг был именно в UI-слое `SetupStagePanel`, причём КОНКРЕТНО в собственной правке этой же
сессии (Round 17, п.4 выше).

**Реальная причина**: `AppModel.updateScreenStructure` вызывает `changed()`, который через
`model.addListener(this::rebuild)` асинхронно (через `SwingUtilities.invokeLater`) заново
вызывает `doRebuild()` — ту же функцию, что заполняет ВСЕ поля формы из текущего экрана
при его выборе. Блок высоты башни (Round 17, п.4) БЕЗУСЛОВНО пересчитывал
`StructureCalc.suggestTowerHeightMm(...)` на КАЖДЫЙ такой ребилд — то есть сразу после
того, как пользователь ввёл своё значение и нажал «Рассчитать» (сам пересчёт СОХРАНЯЛ его
значение корректно), тот же самый клик вызывал `changed()` → `doRebuild()`, который тут же
МОЛЧА откатывал поле формы обратно на авто-подсказку. Пользователь видел: ввёл число →
нажал «Рассчитать» → поле снова показывает прежнее авто-значение → выглядит так, будто
правка не сохранилась (реально сохранялась, но тут же маскировалась следующим ребилдом;
если бы пользователь нажал «Рассчитать» ЕЩЁ раз, второй клик сохранил бы уже откаченное
авто-значение, а не исходную ручную правку — то есть от повторных нажатий модель
действительно застревала на авто-значении).

**Исправление** (SetupStagePanel, блок заполнения формы): авто-подсказка высоты башни
(`StructureCalc.suggestTowerHeightMm`) применяется теперь ТОЛЬКО если у экрана ЕЩЁ НЕТ ни
одной сгенерированной ячейки конструктива (`scr.getStructureFrameCells().isEmpty()`) — то
есть только один раз, для СОВСЕМ НОВОГО экрана, ни разу не считавшегося. Как только «Рассчитать»
хоть раз отработал (ячейки появились), поле дальше всегда показывает ПЕРСИСТИРОВАННОЕ
значение `scr.getStructureTowerHeightMm()` — тем же способом, каким уже работали все
остальные поля формы (`pRiggingPoints`, `pCols` и т.д.). Это и есть буквальная реализация
того, что описал пользователь: калькулятор «держит в памяти» стартовую авто-подсказку
только на старте, а дальше уважает то, что реально сохранено (в т.ч. то, что пользователь
только что ввёл и подтвердил кнопкой) — без отдельного механизма сравнения "было/стало",
достаточно того, что персистентное значение больше НЕ перезаписывается вычисляемым.

**Второй, смежный баг, найденный при разборе** (не то, о чём буквально просил пользователь,
но прямое следствие того же сценария): если 3D-окно (`Structure3DDialog`) уже ОТКРЫТО в
момент клика «Рассчитать конструктив», картинка не обновлялась — окно не подписано на
модель (`AppModel` не имеет `removeListener`, а новый `Structure3DPanel` создаётся при
каждом открытии окна заново, значит подписка копилась бы с каждым открытием/закрытием).
Добавлены `Structure3DPanel.refresh()`/`Structure3DDialog.refresh()` (просто
`gljPanel.repaint()` — рендер и так читает `Screen.getStructureXxxCells()` заново на
каждый кадр, ничего не кэширует) и явный вызов из `SetupStagePanel.calculateStructure()`
сразу после `updateScreenStructure(...)`, если диалог сейчас показан
(`structure3DDialog.isShowing()`).

Прямых Swing-тестов на `SetupStagePanel`/`Structure3DDialog` в проекте нет (стабильная
конвенция — см. секцию про `Structure3DPanel` выше, GL/форма проверяются вручную на живом
приложении, не юнит-тестами) — `mvn test` (274/274, регрессий в сервисном слое нет,
диагностический прогон в исходники не попал) плюс сборка+перезапуск для ручной проверки
пользователем.

## Round 19 — «вынос» = ПОЛНАЯ глубина базы (включая обязательную часть), не сверх неё (2026-08-20)

Баг-репорт пользователя на реальном проекте ДКФ (уличная сцена): ввёл «Вынос базы под
балласт» = 1500мм, но в 3D увидел заметно больше — «в модели построено 2.5, т.е. 2000
вынос». Разобрано двумя сообщениями подряд:

1. Прямая проверка сохранённых данных проекта (`~/.led-scheme/workspace.json`) показала,
   что расчёт был АРИФМЕТИЧЕСКИ верным для СТАРОЙ семантики: `structureExtendedBaseSections
   = 3` — ровно `ceil(1500/500)=3` доп. секции, как и ожидалось по формуле, действовавшей
   на тот момент. Разница была в том, что "ядро" ДО этого раунда занимало не 1, а 2 модуля
   (`coreBaseSectionCount = ceil(2×frameW/sectionDepthMm)`, покрывает оба ряда башни сразу)
   — то есть ПОЛНАЯ база выходила 2(ядро)+3(вынос)=5 модулей×500мм=2500мм, а пользователь,
   разглядывая экран СПЕРЕДИ (где глубина почти не читается), недосчитал/переоценил на глаз.
2. Пользователь сформулировал желаемое правило явно, двумя сообщениями: **"обязательная
   часть базы конструктива — строго 500мм, всё остальное считается выносом"**, и следом
   уточнение: **"значение выноса, которое вбивает пользователь, включает в себя значение
   основания"** — то есть 1500мм, которые он ввёл, ДОЛЖНЫ БЫТЬ равны ИТОГОВОЙ глубине базы
   целиком (обязательная часть + вынос), а не пониматься как "1500мм СВЕРХ обязательной
   части".

**Два самостоятельных изменения, реализованных вместе**:

1. **Обязательная часть базы зафиксирована как РОВНО 1 каталожный модуль**, независимо от
   того, сколько рядов вертикальных рам физически стоит на башне. `StructureCalc
   .coreBaseSectionCount(frameW, sectionDepthMm)` (вычислял `ceil(2×frameW/sectionDepthMm)`,
   обычно 2 модуля) УДАЛЁН целиком, заменён константой `StructureCalc
   .CORE_BASE_SECTION_COUNT = 1`. Физический смысл: раньше второй ряд башни получал опору
   "бесплатно" в составе обязательного минимума — теперь опора под ВТОРЫМ рядом тоже
   считается частью выноса и должна быть явно заложена пользователем в введённое значение
   мм, если она нужна.
2. **`extendedBaseSectionsFromOverhang(baseExtensionMm, sectionDepthMm)` сначала вычитает
   ровно 1 обязательный модуль** из введённого значения, и только оставшуюся часть переводит
   в целое число ДОПОЛНИТЕЛЬНЫХ каталожных секций (округление вверх, как и раньше). Если
   введённого выноса не хватает даже на обязательный модуль — 0 дополнительных секций (сама
   обязательная часть строится в любом случае, вне зависимости от этой формулы).

**Проверка на реальном сценарии из баг-репорта**: `baseExtensionMm=1500`, `sectionDepthMm=500`
→ `1500-500=1000` сверх обязательного → `ceil(1000/500)=2` доп. секции → ИТОГО
`1(обязательная)+2(доп.)=3` модуля × 500мм = **1500мм ровно** — теперь совпадает буквально с
тем, что ввёл пользователь, что и было целью правки (раньше при тех же входных 1500мм итог
был 2500мм — обязательная часть добавлялась СВЕРХ, а не входила В введённое значение).

**Затронутые места**: `AppModel.updateScreenStructure` (`coreBaseSectionCount` больше не
вычисляется через `frameW` — просто `StructureCalc.CORE_BASE_SECTION_COUNT`, передаётся в
`ScreenLogic.regenerateStructureCells` как раньше), `ui.Structure3DPanel` (`frameEnvelope`/
`reinforcementCandidates` — тот же переход с вычисляемого `coreBaseSectionCount(...)` на
константу). `ScreenLogic.regenerateStructureCells` САМА не менялась — как и раньше, просто
принимает `coreBaseSectionCount` обычным параметром, не зная, что именно передаёт вызывающая
сторона.

**Тесты**: `StructureCalcTest.coreBaseSectionCountCoversFullFrameDepthInWholeCatalogModules`
удалён (тестировал удалённый метод); `extendedBaseSectionsFromOverhangConvertsManualMmToWholeCatalogModules`
переименован в `extendedBaseSectionsFromOverhangSubtractsMandatoryModuleFirst` и переписан

## Round 24 — Ctrl-гейтинг добавления рам (баг-репорт, смёржено на master параллельно) — 2026-08-19

**Важная оговорка про историю этой записи**: в одной из более поздних сессий этот же
воркtree был по ошибке принят за место, где такой правки ещё не было (грепом по
`Structure3DPanel.java` на `ctrl`/`isControlDown` — ноль совпадений), и фича была
РЕАЛИЗОВАНА ЗАНОВО, дублируя уже смёрженный на `master` коммит `ae89119` — на самом деле
воркtree просто отстал от `master` на несколько коммитов (независимая сессия). При
подготовке релиза 2.2 (2026-08-20) обнаружено при попытке смержить ветку с `master`,
дублирующая реализация отброшена (`Structure3DPanel.java`/`Structure3DDialog.java`
возвращены к версии `master`), эта запись переписана под РЕАЛЬНЫЙ коммит.

**Настоящая причина** (из commit message `ae89119`, дословно): raycast тестировал
существующие стойки и "призраков" пустых ячеек ЗА ОДИН проход — pickBox призрака — это
весь номинальный объём ячейки (крупная коробка), у существующей стойки — узкие коробки
самих стоек (см. javadoc `Candidate`), поэтому объёмный призрак соседней пустой позиции
нередко оказывался БЛИЖЕ по лучу, чем тонкая стойка реальной рамы прямо под курсором — клик
по существующей раме, призванный её убрать, вместо этого иногда добавлял соседнюю. Не
"защита от случайных кликов" (так это было ошибочно описано в отброшенной дублирующей
версии этой записи), а исправление конкретного бага тай-брейка в raycast'е.

**Что изменилось**: клик по существующему элементу (прячет его) — без каких-либо
модификаторов, эта часть поведения не тронута. Добавление (клик по "призрачному" месту) и
сам показ призраков по наведению — теперь ТОЛЬКО с зажатым Ctrl: без Ctrl призраки не
рисуются и не участвуют в тесте луча вообще (`raycastAtCursor(..., existsFilter=true)` —
кандидаты-призраки физически исключены из списка, не просто визуально скрыты), с Ctrl —
показывается ближайший к курсору призрак и клик по нему добавляет элемент
(`existsFilter=false`). `handleClick`/`updateHover` получают `addMode` = `e.isControlDown()`
напрямую из `MouseEvent`, без отдельного `KeyListener` (тот же приём, что `Ctrl+колесо`-зум

## Изогнутые экраны и раздельные башни (`service.StructureCurveMath`) — запрос 2026-10-01

Ветка `claude/curve`. Только наземный конструктив (`mountType == STRUCTURE`); подвес
(RIGGED), фермы и круглые фермы изгибом НЕ затронуты — отложено пользователем до v3.0.
Развёрнутая ширина экрана, кабинеты, маски, сигнал, питание от изгиба не зависят.

### Терминология (важно для чтения кода)

«Башня» пользователя = ДВА столба вертикальных рам (передний + задний ряд), скреплённых
перемычками, плюс рамы основания между столбами. Ширина башни вдоль экрана — 1 м между
осями столбов, столб 51 мм → внешняя ширина `Wout = 1000 + 51 = 1051` мм; высота кратна
раме, глубина кратна 0,5 м (основание + вынос). В КОДЕ `towerIndex` ячеек — СТОЛБ, «шаг
башен» `StructureCalc.DEFAULT_TOWER_SPACING_MM = 1000` — расстояние между соседними
столбами. Стена (как было) — столбы через 1 м, перемычки/основание в КАЖДОМ промежутке,
две соседние башни пользователя делят средний столб (3 столба). Раздельные башни — 4
столба на 2 башни, между 2-м и 3-м зазор, соединений нет.

### Правило построения (решение пользователя)

- Изогнутый экран (вогнутый/выпуклый) — башни ВСЕГДА раздельные, зазор не меньше 500 мм
  (`StructureCurveMath.MIN_TOWER_GAP_MM`; меньшее значение поднимается до 500 и в форме, и
  в расчёте — `effectiveGapMm`).
- Прямой экран, зазор 0 — прежняя стена, код идёт старым путём (`separateTowers == false`,
  `regenerateStructureCells(..., null)`, в 3D преобразование `null`). Регрессия зафиксирована
  тестом (`StructureCurvedTowersTest.flatScreenWithZeroGapIsStillAWallWithUnchangedNumbers`).
- Прямой экран, зазор > 0 (≥ 500) — тоже раздельные башни, в ряд, без поворота.

### Модель (`Screen`, JSON с дефолтами)

`structureCurveType` (`ScreenCurveType`: FLAT по умолчанию / CONCAVE / CONVEX),
`structureCurveRadiusMm` (радиус к ЛИЦЕВОЙ поверхности, канонический; по умолчанию 10 м),
`structureCurveByAngle` (только UI: показывать угол между кабинетами вместо радиуса),
`structureTowerGapMm` (0 по умолчанию), `structureSeparateTowerCount` (число БАШЕН в
раздельном режиме, 0 = авто). Все — в `copy()` и `ScreenLogic.restore`.

**Число башен в старых проектах**: существующее `structureTowerCount` по-прежнему = число
СТОЛБОВ и в старых проектах трактуется так же (стена). Для раздельного режима — ОТДЕЛЬНОЕ
поле `structureSeparateTowerCount`; при расчёте `AppModel.updateScreenStructure` пишет в
`structureTowerCount` число столбов = 2 × n (n — пользовательское или авто), так что
3D/регенерация, читающие столбы, работают без изменений. Переосмыслять старое поле не
пришлось — прямой экран с зазором 0 открывается и считается как раньше.

**Отмена**: `ScreenLogic.restore` теперь возвращает новые поля ВМЕСТЕ с номинальными
границами сетки (`structureTowerCount`, сегменты, уровни, вынос, высота башни) и самими
ячейками конструктива — иначе после Ctrl+Z форма экрана «прямая», а ячейки остались бы от
раздельных башен. Побочный эффект (осознанный): Ctrl+Z теперь отменяет и клики по рамам
в 3D, и «Предварительный расчёт» — раньше отмена ячейки конструктива не трогала вовсе.

### Геометрия (`StructureCurveMath`, без Swing/GL)

Система координат плана — та же, что в 3D: x вдоль развёрнутого экрана `[0, W]`, z к
зрителю, лицевая поверхность в центре — `(W/2, 0)`. Вогнутый: центр кривизны `(W/2, +R)`;
выпуклый: `(W/2, −R)`.

- **Радиус ↔ угол**: `R = w / (2·sin(θ/2))`, `θ = 2·asin(w / 2R)` (w — ширина кабинета).
  Кабинеты ПЛОСКИЕ: их лицевые грани — хорды окружности R (`cabinetColumns`). Производные
  величины в подсказке: угол между кабинетами, дуга `cols·θ`, хорда `2R·sin(дуга/2)`,
  стрела прогиба `R·(1 − cos(дуга/2))`.
- **Тыльная поверхность** (d — глубина кабинета из `CabinetType.depthMm`, иначе 100 мм):
  вогнутый `Rb = R + d` (все точки кабинетов не дальше от центра), выпуклый —
  консервативно `Rb = √(R² − w²/4) − d` (середина тыльной грани плоского кабинета; на
  несколько мм меньше `R − d` из постановки — уточнение, а не отклонение: башня не задевает
  и плоский кабинет, не только идеальную дугу).
- **Зазор до экрана**: прежний `SCREEN_CLEARANCE_MM = 400` от ЛИЦЕВОЙ поверхности (теперь
  общая константа `StructureCurveMath`, 3D-панель ссылается на неё); от тыльной поверхности
  — `max(100, 400 − d)`. Прямой раздельный экран поэтому стоит на той же плоскости
  z = −400, что и стена.
- **Расстановка**: башни симметричны относительно центра экрана, шаг центров
  `Wout + зазор` по дуге тыльной поверхности (`φk = sk / Rb`, `sk = (k − (n−1)/2)·шаг`),
  каждая — жёсткий блок, повёрнутый на угол касательной (`yaw = −φ` у вогнутого, `+φ` у
  выпуклого; тот же знак, что `glRotate(yaw, 0, 1, 0)`).
  - Вогнутый: передняя плоскость касается окружности `Rb` СНАРУЖИ + зазор — заход в
    экран невозможен (расстояние от центра у всех точек ≥ `Rb + зазор`).
  - Выпуклый: касательная плоскость сдвинута назад на стрелу
    `e = Rb − √(Rb² − (Wout/2)²)` и ещё на зазор — углы передней плоскости внутри `Rb`.
- **Инвариант** «ни одна точка башни не в объёме экрана» проверяется и в плоских
  кабинетах (`insideScreenVolume`), и в кольцевой полосе R…R±d из постановки
  (`insideScreenAnnulus`) — тест на широкой сетке, плюс `analyze` проверяет его на каждом
  расчёте (предупреждение, если когда-нибудь нарушится).
- **Footprint башни** (`footprintLocal`): 2 столба на ВСЮ глубину (над выносом стоят
  усилительные рамы row 2) + все секции основания между ними. Глубина башни
  (`towerSpecOf`) — максимум из введённого выноса (`StructureCalc.totalBaseSections`),
  номинальной сетки и реально стоящих секций/усилительных рам.
- **Коллизии** (`collisions`): SAT по прямоугольникам footprint'ов ВСЕХ пар башен (касание
  — не пересечение). Минимальный зазор — бисекция по зазору от 500 мм (результат вверх до
  10 мм; NaN, если не помогает и 100 м — башня глубже центра кривизны выпуклого экрана, все
  башни сходятся в его окрестности); максимальная глубина при заданном зазоре — бисекция
  по глубине (+∞ у вогнутого/прямого). Ориентиры пользователя подтверждены тестом: выпуклый,
  башни вплотную — пересечение уже при одной секции для R до ~10 м; при подобранном зазоре
  — нет; вогнутый — башни расходятся веером. Ручная проверка: R = 4 м, глубина 2 м →
  минимальный зазор ≈ 1,49 м, при зазоре 0,5 м допустимая глубина ≈ 0,95 м. Зазор
  автоматически НЕ меняется — это параметр пользователя.
- **Край экрана** (информативно): если крайние башни выходят за развёрнутую ширину или
  не доходят до края больше чем на полшага — предупреждение.
- **Авто-число башен**: `⌊(длина тыльной поверхности + зазор) / (Wout + зазор)⌋`, ≥ 1.

### Расчёт ячеек и ведомость

`ScreenLogic.regenerateStructureCells(..., separateTowerSpansMm)`: в раздельном режиме башня
k = столбы 2k/2k+1, валидна целиком, если на её отрезке развёрнутой ширины
(`towerScreenSpanMm`) есть видимый кабинет НИЖНЕГО ряда (то же правило, что у столба стены);
перемычки и основание — только в промежутке 2k → 2k+1. `StructureCalc.compute` считает
железо тем же кодом (раздельность — в самих ячейках): 2 столба на башню, стаканы на
вертикальных стыках как раньше, балласт как раньше. Новое — `Result.curveWarnings`
(пусто у стены).

### 3D и picking (`ui.Structure3DPanel`)

Общий слой «локальная система башни»: кандидаты строятся ТЕМ ЖЕ кодом в координатах
стены, а `StructurePickMath.YawTransform` (anchor + поворот + сдвиг начала башни) переносит
раздельную башню на её место; рендер — `glPushMatrix/glTranslate/glRotate` вокруг каждого
кандидата и стаканов, picking — `intersectObb` (луч переводится в локальную систему,
`t` не искажается). У стены преобразование `null` — ровно прежние вызовы GL и
`intersectAabb`. В раздельном режиме нет перемычек/оснований и их призраков между
башнями и нет призрака «лишнего столба сбоку» (число башен задаётся в форме). Экран
изогнутого экрана — колонны повёрнутых кабинетов реальной глубины (клин-зазоры между
тыльными углами — как у настоящих плоских кабинетов); у прямого — прежние 15 мм.

### UI (`SetupStagePanel`, блок «Наземный конструктив»)

«Форма экрана», «Изгиб задан» (радиусом, мм / углом между кабинетами, °; при смене

### Что НЕ делается

   (передний/задний ряд), т.е. это разные перемычки. В текущих данных пользователя передние
   видимы (возвращены руками), задние скрыты (задний ряд у него из одной рамы 950 мм —
   перемычке на высоте 1425 мм там не к чему крепиться). `toggle*` дублей не создаёт: ищет
   запись по полному ключу и переключает `hidden` (тест
   `ctrlClickOnHiddenPeremychkaUnhidesTheSameRecordInsteadOfAddingANewOne`).
4. **Следы в данных**: скрытые верхние рамы заднего ряда ровно на 15 первых столбах (стена 14 м
   = 15 столбов), порядок записей основания (часть — в порядке ручных кликов, часть — в порядке
   регенерации, башни 7–8 в конце списка). Экран был стеной, отредактированной кликами, и потом
   пересчитан как вогнутый.

### Корень

Merge-not-overwrite (`ScreenLogic.regenerateStructureCells`, Phase 2) сохраняет записи, чей
ключ попадает в новые границы, КАК ЕСТЬ, вместе с `hidden`. Но у стены и у раздельных башен
одинаковые индексы — разные физические детали: у стены столб `t` стоит на `x = t·1000` и делит
соседние промежутки, перемычка `t` — между общими столбами `t`/`t+1`; у раздельных башен
перемычка `2k` — внутри башни `k` на её месте на дуге. При переходе «стена → раздельные башни»
записи чётных промежутков стены 0…12 со всеми ручными скрытиями переезжали в башни 0…6, а
«чистыми» (новые видимые записи) получались только башни 7–8, промежутков которых (14, 16) в
стене из 15 столбов не было, — ровно картинка со скриншота. Воспроизведено тестом
`switchingAnEditedWallToConcaveBuildsEveryTowerWithPeremychkiAndBase` и
`ui/Structure3DPanelSeparateTowersTest` (до правки кандидаты `exists` — только
`peremychka:14:*`/`16:*`).

### Исправление

- `AppModel.updateScreenStructure` (общий `applyScreenStructure`): режим «до» — по полям экрана,
  сохранённым вместе с ячейками прошлым расчётом (`StructureCurveMath.separateTowers(screen)`),

## Напольный каркас (`ScreenMountType.FLOOR`, `service.FloorCalc`) — 2026-10-01

Запрос пользователя 2026-10-01 (ветка `claude/floor`): калькулятор каркаса для
НАПОЛЬНОГО экрана — светодиодного пола, по которому ходят. Отдельный расчёт, НЕ
расширение башен: `StructureCalc`/`Structure3DPanel`/блок «Конструктив…» не менялись.

### Решения пользователя (дословно по постановке)

- Каркас — из ТЕХ ЖЕ рам библиотеки (`StructureFrameType.Kind.FRAME`, 950×500×51 мм), но
  лежащих ГОРИЗОНТАЛЬНО. Длинная сторона рамы = её `heightMm` в библиотеке, короткая =
  `widthMm`.
- Вдоль ДЛИННОЙ стороны соседние рамы (соседние ряды рам) стоят вплотную и скручиваются.
  Вдоль КОРОТКОЙ — соединяются стаканами (`Kind.CUP`); стакан добавляет зазор. Отсюда шаг
  рам: вдоль длинной стороны = длина + зазор стакана (950+50 = 1000 мм = 2 кабинета 500),
  вдоль короткой = ширина (500 мм = 1 кабинет).
- Любой стык двух рам = 2 болта. Стаканы — 2 на стык по короткой стороне; по длинной
  стороне стаканов нет. «Метизы» = только болты.
- Ножек строго 4 на раму, без экономии на общих углах. Высота ножки в расчёте НЕ
  участвует.
- Зубы (фиксаторы кабинета к раме) — настройка пользователя на экран, 2/3/4 на кабинет
  (по умолчанию 4), только для кабинетов, под которыми есть рама.
- Хвост ряда, не кратный раме, — лишняя рама НЕ ставится и не считается, кабинеты без
  опоры подсвечиваются ОРАНЖЕВЫМ на 2D-плане и перечисляются в результате.
- Нагрузка — СРЕДНЯЯ кг/м² по экрану, без пределов и предупреждений.
- Ножки и зубы в библиотеку пока НЕ заносятся (только заготовка, см. ниже).
- Правка того же дня: число стыков — вспомогательная информация калькулятора. Оно есть
  в результате и в окне «Рассчитать пол», но в XLSX-спецификацию НЕ выводится — там только
  позиции: рамы, стаканы, болты, ножки, зубы.

Пример пользователя: экран 14×6 кабинетов 500×500 (7000×3000 мм) → 7 рам в ряду × 6 рядов
= 42 рамы; 36 стыков по короткой стороне (72 стакана), 35 по длинной, болтов
2×(36+35) = 142, ножек 168, зубов 336 при 4 на кабинет (168 при 2).

### Ориентация и число кабинетов на раму

Длинная сторона рамы идёт вдоль ШИРИНЫ экрана (колонки кабинетов, ось X), короткая — вдоль
глубины (ряды кабинетов, ось Y) — так получается пример пользователя (7 рам в ряду). Число
кабинетов на раму считается из размеров, не зашито 2×1:
`cabinetsPerFrameX = round((длина рамы + зазор стакана) / ширина кабинета)`,
`cabinetsPerFrameY = round(ширина рамы / высота кабинета)`, не меньше 1. Если шаг отличается
от целого числа кабинетов больше чем на `FloorCalc.PITCH_TOLERANCE_MM` (10 мм) — расчёт идёт
с округлением, в результат пишется предупреждение.

Источники размеров: рама — `Screen.structureFrameTypeId` (фолбэк 950×500, тогда вес рам в
нагрузке не учитывается и есть предупреждение); зазор стакана — `heightMm` записи
`Screen.structureCupTypeId` (та же ось, по которой стакан наращивает башню), иначе константа
`FloorCalc.DEFAULT_CUP_GAP_MM` = 50 мм.

### Правила расстановки (алгоритм)

1. Ряды кабинетов группируются в полосы по `cabinetsPerFrameY` (для кабинета 500×500 — по
   одному ряду). Неполная нижняя полоса рам не получает, её видимые кабинеты неопёртые.
2. В каждой полосе идём слева направо по НЕПРЕРЫВНЫМ цепочкам колонок, где все кабинеты
   полосы видимы. Скрытые кабинеты формы экрана в каркасе не участвуют и рвут цепочку.
3. Цепочка режется на рамы по `cabinetsPerFrameX` от её левого края; хвост короче рамы —
   неопёртые кабинеты.
4. Стык по короткой стороне — соседние рамы ОДНОЙ цепочки (встык). Через скрытый кабинет
   стыка нет.
5. Стык по длинной стороне — рамы СОСЕДНИХ полос, чьи отрезки колонок перекрываются на
   длину > 0. Полосы независимы, поэтому при сдвинутых цепочках одна рама может стыковаться
   с двумя рамами соседнего ряда — это две пары, по 2 болта каждая.
6. Кабинеты рисуются и считаются по номинальной сетке; ручные смещения отдельных кабинетов и
   переопределение типа по ячейке на расстановку не влияют (вес — влияет, через
   `ScreenLogic.stats`).

### Формулы

- рам = число размещённых рам; ножек = 4 × рам;
- стаканов = 2 × стыков по короткой стороне;
- болтов = 2 × (стыков по короткой + стыков по длинной);
- зубов = зубов на кабинет × опёртых кабинетов;
- средняя нагрузка, кг/м² = (вес видимых кабинетов по `ScreenLogic.stats(...).totalWeightKg()`
  + вес рамы из библиотеки × рам) / площадь видимых кабинетов. Площадь — по видимым
  кабинетам (а не по прямоугольнику `cols×rows`), т.к. скрытые кабинеты — это не пол.
  Вес стаканов/болтов/ножек/зубов не учитывается — его нет в библиотеке.

библиотеки, рама центрирована в своём отрезке кабинетов — между рамами ряда остаётся зазор
стакана), стаканы — красные, по 2 на стык короткой стороны в зазоре на линии рельсов, плитки
кабинетов (`FloorPickMath.DISPLAY_CABINET_THICKNESS_MM` = 80 мм, верх — цвет маски экрана,
неопёртые — оранжевые `FloorPlanPanel.UNSUPPORTED_FILL`), зубы — маленькие светлые метки по
углам опёртых кабинетов (4 — все углы, 3 — три, 2 — диагональ) на верхней поверхности. Флажок
«Кабинеты» прячет плитки (видны рамы/стаканы/зубы на рамах). Скрытые кабинеты формы не
рисуются. Камера: перетаскивание ЛКМ или ПКМ — орбита (смещение > 4 px — вращение, иначе
клик — приём Phase 2), средняя — сдвиг в плоскости пола, колесо — зум; кнопки «Сверху/
Спереди/Сбоку/3/4». Без GL — та же заглушка «3D недоступно на этой системе», что у
конструктива (конструктор ловит `Throwable`; в headless и при `tryGl=false` GL не пробуется).

**Редактирование — как у конструктива (Phase 2 + Round 24).** Клик по раме (или по плитке над
ней) — `AppModel.toggleFloorFrameCell` прячет её; наведение без Ctrl обводит красным раму,
которую уберёт клик. С зажатым Ctrl под курсором — зелёный «призрак» допустимой позиции,
Ctrl+клик возвращает/добавляет раму; без Ctrl призраки в выбор не попадают вовсе. Правка — своя
запись отмены; разрешена только для ТЕКУЩЕГО экрана (снимок отмены берётся с него), иначе —
подсказка в строке состояния окна. Недопустимая позиция ничего не меняет и не пишет отмену.

**Picking (`service.FloorPickMath`, без GL).** Пол плоский, поэтому вместо AABB-теста по каждой
раме луч камеры пересекается с горизонтальной плоскостью верхней поверхности (верх плиток, если
они показаны, иначе верх рам — `topSurfaceY`), точка переводится в план. `pickTarget`: без Ctrl
— видимая рама, в отрезок кабинетов которой попала точка (зазор стакана — не «мёртвая зона»);
с Ctrl — из `FloorCalc.addablePositions` позиция, накрывающая точку, с ближайшим центром (левая
половина кабинета — рама с колонки левее, правая — с этой колонки: так раму можно сдвинуть на
кабинет).

**Модель — `Screen.floorFrameCells: List<model.FloorFrameCell>`** (клиентский класс,
`ledscheme-model` не менялся): `row` (начало полосы рам), `col` (первая колонка), `hidden`,
`manual`. Размер рамы в кабинетах не хранится — выводится из текущих рамы/стакана/кабинета.
`copy()` и `ScreenLogic.restore` копируют список глубоко (Ctrl+Z корректно откатывает правки —
`restore` исторически пропускает многие поля, для этого списка сделано явно). Старый JSON без
поля — пустой список.

**Допустимая позиция** (`FloorCalc.Layout#isValidPosition`): ряд кратен кабинетам на раму по
глубине, рама целиком в сетке, все её кабинеты видимы. Рамы не перекрываются.

**Merge-not-overwrite (`FloorCalc.mergeCells`)** — действующий список = ручные записи
(`manual` или `hidden`) в допустимых позициях (видимые не перекрываются; спрятанная, накрытая
видимой, отбрасывается) + автоматические позиции, не занятые и не перекрывающие ручные записи
(на позиции со спрятанной записью рама так и остаётся спрятанной — убранная рама делает свои
кабинеты неопёртыми, ожидаемо). НЕручные записи каждый раз генерируются заново — это и есть
отличие от конструктива (у него границы — числа, у пола — сама форма экрана): после правки
формы нетронутые участки пересчитываются, как до редактора (не повторяется класс бага Round 18
«пересчёт не менял модель»). Записи вне новой сетки отбрасываются. Операция идемпотентна.
`FloorCalc.compute` ВСЕГДА считает по `effectiveCells` (= merge сохранённого списка с текущей
автоматикой) — поэтому спецификация и 2D-план сразу видят и правки формы, и ручные правки, а
без ручных правок результат в точности прежний. «Рассчитать пол»
(`AppModel.updateScreenFloor`) сохраняет действующий список на экран (старый проект получает
список впервые). `FloorCalc.toggle` перед правкой материализует действующий список; возврат
рамы на позицию автоматики снимает `manual`, новая рама вне автоматики — `manual=true`;
спрятанные записи, накрытые новой рамой, удаляются.

**Стыки по ячейкам**: короткая сторона — две видимые рамы одной полосы ВСТЫК (`colEnd ==
col`), между ними не должно быть ни убранной рамы, ни скрытого кабинета; длинная — рамы
соседних полос с перекрытием > 0 (как раньше). Для чистой автоматики — те же числа, что до
редактора (все прежние тесты `FloorCalcTest` прошли без изменений).

Тесты — `service/FloorFrameCellsTest` (8), `service/FloorPickMathTest` (4),
`ui/FloorPlanViewPanelTest` (4), см. TESTS.md. Сам GL-рендер не покрыт (конвенция проекта для
