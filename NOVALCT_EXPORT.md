# Экспорт NovaLCT — детальный гид для агента

Отдельный документ (не часть `CLAUDE.md`, см. ссылку оттуда в секции 5) — эта
фича полностью reverse-engineered (NovaStar/Xixun формат нигде не
задокументирован официально), и в коде накоплен большой объём выводов из
разбора реальных сэмплов, которые легко потерять при поверхностном чтении.
Цель файла — чтобы следующий агент, которому дадут задачу по этой фиче, не
переоткрывал те же выводы заново и не наступил на уже известные грабли.

**Как читать этот файл**: секции 1–6 — что есть и как устроено (для
понимания перед правкой). Секции 7–9 — что НЕ доделано/не подтверждено
(отсюда начинать, если задача — «улучшить/доделать NovaLCT»).

## 1. Что это и зачем

NovaLCT — проприетарное ПО NovaStar/Xixun для настройки светодиодных
контроллеров. Приложение экспортирует файл-пресет (`.scr`), который
инженер импортирует прямо в NovaLCT, чтобы не вбивать раскладку
кабинетов/портов руками ещё раз. Формат бинарный, нигде официально не
описан — вся структура ниже восстановлена (a) побайтовым сравнением
сэмплов, отличающихся ровно одним параметром, и (b) декомпиляцией (ildasm)
реальной NovaLCT, установленной у пользователя — конкретно
`Nova.LCT.GigabitSystem.HWConfigAccessor.Accessors.CommonInfoAccessor
.SoftWareSpaceAnalyser` (методы `CaculateCRC` и `ScreenInfoToArray1600`).
Это не теория, а подтверждённый разбор чужого бинарника — при сомнениях в
формате доверяй коду и его комментариям больше, чем интуиции.

## 2. Карта файлов

**Экспорт (единственный путь, реально доступный из UI):**

| Файл | Роль |
|---|---|
| `ui/NovaLctControllerExportDialog.java` | Точка входа: диалог-оркестратор — выбор контроллера, разрешение кабинетов, ветвление одиночный/combine/separate, сохранение `.scr`, опционально следом скачивание `.rcfgx`. |
| `ui/LctPresetMasterDialog.java` | «LCTPresetMaster» — редактор раскладки экранов при мультиэкранном контроллере (визуально имитирует панель Basic Information самой NovaLCT). |
| `service/NovaLctScrWriter.java` | Сам бинарный писатель `.scr` — Standard Screen, Complex Screen, мультиэкранный (экспериментальный) форматы. Это ядро фичи. |
| `service/NovaLctControllerResolver.java` | Собирает ВСЕ кабинеты по всем экранам сцены, расключённые через ОДИН конкретный контроллер. |
| `service/NovaLctCombineHelper.java` | Объединяет несколько разрешённых экранов в один виртуальный Standard-Screen грид (или оставляет раздельными). |
| `service/ScreenLogic.java` | Сквозные геометрия/порты, используются писателем: `isUniformRectangularGrid`, `cardAndLocalPort`, `effectiveType`, `offsetPx`. |
| `ui/CabinetConfigPickerDialog.java` | Не сам экспорт, но диалог «скачать конфиг приёмной карты (.rcfgx)», предлагаемый после экспорта. |
| `ui/MainMenuBar.java` | Единственная точка входа в меню (см. секцию 3). |

архитектурная граница, см. секцию 6.

## 3. Точка входа и порядок проверок в UI

Единственная точка входа во всём приложении: меню Инструменты → «Экспорт
NovaLCT для контроллера…» (`MainMenuBar.java`). Ни одна панель этапов
(`PowerStagePanel`/`SignalStagePanel`) кнопки экспорта не содержит.
Предыдущий, экранно-центричный диалог `NovaLctExportDialog` **полностью
удалён** — не существует в дереве, только упоминается в комментариях.

`NovaLctControllerExportDialog.showExportFlow` — последовательность (важен
именно порядок, каждый шаг может прервать поток):

1. Нет ни одного контроллера в сцене → предупреждение, стоп.
2. Пользователь выбирает контроллер, подтверждает (Cancel → стоп).
3. Резолвер вернул пустой список → предупреждение «нечего экспортировать»,
   стоп.
4. Ветвление по числу затронутых экранов (`involvedScreens.size()`):
   - `== 1`: прямой путь через `NovaLctScrWriter.write` (побайтово идентичен
     подтверждённому одноэкранному писателю).
   - `> 1`: пользователь выбирает Combine/Separate (Cancel → стоп); если
     Separate — **отдельное явное предупреждение об экспериментальности**
     (отказ → стоп). Затем обязателен непустой результат из
     `LctPresetMasterDialog` (Cancel → стоп).
5. Предупреждение о нерасключённых кабинетах — если на затронутом экране
   есть кабинет, не покрытый резолвером ЭТОГО контроллера (либо реально не
   расключён, либо расключён через ДРУГОЙ контроллер той же сцены) —
   пользователь может отказаться и прервать.
6. Диалог сохранения файла — Cancel прерывает тихо; ошибки записи ловятся и
   показываются, не проглатываются молча.
7. `.rcfgx` предлагается скачать **только** если экран был ровно один —
   при объединении/разделении разных экранов они могут быть разных типов
   кабинета, гадать какой предлагать было бы неправильно (это осознанное
   решение, не пропущенный случай).

## 4. Формат `.scr` — бинарная структура

НЕ XML/текст (кроме одного встроенного JSON-фрагмента). Магические байты
`"DSCI"`. Все многобайтовые числа — little-endian. Три структурно разных
варианта под одним расширением `.scr`, у всех общий preamble/checksum-контейнер
(~340 байт).

### Standard Screen (`writeStandardCore`)
Используется, когда `ScreenLogic.isUniformRectangularGrid` возвращает
`true` (нет скрытых ячеек, свободных офсетов, разнотипных ячеек).

- Фиксированный заголовок 340 байт (`HEADER_LEN = 0x154`), большинство полей
  — подтверждённые побайтово константы (не выдумка, см. код —
  многочисленные `header[0x..] = 0x..` с комментариями типа «константа во
  всех однокэранных сэмплах»).
- Перед каждой 17-байтовой записью кабинета и перед хвостовым JSON —
  6-байтовый «якорь»: `{0x00, cabW&0xff, 0x00, cabH&0xff, 0x00, 0x01}` —
  раньше ошибочно считался константой `00 80 00 80 00 01`, на деле это
  пиксельные ширина/высота кабинета (однобайтовые, т.к. кабинеты <256px).
- Записи кабинетов идут **в порядке столбец-за-столбцом (column-major)**,
  НЕ построчно — подтверждено сравнением с реальным сэмплом 4×3, где
  построчный порядок давал верные байты, но неверный порядок записей.
- **Ячейка (0,0) никогда не пишется отдельной записью** — её «номер
  приёмной карты» (seq) хранится прямо в заголовке, поле `0x14b`. Раньше
  считалось, что это выводимая формула — «случайно совпадало на 2 из 3
  сэмплов», реальный источник — прямой баг-репорт «неверный номер именно
  у ячейки (0,0)».
- Хвост: якорь ещё раз, 2-байтовая длина, затем ASCII JSON-массив
  warp-координат на экран (сейчас всегда один элемент с нулевыми
  искажениями — реальный warp не поддерживается/не нужен).
- Две контрольные суммы — **простая сумма байт по модулю 65536**, НЕ
  полиномиальный CRC, несмотря на название полей (подтверждено
  декомпиляцией `CaculateCRC`). Порядок вычисления важен: внешняя сумма
  включает уже пропатченные байты внутренней.
- `TAIL_FOOTER` — фиксированный блок 173 байта в конце, в основном нули.
  Обнаружен потому, что БЕЗ него настоящая NovaLCT отказывалась грузить файл
  («Failed to load screen information file!»).

### Complex Screen (`writeComplex`)
Используется, когда грид неоднородный (скрытые ячейки/свободные
офсеты/разнотипные ячейки).

- Тот же preamble/checksum-механизм, что у Standard (это было отдельным
  открытием, не очевидно с первого взгляда), но короче — `COMPLEX_HEADER_LEN
  = 0x13f`.
- После заголовка: `Type=2` (у Standard `Type=1`, тот же контейнер
  `ILEDDisplayInfo`, другой подвид), `VirtualMode=0`, `Count` (u32).
- 16-байтовая запись на кабинет с явной пиксельной геометрией (X/Y/Width/
  Height), а не индексами грида — см. код для точной раскладки полей.
  `XInPort`/`YInPort` в обоих реальных сэмплах были 0 — смысл ненулевых
  значений неизвестен.
- Хвостовой JSON тут всегда пустой массив `"[]"`.

### Мультиэкранный (`writeStandardMultiScreen`) — статус: ПОЛНОСТЬЮ ПОДТВЕРЖДЕНО
Пакует несколько независимых Standard-Screen-подобных блоков (НЕ слитых в
один грид — в отличие от Combine, см. секцию 5) в один файл. Раньше (до
сессии 2026-08-09) — best-effort по единственному вырожденному образцу с
двумя ПУСТЫМИ экранами. Пользователь подготовил и сохранил из реальной
NovaLCT 4 НЕПУСТЫХ многоэкранных образца (2, 3 и 2 экрана, включая случай с
двумя РАЗНЫМИ физическими Sending Card) — байтовый разбор вскрыл, что
прежняя best-effort модель была неверна в трёх местах (расположение и
содержимое сдвиговой зоны, раскладка полей компактного блока, абсолютность
координаты в записи кабинета), сейчас всё подтверждено точно и покрыто
golden-байтовыми тестами (`NovaLctMultiScreenWriterTest`). Подробности —
javadoc `NovaLctScrWriter.writeStandardMultiScreen`, не дублируются здесь.

## 5. LCTPresetMaster и мультиэкранный контроллер

Два РАЗНЫХ понятия, оба зовутся «мультиэкранными» — не путать:

**a) Complex Screen** (секция 4) — это выбор ПОДФОРМАТА для ОДНОГО экрана,
зависит только от того, однородный ли у него грид. К охвату контроллером
нескольких `Screen` отношения не имеет.

**b) Контроллер, покрывающий несколько экранов** — реальный смысл вопроса.
Существует потому, что порты одного контроллера физически могут быть
разведены на кабинеты, лежащие на РАЗНЫХ объектах `Screen` одной `Scene`.
Определяется на лету при экспорте: резолвер собирает `involvedScreens` из
фактически затронутых экранов, ветвление `== 1` vs `> 1` — единственный
признак, отдельного поля в модели «этот контроллер мультиэкранный» нет.

**LCTPresetMaster** (`LctPresetMasterDialog`) — UI размещения экранов,
показывается только в мультиэкранном случае. Мотивация из javadoc класса:
более раннюю попытку использовать существующий `ContentCanvas` (пиксельный
инструмент, сделанный для позиционирования экранов под видеоконтентом) как
редактор размещения для NovaLCT-combine — реальная ошибка загрузки в NovaLCT
при объединении экранов разной высоты через этот канвас. Настоящая причина
той ошибки оказалась не в канвасе (см. ниже про blank-механизм), но
отдельно было решено, что канвас — не тот инструмент: combine нуждается в
дискретной сетке ячеек (Колонки/Строки, как в самой панели Basic
Information NovaLCT), а не в произвольном пиксельном позиционировании.
LCTPresetMaster визуально имитирует именно эту панель NovaLCT.

Два пути после обнаружения мультиэкранности, выбор пользователя:
- **Combine** (`NovaLctCombineHelper.combine` →
  `NovaLctScrWriter.writeStandardCombined`) — сливает ВСЕ затронутые экраны в
  один виртуальный Standard-Screen грид, безусловно. Рекомендуемый путь,
  подтверждён и на вырожденном случае, и на реальном сэмпле.
- **Separate** (`splitSeparateGrouped` → `writeStandardMultiScreen`) —
  писатель подтверждён (см. секцию 4). C 2026-08-09 поддерживает
  ГРУППИРОВКУ: в `LctPresetMasterDialog` Ctrl+клик по размещённым экранам
  выбирает несколько, кнопка «Группировать» присваивает им общий id —
  такие экраны сливаются в ОДИН NovaLCT-экран (тем же blank-механизмом, что
  и `combine`, но в границах группы, а не всей сетки), реальный кейс
  «несколько экранов проекта → один из НЕСКОЛЬКИХ NovaLCT-экранов» (например:
  2 экрана слиты в screen 0, ещё один экран — отдельный screen 1). Экран без
  явной группы — как и раньше, свой собственный NovaLCT-экран
  (`splitSeparateGrouped` с пустой/`null` картой групп даёт РОВНО то же самое,
  что старый `splitSeparate`, который оставлен нетронутым и по-прежнему
  покрыт тестами). Golden/структурные тесты — `NovaLctCombineHelperTest`
  (`splitSeparateGrouped_*`).

**Механизм «дырок» (blank cells)** в `combine`/`splitSeparateGrouped`: любая
ячейка внутри общего бокса (всей сетки — для `combine`, bounding box ГРУППЫ —
для `splitSeparateGrouped`), не покрытая НИ ОДНИМ размещённым экраном,
получает синтетическую запись с `card=0xFF (255)` — подтверждённый (не
выдуманный) сентинел «нет карты» у самой NovaLCT, вычленен побайтовым
разбором реального файла `111.scr`, сохранённого самой NovaLCT (несколько
экранов одного типа кабинета, объединённых внутри одного NovaLCT-экрана).
Это ОТЛИЧАЕТСЯ от ячейки реального экрана без расключённой цепочки — такая
просто не пишется вовсе, как и в одноэкранном писателе.

## 6. Маппинг доменных понятий → числа NovaLCT

Цепочка трансляции (важно для любой правки нумерации портов/карт):

1. `SignalChain.getPortNumber()` — **сквозной по сцене** номер порта
   (1-based по всем контроллерам сцены, в порядке `controllersInScene`).
2. `AppModel.portOffsetOf(Scene, ControllerInstance)` — сумма
   `ControllerType.effectivePortCount()` всех контроллеров ДО целевого в
   порядке сцены → даёт офсет для перевода в локальный для контроллера
   номер порта.
3. `ControllerType.ethernetPoolLocalPort(int controllerLocalPort1Based)` —
   переводит локальный номер порта в пару `(индекс карты 0-based, номер в
   пуле)`, ПОЛНОСТЬЮ пропуская не-Ethernet (fiber) группы портов — fiber
   возвращает `null` и не попадает в экспорт (это магистральные линии
   между устройствами, не финальные кабинеты). Именно тут порядок карт/
   портов берётся из групп `SchemaCard`/`CardPort` контроллера, в порядке
   объявления.
4. `NovaLctControllerResolver.resolve` — обходит цепочки сцены, фильтрует
   по попаданию порта в диапазон контроллера, переводит через шаги 2–3,
   идёт по `chain.getCabinetInstanceIds()` присваивая `seq` (0-based
   позиция В СВОЕЙ цепочке), находит реальный `Screen` кабинета (может
   отличаться от экрана, где физически «числится» контроллер — резолвер
   сканирует ВСЕ экраны сцены).
5. Row/col — напрямую из `CabinetInstance.getRowIndex()`/`getColIndex()`
   без трансформации (Standard Screen). Для Complex Screen — пиксель
   X/Y = номинальная позиция грида ПЛЮС свободный офсет
   (`CabinetInstance.offsetXMm/offsetYMm`, переведённый мм→px через
   `ScreenLogic.offsetPx`).
6. **Резолвер контроллера намеренно НЕ использует `ScreenLogic
   .cardAndLocalPort`** — та функция суммирует только `screen.getControllers()`
   ОДНОГО экрана, что даёт неверный офсет, если контроллер физически
   «числится» под ДРУГИМ экраном той же сцены. Резолвер напрямую зовёт
   `AppModel.portOffsetOf(Scene, ControllerInstance)`, т.к. контроллер уже
   известен явно.
7. `firstCard`/`firstPort` в заголовке берутся из первой РЕАЛЬНОЙ (не
   `0xFF`-заглушки) записи в column-major порядке — код явно защищается от
   выбора blank-сентинела как дефолта заголовка (иначе NovaLCT показала бы
   «Sending Card 256» для объединённых гридов с дыркой в первом столбце).

## 7. Уже обработанные edge cases (не переоткрывай)

- Нерасключённые кабинеты на затронутом экране — детектируется, включая
  случай «расключён, но через другой контроллер той же сцены».
- Несовпадение физического размера кабинета между объединяемыми экранами —
  `NovaLctCombineHelper.validateSlots` отклоняет combine.
- Перекрытие размещений экранов (одна ячейка занята дважды) — отклоняется
  явно, это НЕ то же самое, что дырка, и не поддерживается.
- Экраны разной высоты рядом друг с другом — explicitly ДОПУСКАЕТСЯ,
  заполняется дырками (это исправление более раннего ошибочного
  допущения — см. регрессионный тест на эту тему).
- Дефолт card/port заголовка обязан пропускать blank-сентинел (секция 6,
  п.7).
- Порядок выбора первой карты — детерминированный через column-major
  ИТЕРАЦИЮ, не порядок `HashMap` — важно для контроллеров с несколькими
  картами/портами на разных ячейках одной объединённой сетки.

## 9. Известные проблемы / неподтверждённые места — приоритет для будущей работы

Литеральных `TODO`/`FIXME` в коде нет — вместо этого используется явный
русскоязычный hedge-язык в javadoc («ДОГАДКА», «не подтверждено», «best-
effort»). Собранный список:

1. **`writeStandardMultiScreen` — ПОДТВЕРЖДЁН на 4 реальных образцах
   (2026-08-09)**, был best-effort до этой сессии. Группировка экранов проекта
   в один из нескольких NovaLCT-экранов — тоже реализована (2026-08-09,
   `splitSeparateGrouped` + Ctrl+клик/«Группировать» в `LctPresetMasterDialog`,
   см. секцию 5). **Сессия 2026-08-10** прогнала реальную загрузку (и краш, и
   успешные раунды байт-в-байт сверки с образцом, сохранённым САМОЙ NovaLCT
   для конфигурации Left+Center+Right, Center на 2 портах одной карты) и нашла
   три реальных бага (все исправлены):
   - **Порядок экранов** (`NovaLctCombineHelper.SCREEN_ORDER`) — раньше
     сортировался по пространственному `screenXPx` ("экран 0 — самый левый"),
     реальная NovaLCT требует сортировку по возрастанию (Sending Card, Port)
     первой записи экрана — иначе `LoadFromFile` отклоняет файл целиком.
   - **Нумерация Sending Card** (`ControllerType.hasEthernetOutput` +
     переработанные `ethernetPoolCount`/`ethernetPoolLocalPort`/`globalPortFor`)
     — карты без единого выходного Ethernet-порта (входные карты, типичны для
     Novastar H-серии) раньше всё равно занимали номер в нумерации; реальная
     NovaLCT нумерует ТОЛЬКО отдающие карты, с 1, входные карты в счёт не идут.
   - **Blank-записи** (`buildGroupBlock`) — port/seq у синтетических
     card=0xFF-записей должны быть 1/1, а не 0/0 (само значение card=0xFF было
     верным и раньше).
   - **Всё ещё НЕ решено**: последний байт 6-байтового якоря (см. javadoc
     {@code buildAnchor}) и два байта заголовка (0x13c, 0x140) в области
     "сдвиговой зоны" — у реального образца эти поля не совпадают с
     подтверждённой для одноэкранного случая константой (anchor[5]=0x01
     всегда), но и не сводятся к простой гипотезе "относится к blank-записям"
     (та проверена и опровергнута тем же образцом — 0xFF стоит у ЧАСТИ
     не-blank записей на границе колонок 1..10 из 14, но не у 11..13, хотя
     card/port там не меняются). Сейчас везде пишется безопасная константа
     0x01/нули — байт-в-байт сходится ВСЁ, кроме этих 3 полей (и производных от
     них чек-сумм). Нужен второй реальный образец с другой раскладкой
     колонок/портов внутри группы, чтобы разобрать правило.
   - `XInPort`/`YInPort` при ненулевых значениях в Complex Screen — оба
     реальных сэмпла содержали 0, смысл ненулевых (daisy-chain регионы на
     одном физическом порту?) неизвестен.
   - Порядок карт при НЕСКОЛЬКИХ цепочках/портах на один Complex Screen —
     единственный реальный сэмпл содержал ровно одну цепочку.
2. Дублирующиеся координатные поля в 17-байтовой записи Standard Screen
   (col*cabW/row*cabH на +4/+6) — «по аналогии, не подтверждено напрямую»
   для некабинетов, отличных от 128px/неквадратных.
3. Импорт — см. секцию 8 целиком, включая отсутствие тестов.

## 10. Тестовое покрытие

**Хорошо покрыто**: одноэкранный Standard Screen (2 golden-сэмпла — тривиальный
1×1 и сложный 4×3/11 записей с не-построчной цепочкой), Complex Screen
(2 golden-сэмпла, отличающиеся ровно одним Ethernet-портом), эквивалентность
combine вырожденному случаю прямой записи, точное размещение дырок по
координатам реального сэмпла, отклонение перекрытия/несовпадения размера,
разрешение цепочки через 2 экрана, пропуск blank-сентинела при выборе
дефолта заголовка, `writeStandardMultiScreen` (3 golden-сэмпла — 2 экрана
разного размера с ненулевым зазором Coordinate X, 3 экрана, 2 экрана на

экранов для Separate-экспорта (пустая/`null` карта групп совпадает со старым

blank-дыры в границах группы, а не всей сетки — см.

- Нет теста на combine с несколькими разными Sending Card/портами по

- Группировка (`splitSeparateGrouped`) не проверена реальной загрузкой в
  NovaLCT — только юнит-тестами, см. секцию 9, п.1.
- Нет теста для `NovaLctScrParser` вообще.
- Нет теста, гоняющего сам UI-поток `NovaLctControllerExportDialog`/

  гвардов вроде «предупреждение о нерасключённых» проверяется только

- Нет теста на связку с последующим скачиванием `.rcfgx`.

## 11. Архитектурная граница модели — куда класть новые поля

`ledscheme-model` (`C:\Development\ledscheme-model`) — только
библиотечные/типовые классы, используемые деталями формата: `ControllerType`
(вся логика нумерации карт/портов из секции 6 — `effectivePortCount`,
`isEffectivePortEthernet`, `ethernetPoolCount`/`ethernetPortCountInPool`,
`ethernetPoolLocalPort`, `globalPortFor`), `SchemaCard`/`CardPort`/
`PortDirection`, `CabinetType` (resolutionWidth/Height → `cabW`/`cabH`;
widthMm/heightMm → офсеты Complex Screen).

Классы экземпляров проекта остаются в `VJsTB_reborn`'s own `model` package
(не расшарены, это данные конкретного проекта, не библиотечный контент):
`CabinetInstance` (rowIndex/colIndex/hidden/cabinetTypeId-override/
offsetXMm/offsetYMm), `ControllerInstance`, `SignalChain`
(portNumber/cabinetInstanceIds/backup-поля), `Screen`.

**Практическое следствие**: новое поле уровня ТИПА (например, метаданные
контроллера, нужные NovaLCT) — в `ledscheme-model`, и потребует `mvn
-DskipTests install` там перед пересборкой `VJsTB_reborn`. Новое поле
уровня ЭКЗЕМПЛЯРА (например, кабинет-специфичный оверрайд только для
NovaLCT) — прямо в `VJsTB_reborn`, без кросс-репозиторного шага.
